Start with the idea

Binary search means checking the middle of an ordered row, then continuing in only the half where the value could still be.

Think of a number-guessing game where the answer is “higher” or “lower”. A middle guess lets you rule out many possibilities at once. This only works for an array if its values are already in order.

A small example

Look for 8 in [2, 4, 6, 8, 10]. The middle value is 6. Because 8 is larger, ignore 6 and everything to its left. In the remaining [8, 10], check 8 and find it. Its original position is index 3, counting from 0.

The diagram below searches for 7 in a larger ordered row. “Low” and “high” mark the first and last positions still possible; “mid” is the middle position we check. The values themselves stay still.

Searching / Binary search · The textbook definition

The textbook definition

Binary search finds a value in a sorted array by repeatedly comparing the key with the middle element of the part of the array that could still contain it. If the middle element equals the key the search ends. Otherwise the half that cannot contain the key is discarded, and the search continues in the other half. It returns the index of the key, or -1 when no candidates remain.

Precondition: sortedThe array must already be in order (ascending, or descending with the comparison flipped). On unsorted data the answer is simply wrong.
low and highThe first and last indexes that could still hold the key. Together they are the search window.
midThe probe position, the middle of the window: low + (high − low) / 2.
ProbeOne comparison of the key with arr[mid].
DiscardThrowing away the half that cannot contain the key, by moving low up (mid + 1) or high down (mid − 1).
Not foundThe window becomes empty: low > high.
InvariantIf the key is in the array at all, it is somewhere in low … high.

The name means “two parts”: every probe splits the remaining candidates into two parts and throws one away.

Searching / Binary search · In plain language

In plain language

Guess the number I am thinking of by always guessing the middle: each answer throws away half of the possibilities.

You have played this game. I think of a number from 1 to 100, and you guess. After each guess I say “higher” or “lower”. A clever player never guesses randomly: she guesses 50, the middle. Whatever the answer, half of all the numbers are gone at once. Then she guesses the middle of what is left.

A phone book works the same way. Looking for “Mokoena”, you do not start at page 1: you open the book in the middle, see that you are at “K”, know that M comes later, and ignore everything before that page.

Here is the game for a secret number of 37:

Guess no.GuessAnswerNumbers still possible
150too high → guess lower100
225too low → guess higher49
337equal: found!24

Only 3 guesses were needed out of 100 possibilities. The very worst case for 1 to 100 is 7 guesses, because 100 → 50 → 25 → 12 → 6 → 3 → 1 uses at most seven halvings. A player who guesses 1, 2, 3, … needs up to 100.

Binary search is exactly this game, played on an array: mid is the guess, “higher / lower” is the comparison with arr[mid], and the sorted order is what lets a single comparison eliminate half of the array.

Searching / Binary search · The main idea

The main idea

Binary search keeps a window of cells where the key could still be, and each probe shrinks it. The window starts as the whole array and obeys one rule that never breaks:

Invariant: if the key is in the array, it is inside the window low … high.

Here is the search for 18. Crossed-out cells have been discarded; low, mid and high are labelled. After the first probe, 34 is larger than the key, so everything from 34 rightwards is discarded. The second probe lands on 18.

Why the middle?

Probing the middle guarantees that, whatever the comparison says, at least half the window disappears. Probing anywhere else risks removing less. The window for ten values shrinks roughly 10 → 5 → 2 → 1, halving each time, so the number of probes is the number of times you can halve n, about log₂ n.

Why the array must be sorted

The discarding step is only legal because of order. “34 > 18, so 18 cannot be to the right of 34” is true only if everything to the right of 34 is at least 34. In an unsorted array that statement is false, and binary search would throw away the very cell it was looking for. The mistakes section shows this with a real example.

1
Set low = 0, high = n − 1.
2
While low ≤ high: compute mid.
3
Equal to the key? Return mid.
4
Key larger? low = mid + 1. Key smaller? high = mid − 1.
5
Window empty? Return -1.
Searching / Binary search · Probe, compare, discard

Probe, compare, discard

Each loop turn of binary search is three small steps. Keeping them separate makes the trace table easy to write.

ProbeCompute mid and read arr[mid].
CompareThree possible answers: arr[mid] == key (found), arr[mid] < key (key is to the right), arr[mid] > key (key is to the left).
DiscardMove one end of the window past mid: low = mid + 1 or high = mid − 1.
IterationOne probe, one comparison outcome and one discard. “After how many iterations?” counts these.

Why mid + 1 and mid − 1, not just mid?

The probe at mid has already been compared and failed, so mid itself is ruled out. If you wrote low = mid the window could stay the same size forever, for example with low = 2, high = 3, where mid is 2. Stepping past mid guarantees the window shrinks every time, so the loop must end.

Why low + (high − low) / 2 and not (low + high) / 2?

For small arrays they give the same answer. But low + high can be too big for an int. An int in Java holds numbers up to 2,147,483,647 (about 2.1 billion). With low = 2,000,000,000 and high = 2,100,000,000:

FormulaCalculationResult
(low + high) / 22,000,000,000 + 2,100,000,000 = 4,100,000,000: more than the largest int, so Java wraps round to a negative number-194,967,296 → -97,483,648 (a negative index: crash)
low + (high − low) / 22,100,000,000 − 2,000,000,000 = 100,000,000, halved is 50,000,000, plus low2,050,000,000 (correct)

The second form only ever adds half of the distance between the ends to low, so it can never leave the range of valid indexes. The extra effort costs nothing, so it is the form to always use.

Searching / Binary search

Discard half each time

Binary search works only on a sorted array. Compare with the middle: go left when the key is smaller, right when it is larger, or stop when equal.

Non-negotiable rule: if the array is not sorted by the same key, binary search can discard the part that actually contains the answer.

Implementation

Iterative binary search
public static int binarySearch(int[] arr, int key) {
    // The active search range includes both endpoints.
    int low = 0, high = arr.length - 1;
    while (low <= high) {
        // This form avoids overflow from (low + high) / 2.
        int mid = low + (high - low) / 2;
        if (arr[mid] == key) return mid;
        // Ascending order: larger keys can only be on the right.
        if (arr[mid] < key) low = mid + 1;
        else high = mid - 1;
    }
    // The range is empty when low passes high.
    return -1;
}
Recursive implementation
Write it from scratch
  1. Set low and high.
  2. Repeat while low <= high.
  3. Calculate mid.
  4. Return, move low, or move high.
  5. Return -1.
Descending-order change

Equality stays the same, but the direction reverses: when key > arr[mid], set high = mid - 1; otherwise set low = mid + 1.

Questions

Why is binary search faster on large arrays?
Each comparison discards about half of the remaining values, so the number of steps grows logarithmically rather than linearly.
What is the recursive base case for “not found”?
low > high. It means no indexes remain in the current search range.
Binary search in one sentence

On a correctly sorted array, compare with the middle and discard the impossible half until a match is found or the range is empty.

Sorted data only

This is the one big requirement. If the data is not sorted, either sort it first (O(n log n)) or use linear search.

Random access

It jumps straight to arr[mid]. That is instant in an array but slow in a linked list, where reaching the middle means walking there. On a linked list, binary search loses its advantage.

Duplicates

If the key appears several times, binary search returns one of them, not necessarily the first. With [10, 20, 20, 20, 30] and key 20 it returns index 2, the middle one. Finding the first or last occurrence needs a small variation.

Logarithmic cost

Doubling the array size adds only one extra probe.

Ten times more data adds about 3 probes, not 10 times the work. Even for a billion values binary search needs at most 30 probes.

Average and best case

The average is still about log₂ n: most keys sit deep in the tree of halving, not near the first probe. The best case is a single probe.

Is it worth sorting first?

Binary search is fast, but it needs sorted data, and sorting costs about n log₂ n. For n = 1,000,000 that is roughly 20,000,000 steps, once. Each later linear search costs up to 1,000,000 steps but each binary search only 20, saving almost a million steps per search. So the sort pays for itself after about 21 searches. For one search, just scan; for many, sort once.

Space

The iterative version needs just low, high and mid: O(1).

Searching / Binary search · When to use it

When to use it

A good choiceLarge collections that are sorted (or that you can sort once) and searched many times; dictionaries, phone books, product catalogues, leaderboards; any array with random access.
A poor choiceUnsorted data searched once; very small arrays (linear search is just as fast and simpler); linked lists (no fast access to the middle); data that changes constantly, since keeping it sorted costs time.

The decision rule: sorted + random access + searched more than a few times → binary search. Otherwise linear search. This is exactly the choice behind the past paper's last question: of the four algorithms listed, binary search is the most efficient for searching, O(log n).

What searching means

Searching is the process of looking for a particular element in a collection. A successful method returns its index; an unsuccessful search returns -1.

Search keyThe value being looked for.
ComparisonChecking the key against an array value.
Ordered collectionValues already arranged by a rule.
Unordered collectionValues may appear in any order.

Use a search to check membership, display or update an item, or find the position needed for another operation.

Reading Big-O: why we count steps

Big-O describes how the number of steps grows as the number of values n grows. It ignores small constant details and keeps the dominant growth. Best, average and worst case describe three situations for the same size n: the most favourable input, a typical input, and the least favourable input. In this guide one comparison means one probe: one look at an array value (for binary search, arr[mid]), even though Java may spell it as two tests such as == then <.

Searching / Binary search · Descending order

Descending order

If the array is sorted from largest to smallest, the logic is the same but the directions swap: a probe that is larger than the key means the key is to the right, where the smaller values are.

Ascending array
if (arr[mid] == key) return mid;
if (arr[mid] < key) low = mid + 1;
else                high = mid - 1;
Descending array
if (arr[mid] == key) return mid;
if (arr[mid] > key) low = mid + 1;
else                high = mid - 1;

Searching / Binary search · Common mistakes

Common mistakes

1
Searching an unsorted array.
Binary search on [5, 1, 9, 3, 7] for 3 (which is there, at index 3) returns -1: the first probe reads 9, concludes “3 must be to the left”, and discards the cell holding 3. Always check the precondition.
2
Computing mid as (low + high) / 2.
Works for small arrays but can overflow for very large ones (see the earlier section). Write low + (high − low) / 2.
3
Looping with low < high instead of low <= high.
When one candidate remains, low == high, and the loop quits without checking it. On [1, 3, 5, 7, 9], searching for 9 (index 4) returns -1 with the wrong condition.
4
Setting low = mid or high = mid.
The window may stop shrinking and the loop never ends. Use mid + 1 and mid − 1.
5
Getting the direction wrong for descending data.
Larger-than-key means go right in a descending array. Decide this before you trace.
6
Comparing Strings with < or ==.
Use compareTo for order and .equals for equality.
7
Returning mid when the key is absent.
Return -1 only after the loop ends.
8
Miscounting iterations.
One iteration is one probe. The final check that finds low > high is not a probe.
Searching / Binary search · A test-ready summary

A test-ready summary

Binary search finds a key in a sorted array. It keeps a window low…high, probes the middle at mid = low + (high − low) / 2, and either returns mid if arr[mid] equals the key or discards the half that cannot contain the key (low = mid + 1 or high = mid − 1). When the window is empty (low > high) it returns -1. Each probe halves the candidates, so the worst case is O(log n), at most ⌊log₂ n⌋ + 1 probes, with O(1) extra space. It requires sorted data and random access, and is far faster than linear search, O(n), on large sorted arrays.

B. Explain the best and worst time using input examples. [4]

Best: key equals the first midpoint, one probe. Worst: key absent or only located after the range repeatedly halves, logarithmic probes.

C. Debug the bounds and return statement. [4]

low and high are inclusive. Use low <= high, calculate the overflow-safe midpoint, and exclude mid using ±1. The not-found return belongs after the range empties.

D. Return the first occurrence of a duplicate. What must change? [3]

Keep a result variable. On equality record mid, set high = mid - 1, and continue. Return the recorded index after the loop.

E. Empty array: can this code access index 0? [2]

No. high is -1, so low <= high is false. It returns -1 without reading a cell.
