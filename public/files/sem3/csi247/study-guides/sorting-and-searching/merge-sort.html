Start with the idea

Merge sort puts values in order by solving smaller parts first, then joining two ordered parts by repeatedly taking the smaller front value.

Imagine two small piles of numbered cards, each already ordered from smallest to largest. Compare their front cards and copy the smaller one into a new row. Repeat until one pile runs out, then copy what is left of the other. That joining step is called a merge.

A small example

To sort [4, 2, 1, 3], split into smaller parts until each has one value. The left pair becomes [2, 4]; the right pair becomes [1, 3]. Merge those ordered pairs by taking 1, then 2, then 3, then the leftover 4: [1, 2, 3, 4].

The diagram below follows eight values. Going down the tree means splitting the problem, not rearranging values. Coming back means finishing both smaller parts, merging their results, and passing the ordered result to the larger problem above.

Sorting / Merge sort · The textbook definition

The textbook definition

Merge sort is a comparison-based, divide-and-conquer sorting algorithm. It splits the array into two halves, sorts each half by calling itself recursively, and then merges the two sorted halves into one sorted array. A sub-array of one value is already sorted, so it is the base case of the recursion. The work of actually putting values in order is done by the merge step on the way back up.

Divide and conquerSolve a big problem by solving smaller copies of the same problem, then combining the answers.
RunA sorted stretch of the array. Single values are runs of length 1; the merge step builds longer runs.
Split point midThe index where the range is cut: mid = start + (end − start) / 2. The left half is start..mid and the right half mid + 1..end.
Base caseA range with one value (start ≥ end). It returns immediately, because one value is already sorted.
MergeCombine two sorted runs into one by repeatedly taking the smaller of the two front values.
Temporary arraysCopies of the two halves made during a merge, so values can be written back without overwriting unread ones.
LevelOne row of the recursion tree. Halving 8 values down to single values takes 3 splitting levels.

Everything interesting about merge sort comes from one fact: merging two sorted runs is cheap, because only the two front values ever need to be compared. The recursion exists only to create sorted runs for the merge to work on.

Sorting / Merge sort · In plain language

In plain language

Merge sort turns “sort this pile” into “zip together two sorted piles” over and over.

Imagine two stacks of exam papers, each already sorted by mark from lowest to highest. You want one sorted stack. You do not need to look through the stacks: only the two papers on top matter. Whichever top paper has the lower mark goes onto the new stack, and then you look at the two tops again.

That is a merge. It is like a zip: two sorted lines go in, one sorted line comes out, and every paper is touched once.

Merge sort uses this trick on an unsorted pile: split the pile in half and keep splitting until each piece is a single paper. A single paper is a perfectly sorted stack of one. Now merge pairs of stacks, then pairs of those, until one stack is left.

Why this is fast

Look at any one row of the tree: all its boxes together hold the 8 values once, so merging a whole row costs about 8 steps. There are only 3 rows of merges, because halving 8 down to 1 takes 3 cuts. Total work ≈ 8 × 3 = 24 value-writes. For a million values there are only about 20 rows, so the work is about one million × 20, not one million × one million. That halving is the same trick binary search uses.

The mental picture: the recursion is just a way of organising merges. The real sorting happens in the merge step, always on two runs that are already sorted.
Sorting / Merge sort · Split, call, merge

Split, call, merge

Three different things happen in merge sort, and a trace mixes them up unless you keep them apart.

SplitCalculating mid. No values move; only a number is computed.
CallRecursing on a half. A call that waits for its two halves to finish is parked on the call stack.
MergeThe only phase that moves values: they are copied from two temporary arrays back into arr in sorted order.
ComparisonOne question per output value while both runs still have values: left[i] <= right[j].

Where exactly is the split?

The left half is start..mid and the right half mid + 1..end, with mid = start + (end − start) / 2 (integer division). When the number of values is odd, the left half gets the extra value:

What is waiting on the call stack?

Merge sort calls itself, so Java keeps a stack of calls that have started but not finished. At the moment of the first merge on our eight values, three calls are alive:

PositionCallWhat it is doing
top (running)mergeSort(arr, 0, 1)Both of its halves, (0, 0) and (1, 1), have returned: it merges them now.
belowmergeSort(arr, 0, 3)Waiting. Its left half (0, 1) is still running; the right half (2, 3) has not started.
bottommergeSort(arr, 0, 7)Waiting. Its left half (0, 3) is still running; the right half (4, 7) has not started.

The stack is never deeper than the number of levels (here 4), which is why merge sort's recursion cannot overflow the stack for any realistic array: log₂ n is small even for a billion values (about 30).

The left half is always finished first

Because the left call is written before the right call, the whole left side is sorted and merged before the right side is even cut up. This is why the merges happen in depth-first order (see the trace table earlier), and why a bottom-up version that goes level by level makes the same merges in a different order.

Sorting / Merge sort

Divide first. Merge on the way back.

Merge sort repeatedly divides an array into halves until every piece has one value. It then combines sorted pieces into larger sorted pieces.

1
Base case: start >= end. A section with one value is already sorted.
2
Divide: calculate mid.
3
Recur left: sort start..mid.
4
Recur right: sort mid+1..end.
5
Merge: combine both sorted halves.

Implementation

Recursive merge sort
public static void mergeSort(int[] arr, int start, int end) {
    // A zero- or one-value range is already sorted.
    if (start < end) {
        // Split without risking integer overflow.
        int mid = start + (end - start) / 2;
        // Sort both halves before combining them.
        mergeSort(arr, start, mid);
        mergeSort(arr, mid + 1, end);
        merge(arr, start, mid, end);
    }
}

Ascending ↔ descending

Ascending merge chooses the left value when left[i] <= right[j]. Descending chooses it when left[i] >= right[j].

Same fronts, opposite choice: with left front 29 and right front 3, ascending takes 3; descending takes 29 because 29 >= 3.

Same time for every input

The array is cut in the same places whatever the values are, and every level merges every value. A sorted, reversed or random array all cost O(n log n). That predictability is merge sort's main selling point.

Stable

Equal values keep their original order, provided the merge uses <= so ties are taken from the left run (which contains the earlier values). Changing it to < silently loses stability.

Not in-place

The merge copies both halves into temporary arrays before writing back, so extra memory proportional to n is needed: O(n). This is the price paid for the guaranteed speed.

Not adaptive

The standard version cannot take advantage of existing order, as the sorted example showed.

Comparison-based

For comparison-based sorting, O(n log n) is the best possible worst case, and merge sort reaches it.

How many times can you halve 8 before you reach 1? Three: 8 → 4 → 2 → 1. In general log₂ n times. That is the number of rows of merging.

Each row merges every value exactly once (the boxes in a row together hold all n values), so one row costs about n steps. Rows × work per row:

n values × log₂ n levels = n log₂ n steps

You can also write this as a recurrence: sorting n values costs two sorts of n / 2 plus one merge of n, that is T(n) = 2·T(n / 2) + n, and unrolling it gives the same n log₂ n.

For a million values, merge sort takes about 20 million steps and a quadratic sort about a trillion. Even if each step of merge sort cost ten times as much (because of copying), merge sort would still be thousands of times faster. This is why the sorting library of nearly every language uses a merge-sort relative.

Space

During one merge, two temporary arrays hold copies of the two halves: together at most n values. Merges happen one at a time, so the copies are discarded between them and the peak extra memory is O(n), plus O(log n) for the call stack.

Sorting / Merge sort · When to use it

When to use it

A good choiceLarge arrays; when you need guaranteed O(n log n) whatever the data; when you need a stable sort (sorting records by one field while keeping the order of ties); when data is too big for memory and is sorted in chunks that are merged (external sorting); sorting linked lists.
A poor choiceVery small arrays, where the overhead of recursion and copying costs more than a simple insertion sort; situations with very little spare memory (O(n) extra space); data that is already nearly sorted, where insertion sort is almost free.

Real libraries combine the ideas: they use merge sort (or a close relative) for the big picture, and switch to insertion sort for pieces smaller than about 10 to 20 values, because on tiny arrays the simple sort wins. Knowing both lets you see why.

Before the algorithms: what does sorted data give you that unsorted data does not, and what does it cost?

Sorting / Merge sort · Descending order

Descending order

To sort largest to smallest, change the comparison that decides which front value is taken: take the left value when it is greater than or equal to the right one.

Ascending
arr[cur++] = left[i] <= right[j]
        ? left[i++]
        : right[j++];
Descending
arr[cur++] = left[i] >= right[j]
        ? left[i++]
        : right[j++];

The splitting, the recursion, the base case and the leftovers loops do not change. Only the merge direction does, and note that it is still = that makes ties take the left value, which keeps the sort stable in both directions.

Sorting / Merge sort · Common mistakes

Common mistakes

1
Recursing on mid instead of mid + 1 for the right half.
The ranges must not overlap: left is start..mid, right is mid + 1..end. Overlap causes endless recursion or wrong results.
2
Merging before the halves are sorted.
merge must come after both recursive calls. Merge only works on two sorted runs.
3
Using < instead of <= in the merge.
The sort still sorts but is no longer stable: equal values from the right run jump ahead of equal values from the left.
4
Forgetting the leftovers.
When one run is exhausted, the remaining values of the other must still be copied. Without the two leftover loops the end of the array keeps stale values.
5
Copying the left half with copyOfRange(arr, s, m).
The end index is exclusive, so the left half needs m + 1: copyOfRange(arr, s, m + 1).
6
Wrong base case.
Stop when start >= end (zero or one value). Testing start == end only can loop forever on an empty range.
7
Writing the answer into the temporary arrays.
The result must land back in arr, starting at index start, not index 0.

Expecting the merges to happen level by level.

Sorting / Merge sort · A test-ready summary

A test-ready summary

Merge sort is a stable, comparison-based, divide-and-conquer sorting algorithm. It splits the array at the midpoint, recursively sorts the left and right halves, and then merges the two sorted halves into one sorted array by repeatedly taking the smaller front value (taking the left value on ties). A single value is the base case. Its time complexity is O(n log n) in the best, average and worst cases, because there are log₂ n levels and each level merges n values, but it needs O(n) extra space and is not in-place. It is the right choice for large arrays and when a guaranteed running time or stability matters, and a poor choice when memory is very limited.

Two traps on that question: (1) Binary search is O(log n), not O(n²): it does not have a loop inside a loop; each pass halves the work. (2) Comparing a searching algorithm with sorting algorithms is not quite fair, since binary search needs data that is already sorted. Say so if the question lets you; the expected answer is still binary search.

How to read a Big-O answer quickly

  • One loop over all the data → O(n). Linear search.
  • A loop inside a loop over the data → O(n²). Bubble, selection and insertion sort.
  • Halve the problem each step → O(log n). Binary search.
  • Halve the problem and do n work at each level → O(n log n). Merge sort.
Quick check: put these in order from fastest to slowest growth: O(n²), O(log n), O(n log n), O(n)
