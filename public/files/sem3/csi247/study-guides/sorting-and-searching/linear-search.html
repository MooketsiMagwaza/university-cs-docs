Searching / Linear search · The textbook definition

The textbook definition

Linear search (also called sequential search) finds a value in a collection by examining the elements one at a time, in order, starting from the first. It stops as soon as an element equals the target and returns that element's index. If it reaches the end without a match it reports failure, by convention by returning -1. It works on any array, sorted or not.

KeyThe value we are looking for. Also called the target or search value.
IndexThe position of a value in the array, starting at 0.
Probe / comparisonOne equality test, arr[i] == key. The cost of a search is measured in these.
MatchA cell whose value equals the key.
FoundThe search returns the index of the match.
Not foundThe search returns -1, a value that can never be a valid index.
Early exitStopping at the first match instead of examining the rest.

“Linear” describes the cost: in the worst case you look at every one of the n elements, so the work grows in a straight line with the size of the array.

Searching / Linear search · In plain language

In plain language

Open the drawers one by one until you find what you are looking for, or run out of drawers.

Imagine a row of ten closed drawers and you are looking for the one containing your keys. You have no idea which it is, so you open the first drawer, then the second, then the third, until you find them. If you open the last drawer and still have not found them, they are not in the row.

That is the entire algorithm. There is no clever shortcut because nothing tells you where to look. The only way to be sure a value is not there is to have looked everywhere.

Searching / Linear search · The main idea

The main idea

Linear search is built on one statement that stays true all the way through, called a loop invariant:

Invariant: when the loop is about to examine index i, the key is not in cells 0 … i − 1.

The loop is about to examine index 0: nothing is ruled out yet

6329857218422354832

The loop is about to examine index 3: indexes 0..2 are ruled out

6329857218422354832

The loop is about to examine index 7: indexes 0..6 are ruled out

6329857218422354832

Each failed comparison enlarges the ruled-out region by one cell. That has two consequences:

  • If a comparison succeeds at index i, the key is there, and returning i is correct.
  • If the loop ends, every cell has been ruled out, so returning -1 is correct. The return -1 belongs after the loop, never inside it.

Searching / Linear search · Comparison, match, return

Comparison, match, return

A linear search only ever does two things: compare and return. Being precise about both is what makes a trace correct.

Comparisonarr[i] == key. Only equality is tested, never < or >, which is why the order of the array does not matter.
MatchThe comparison is true. The search ends here.
Return valueThe index on success, -1 on failure. Some programs return true / false instead; that changes the answer's type, not the work done.
MissA false comparison. The search moves on.

Why -1?

The return value has to tell the caller two things with one number: where, or not found. Every real index is 0 or more, so -1 can never be confused with one. Returning 0 for “not found” would be a bug, because index 0 is a real position.

Implementation

Iterative linear search
public static int linearSearch(int[] arr, int key) {
    // Visit every valid index from left to right.
    for (int i = 0; i < arr.length; i++) {
        // Stop immediately when the current value matches.
        if (arr[i] == key) return i;
    }
    // Reaching this line means that no position matched.
    return -1;
}
Recursive implementation
Write it from scratch
  1. Accept the array and key.
  2. Loop from index 0 to length - 1.
  3. Return the matching index.
  4. After the loop, return -1.
Ascending or descending?

Linear search uses equality only, so the same code works for ascending, descending, or unsorted arrays.

Debug checklist
  • Use i < arr.length, not <=.
  • Put return -1 after the loop.
  • Start recursion with index 0.

Strings and objects. For primitive cells == compares values. For reference cells it compares references, so text must be compared with .equals.

Search a String array
public static int linearSearchStrings(String[] names, String key) {
    for (int i = 0; i < names.length; i++) {
        // Unfilled cells are null; calling equals on null would throw.
        // equals compares the text. == would only compare references.
        if (names[i] != null && names[i].equals(key)) return i;
    }
    return -1;
}

Quick check: why test names[i] != null first?
A cell that was never assigned holds null. Calling .equals through it throws NullPointerException. The && stops before that call.
Quick check: can new String("Raj") == "Raj" be true?
No. new String(...) creates a different object, so the references differ even though the text matches. .equals returns true.

Questions

When is linear search a sensible choice?
When the collection is small, unsorted, or searched only once. Sorting first would add unnecessary work.
What are the best and worst cases?
Best: the key is at index 0, so one comparison gives O(1). Worst: the key is last or absent, so all n values are checked: O(n).
Linear search in one sentence

Check each value in order; return its index on a match, otherwise return -1 after the final position.

No precondition

It needs the data in no particular order, and it does not care whether the array is ascending, descending or random. This is its great strength: it always works.

Simple and safe

There is no arithmetic on indexes, nothing to overflow, and no way to skip over the answer. It is hard to get wrong.

Any structure you can walk

It needs only “give me the next element”, so it works on a linked list, a file read line by line, or any stream, where jumping to the middle (as binary search does) is impossible.

The price is time

The cost grows in a straight line with the number of values. Search a million values and a miss costs a million comparisons.

Searching / Linear search · Why those complexities occur

Why those complexities occur

Best case · O(1)The key is in the first cell: one comparison, whatever the size.
Worst case · O(n)The key is in the last cell or missing: all n comparisons.

The cost depends on where the key is

For our ten values, the number of comparisons needed to find a key is its index plus one. Here is that cost for a key in each position:

A taller bar means more comparisons. A key that is absent costs the full height of the last bar, 10.

The average case

If the key is equally likely to be in any cell, the average cost is the middle of 1 and 10:

(1 + 2 + … + n) / n = (n + 1) / 2 → O(n)

For ten values that is 5.5 comparisons. Halving the cost still leaves a cost proportional to n, so the order of growth is linear.

Searching / Linear search · When to use it

When to use it

A good choiceThe data is not sorted and is searched only once or twice; small collections (a handful of values); a quick check inside a bigger program; data in a structure with no random access (linked list, file); when you need the first match, or all matches.
A poor choiceA large array searched many times (sort it once, then use binary search); when the data is already sorted (binary search is far faster); when speed matters and you can organise the data in advance.

The honest comparison: sorting an array first costs about n log n. If you will only search once, scanning (n) is cheaper than sorting and then binary searching. If you will search many times, the one-off sort pays for itself, as the binary-search chapter shows with numbers.

Searching

What searching means

Searching is the process of looking for a particular element in a collection. A successful method returns its index; an unsuccessful search returns -1.

Search keyThe value being looked for.
ComparisonChecking the key against an array value.
Ordered collectionValues already arranged by a rule.
Unordered collectionValues may appear in any order.

Use a search to check membership, display or update an item, or find the position needed for another operation.

Reading Big-O: why we count steps

Big-O describes how the number of steps grows as the number of values n grows. It ignores small constant details and keeps the dominant growth. Best, average and worst case describe three situations for the same size n: the most favourable input, a typical input, and the least favourable input. In this guide one comparison means one probe: one look at an array value (for binary search, arr[mid]), even though Java may spell it as two tests such as == then <.

for (int i = 0; i < arr.length; i++) {

}
return count;

The first-match version is the only one that can finish early. Any question that needs all the matches, or the last, forces a full scan every time: n comparisons whether or not the key is present.

Searching / Linear search · Common mistakes

Common mistakes

1
Returning -1 inside the loop.
for (...) { if (arr[i] == key) return i; else return -1; } gives up after the first cell. The failure return belongs after the loop.
2
Looping to i <= arr.length.
Index arr.length does not exist and throws ArrayIndexOutOfBoundsException. Use <.
3
Returning 0 for “not found”.
0 is a valid index. Use -1.
4
Comparing Strings with ==.
That compares references. Use arr[i].equals(key); and test for null cells first if the array may have empty slots.
5
Assuming the array must be sorted.
Linear search does not need sorting. Sorting first just to linear search wastes time.
6
Counting a comparison after the match.
The search stops at the match, so the comparison that succeeds is the last one counted.
7
Returning the value instead of the index.
The caller already knows the value (it is the key). The useful information is the position.
8
Believing it is “slow”.
It is only slow on large data searched repeatedly. For ten values it is as fast as anything.
Searching / Linear search · A test-ready summary

A test-ready summary

Linear search examines the elements of an array one at a time from the first, comparing each with the key, and returns the index of the first match or -1 if the end is reached without one. It needs no sorted data and works on any collection. Its best case is O(1) (key in the first cell), and its average and worst cases are O(n) (about n / 2 and n comparisons), with O(1) extra space. It is the right choice for small or unsorted data searched rarely, and the wrong choice for large collections searched repeatedly, where sorting once and using binary search is faster.
