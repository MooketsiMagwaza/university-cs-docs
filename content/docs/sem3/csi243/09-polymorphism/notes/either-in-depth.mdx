`Maybe` tells a caller that a result is absent. A rejected password, a missing account and an invalid amount need different repairs. `Either` can return the explanation as data so the caller can respond to the actual problem.

<LearningObjectives items={["Read both type parameters and both constructors", "Write validators with distinct failure reasons", "Define and trace Either consumers and collectors", "Chain dependent validations and identify the first failure", "Convert deliberately between Maybe and Either"]} />

## 1. Why absence alone is insufficient

Imagine a login form that returns `Nothing`. Is the name missing, the password too short or the account locked? The caller cannot recover a reason that the result never stored. Give failure its own payload:

```haskell
data Either a b = Left a | Right b
```

This is the Prelude declaration, shown for reading. `Either` takes two type arguments. `Left :: a -> Either a b` carries an `a`; `Right :: b -> Either a b` carries a `b`. Each value contains one side, never both. The other type parameter still belongs to its type even though that value carries no payload of that type.

The common validation convention is `Left reason` for failure and `Right value` for success. It is a convention, not a restriction built into the declaration. `Either String Int` can mean an error message or a valid integer.

**Template:** `Left reason :: Either ErrorType ResultType` or `Right result :: Either ErrorType ResultType`. Fix both types when a printed value leaves one side unknown.

## 2. A plain choice between two types

A list may contain different constructors while every element has the same overall type. This can describe imported identifiers which are either numeric codes or text names, without treating either side as failure.

**Template:** `[Left code, Right name] :: [Either Int String]`: map a two-branch consumer over a uniformly typed list.

**Defining equations:**

```haskell
describeChoice :: Either Int String -> String
describeChoice (Left n) = "code " ++ show n
describeChoice (Right s) = "name " ++ s
```

### Variation: mixed choices

<HaskellTryIt>

**Validation template:**

```haskell
validate badReason invalid calculate input
  | invalid input = Left badReason
  | otherwise = Right (calculate input)
```

`badReason` is the failure payload, `invalid` the test, `calculate` the success computation, and `input` the checked data. With several rules, use guards in priority order. The first true guard determines the reported reason. Both branches must have the same full `Either ErrorType ResultType` type.

The age and mark validators below share this deliberately small parser for **non-empty ASCII decimal digits only**, with no sign or spaces. It avoids partial `read` and uses unbounded `Integer` arithmetic. It is not a general parser for Haskell numeric syntax.

## 3. `parseNatural`: a total decimal parser

Reject empty or non-digit input, otherwise accumulate the value. Each digit shifts the previous accumulator one decimal place.

**Template:** `digits accumulator remaining`: update with `10 * accumulator + digit`, and return the accumulator when no characters remain.

**Defining equations:**

```haskell
parseNatural :: String -> Maybe Integer
parseNatural [] = Nothing
parseNatural cs = digits 0 cs
  where
    digits acc [] = Just acc
    digits acc (c:rest)
      | c >= '0' && c <= '9' =
          digits (10 * acc + toInteger (fromEnum c - fromEnum '0')) rest
      | otherwise = Nothing
```

### Variation: several digits

## 5. `parseAge`: distinct text failures

## 6. `validatePassword`: ordered rules

This teaching policy requires at least six characters, no spaces and at least one ASCII digit. Rule order defines which failure is reported when several rules fail; it is not a security recommendation.

**Template:** `validatePassword text`: test each rejection rule in its stated priority, then return the original value.

**Defining equations:**

```haskell
validatePassword :: String -> Either String String
validatePassword s
  | length s < 6 = Left "too short"
  | ' ' `elem` s = Left "contains space"
  | not (any (\c -> c >= '0' && c <= '9') s) = Left "digit required"
  | otherwise = Right s
```

## 8. `lookupE`: name the missing key

## 10. `checkSorted`: report the first inversion

Check non-decreasing order, allowing equal neighbours. On failure report the **zero-based index of the right element** of the first descending adjacent pair. Empty and singleton lists are sorted.

**Template:** `go rightIndex remaining`: compare neighbours; move one place only after a successful comparison. A success returns the original list.

**Defining equations:**

```haskell
checkSorted :: Ord a => [a] -> Either Int [a]
checkSorted xs = go 1 xs
  where
    go _ [] = Right xs
    go _ [_] = Right xs
    go i (x:y:rest)
      | x > y = Left i
      | otherwise = go (i + 1) (y:rest)
```

## 28. Choose the error channel deliberately

| Requirement | Choice | Reason |
|---|---|---|
| A lookup is optional; its absence needs no explanation | `Maybe a` | The single absence case is enough |
| Several expected failures require different responses | `Either e a` | Error values retain their reasons |
| A tuple must store two pieces at once | `(a,b)` | A product holds both; `Either` holds one |
| An effectful operation encounters an exceptional condition | An exception, handled at a suitable boundary | Runtime failure is outside the ordinary return channel |

An `IO (Either e a)` can combine effects and an ordinary validation result; returning `Left` is not throwing an exception. A pure `Either` value is data the caller can pattern-match. An exception is not a substitute for specifying expected input failures.

| Mistake | Key GHC diagnostic or consequence | Repair |
|---|---|---|
| Return `Right "bad"` in a function returning `Either String Int` | `Couldn't match type` | Return `Left "bad"` |
| Return bare `"bad"` where an `Either` is required | `Couldn't match type` | Apply `Left` |
| Return just `Left` | A function is supplied where an `Either` value is expected | Supply the reason argument |
| Print `Left 3` with no right-side context | Unresolved `Show` constraint on the unseen right type | Annotate `Left 3 :: Either Int String` |
| Match only `Right` | `-Wincomplete-patterns`: `Pattern match(es) are non-exhaustive` | Handle the left case too |
| Use `lefts` without importing it | `Variable not in scope` | Add `import Data.Either (lefts)` inside the program |

This is deliberately rejected and remains a plain code block:

```haskell
-- Incorrect: the success side must contain an Int.
bad :: Either String Int
bad = Right "bad"
```

The stable key phrase is `Couldn't match type`; the surrounding expected/actual ordering depends on the expression context. The repair is `bad = Left "bad"` if the text describes failure.

## Summary

<Callout type="key" title="Remember">

`Either a b` holds one left payload or one right payload. Failure-on-left is a convention; validators use it to preserve reasons. `either` consumes with two handlers of one common result type. Collectors process a batch, whereas bind stops a dependent chain at its first error. Conversion to `Maybe` discards reasons. Equality and ordering inspect constructors before payloads.

</Callout>
