The previous lesson showed that a fully general type variable permits nothing. But `sumTree` needed `+`, and `elem` needs `==`. **Type classes** are how Haskell states what a type variable must support — and how the compiler decides, mechanically, which concrete behaviour a shared symbol like `==` actually runs.

## 1. Overloading

In Haskell, `Integer`, `Int`, `Bool`, `Char`, and many other types can all be compared for equality using `==`. The symbol is used for equality over **any type for which an equality operation can be defined**.

This is called **overloading**: one name with several implementations, chosen by the type it is used at. It exists because writing `eqInt`, `eqBool`, `eqChar`, ... for every type, and remembering which name to call where, would defeat the purpose of a shared, readable symbol — the *idea* of equality is the same across types even though the *machinery* differs completely (comparing two machine words is nothing like comparing two linked lists of characters).

```text
ghci> 3 == 3
True
ghci> 'a' == 'a'
True
ghci> "cs" == "cs"
True
ghci> True == False
False
```

Four different comparisons, four different underlying implementations, one name. Numeric literals are overloaded too — `4` belongs to both `Integer` and `Double`.

### How dispatch actually works

"Chosen by the type it is used at" is not hand-waving — it is a concrete mechanism. When GHC type-checks `3 == 3`, it first works out what type the `3`s have (here, defaulted to `Integer`). It then looks for the `Eq` **instance** declared for that type, and the `==` that runs is the one written in *that* instance's definition. Change the inferred type and you change which piece of code runs, with no change to what you typed.

<Mermaid chart={`flowchart TD
  E["Expression: x == y"] --> T{"What type does GHC infer for x and y?"}
  T -->|"Integer"| I["Run the Eq Integer instance's =="]
  T -->|"Bool"| B["Run the Eq Bool instance's =="]
  T -->|"Char"| C["Run the Eq Char instance's =="]
  T -->|"no Eq instance for that type"| X["Rejected at compile time: No instance for (Eq ...)"]`} caption="Overloading is resolved once, at compile time, by the inferred type of the operands — there is no run-time lookup and no way to write == on a type with no matching instance." />

`(+)` is overloaded the same way, but the difference between implementations is starker: `(+)` on `Int` is a single machine instruction, while `(+)` on a user-defined `Complex` number (from a library) does four separate multiplications and two additions under the hood. Same symbol, same *idea* — combine two values of the same type into a new one — completely different machine code, chosen once, at compile time, by the type.

```haskell
main :: IO ()
main = do
  print ((3 :: Int) + 4)
  print ((3.5 :: Double) + 4.25)
  print (show (3 :: Int) == show (3 :: Integer))
```

```text
7
7.75
True
```

The third line overloads three different symbols at once — `show` twice (once for `Int`, once for `Integer`) and `==` once (on the resulting `String`s) — and every one of them is resolved independently by the type of its own arguments.

## 2. What a type class is

A **type class** is a named collection of operations that a type may provide. A type that provides them is an **instance** of the class.

| Class | Requires the type to provide | So you may use |
|---|---|---|
| `Eq` | Equality testing | `==`, `/=` |
| `Ord` | Ordering | `<`, `<=`, `>`, `>=`, `compare`, `max`, `min` |
| `Show` | Conversion to `String` | `show`, and therefore `print` |
| `Num` | Arithmetic | `+`, `-`, `*`, `abs`, `negate` |

You met these in Chapter 8 as things to `derive`. Now you can say what deriving does: it asks GHC to generate the instance that makes your type a member of the class.

<Callout type="info" title="A class is not a type">
`Eq` is not a type — you cannot have a value of type `Eq`. It is a *constraint on* types: a statement about what a type can do. This is quite different from a class in Java or C++.
</Callout>

### What membership does and does not guarantee

Being an instance of `Eq` guarantees that `==` and `/=` exist for that type and type-check. It does **not** guarantee that `==` behaves the way you might informally expect equality to behave — that is a discipline the *instance's author* has to uphold, not something the compiler checks. A derived `Eq` instance compares every field of every constructor, which does behave the way you would expect. A hand-written one might not — Lesson 4 of this chapter builds exactly such an instance, deliberately, and shows the trade-off.

## 3. Reading a constraint

A **class constraint** appears before a fat arrow `=>`:

```haskell
sumList :: Num a => [a] -> a
```

Read: “for any type `a` **that is a member of** `Num`, `sumList` takes a list of `a` and returns an `a`.”

Everything before `=>` is the constraint. Everything after it is the type.

<InteractiveStepper>
  <StepperStep title="Find the fat arrow">Locate `=>` in the signature. Everything to its left is the constraint; everything to its right is the ordinary function type.</StepperStep>
  <StepperStep title="Read the constraint aloud">"For any type `a` that is a member of `<Class>`" — or, for a tuple of constraints, "that is a member of both `<Class1>` and `<Class2>`".</StepperStep>
  <StepperStep title="Read the remaining type as in Chapter 2">Apply the ordinary arrow-reading rule to the part after `=>`, exactly as if the constraint were not there.</StepperStep>
  <StepperStep title="Join the two readings">"For any type `a` that is a member of `Num`, `sumList` takes a list of `a` and returns an `a`."</StepperStep>
</InteractiveStepper>

```haskell
elem   :: Eq a => a -> [a] -> Bool
maximum :: Ord a => [a] -> a
show   :: Show a => a -> String
print  :: Show a => a -> IO ()
div    :: Integral a => a -> a -> a
(/)    :: Fractional a => a -> a -> a
```

You have been reading these since Chapter 2, where `Integral a =>` was glossed as “for any whole-number type `a`”. Now the mechanism is visible: `Integral` is a class, and `a` must be an instance of it.

Several constraints are written as a tuple:

```haskell
showAll :: (Show a, Ord a) => [a] -> String
showAll xs = show (maximum xs) ++ " is the largest of " ++ show xs
```

“For any type that is both showable and orderable.”

```haskell
main :: IO ()
main = do
  putStrLn (showAll [3, 1, 4, 1, 5])
  putStrLn (showAll "banana")
```

```text
5 is the largest of [3,1,4,1,5]
'n' is the largest of "banana"
```

One definition, and both constraints are earned honestly: `maximum` needs `Ord`, and the two `show` calls need `Show`. Change either type argument — try it on `[True, False]`, which has `Ord` and `Show` but nothing else — and it still runs; try it on a bag of unordered records with no `Ord` instance, and GHC rejects the call before running anything.

## 4. The three levels of generality

This is the idea to take from the chapter.

<Mermaid chart={`flowchart LR
  C["[Int] -> Int\nconcrete"] -->|"generalise the type\nkeep the same power"| N["Num a => [a] -> a\nconstrained"]
  N -->|"drop the constraint too"| G["[a] -> Int\nfully general"]
  G -.->|"add back only what's needed"| N`} caption="Moving right accepts more types but permits the function to do less with the elements; moving left narrows the accepted types in exchange for more capability. A constrained variable sits exactly between the two extremes." />

There is a trade-off in both directions:

- **More constraints** → works on fewer types, but the function can do more.
- **Fewer constraints** → works on more types, but the function can do less.

The right signature is the **most general one that still permits what the function needs**. Constraining to `Int` when `Num a` would do makes the function needlessly narrow.

### Worked exercise: choosing the right point on the spectrum

Suppose you are asked to write `countMatches`, which counts how many elements of a list equal a given value. Three candidate signatures:

```haskell
countMatches1 :: Int -> [Int] -> Int          -- too narrow
countMatches2 :: Eq a => a -> [a] -> Int      -- candidate
countMatches3 :: a -> [a] -> Int              -- too general
```

`countMatches3` cannot be written at all — comparing the target to each element needs `==`, which an unconstrained `a` forbids. `countMatches1` compiles and works, but locks the function to `Int` for no reason: nothing in the logic is specific to numbers. `countMatches2` is the answer — it is the most general signature under which the function's own body (which only ever uses `==`) still type-checks.

```haskell
countMatches :: Eq a => a -> [a] -> Int
countMatches v = length . filter (== v)

main :: IO ()
main = do
  print (countMatches 3 [3, 1, 3, 4, 3])
  print (countMatches 'a' "banana")
```

```text
3
3
```

## 5. Where constraints come from

You rarely write constraints from scratch. GHC infers them from the operations you use, and you copy them into the signature.

```haskell
-- Without a signature, GHC works out what is needed.
addUp xs = sum xs + 1
```

```text
ghci> :type addUp
addUp :: Num a => [a] -> a
```

`+` requires `Num`, so `Num a =>` appears. Ask for two different operations and both constraints surface together, in one tuple:

```haskell
rangeSize xs = maximum xs - minimum xs
```

```text
ghci> :type rangeSize
rangeSize :: (Ord a, Num a) => [a] -> a
```

`maximum` and `minimum` need `Ord`; `-` needs `Num`. Neither constraint was written by hand — GHC read the body and reported exactly what it required.

This is the practical technique: **write the function, ask GHCi for the type, then write that type into your file.** For course work, always write explicit signatures — they document intent and expose mistakes near their cause.

## 6. What goes wrong without a constraint

```haskell
-- Rejected.
sumList :: [a] -> a
sumList []     = 0
sumList (x:xs) = x + sumList xs
```

```text
* No instance for (Num a) arising from a use of '+'
  Possible fix: add (Num a) to the context of the type signature
```

GHC is explicit about the repair. `a` promises nothing, but `+` and the literal `0` both require `Num`. Adding the constraint fixes it:

```haskell
sumList :: Num a => [a] -> a
```

The same happens with comparison:

```haskell
-- Rejected: == is not available for an arbitrary type.
countOf :: a -> [a] -> Int
countOf _ [] = 0
countOf v (x:xs)
  | v == x    = 1 + countOf v xs
  | otherwise = countOf v xs
```

```haskell
-- Correct.
countOf :: Eq a => a -> [a] -> Int
```

<Callout type="warn" title="Read the error; it names the class">
“No instance for (Num a) arising from a use of '+'” tells you the class, the operation that needed it, and the fix. These are among the most helpful error messages GHC produces.
</Callout>

### A different failure: a concrete type with no instance at all

Every error above involved a **type variable** with no constraint. A second, easily confused failure involves a **concrete type that simply has no instance** — not because a signature is missing a constraint, but because nobody ever wrote (or derived) the instance for that specific type.

```haskell
data Direction = North | South | East | West
-- No deriving clause at all.
```

```text
ghci> North == South
<interactive>: error:
    * No instance for (Eq Direction) arising from a use of '=='
      Possible fix: add an instance declaration for (Eq Direction)
```

The fix is different in kind from the earlier ones. There is no signature here to add `Eq a =>` to — `Direction` is a fixed, concrete type, and the message says exactly that: add an *instance declaration*, most simply by deriving one.

```haskell
data Direction = North | South | East | West
  deriving (Eq, Show)
```

```text
ghci> North == South
False
ghci> North == North
True
```

<CommonMistake title="Two different 'No instance' errors, two different repairs">
`No instance for (Eq a) arising from a use of '=='` inside a function body means a **type variable** in your own signature is missing a constraint — add `Eq a =>` to that signature. `No instance for (Eq Direction) arising from a use of '=='` means a **specific, concrete type** was never given an `Eq` instance at all — add `deriving (Eq)` to that type's declaration, or write `instance Eq Direction where ...` by hand. Reading which one GHC named — a lowercase variable or an uppercase type — tells you immediately which repair applies.
</CommonMistake>

## 7. Class hierarchies

Classes can require other classes. `Ord` requires `Eq`, because ordering values presupposes being able to tell whether they are equal:

<Mermaid chart={`flowchart TD
  Eq --> Ord
  Num --> Integral
  Num --> Fractional`} caption="Ord's own definition requires every Ord instance to already be an Eq instance. Num, Integral and Fractional are three separate classes: Integral and Fractional each independently extend Num, but neither extends the other." />

A consequence: writing `Ord a =>` gives you `==` as well, because every `Ord` instance is also an `Eq` instance. You do not need to write `(Eq a, Ord a) =>`.

```haskell
-- Ord alone is enough; == comes with it.
countMax :: Ord a => [a] -> Int
countMax xs = length (filter (== maximum xs) xs)

main :: IO ()
main = do
  print (countMax [3, 1, 4, 1, 5, 9, 2, 6])
  print (countMax "mississippi")
```

```text
1
4
```

`countMax`'s signature only ever wrote `Ord a =>`, yet its body freely uses `==`. That is exactly what the hierarchy diagram promises: `Ord` cannot exist for a type without `Eq` already existing for it, so the compiler lets you use `Eq`'s operations under an `Ord` constraint without asking for both.

<RecognitionStrategy title="Spotting => versus ->, at a glance">
Look at what sits immediately to the left. `Eq a =>` pairs a class name with a type variable and is always followed by more type — never by a value being applied. `Bool ->` or `a ->` names the type of an actual argument. A quick test: delete the segment together with its arrow; if what remains still reads as a complete, sensible function type, you deleted a constraint; if the arrows no longer line up, you deleted an argument type.
</RecognitionStrategy>

## 8. Common errors

| Message or attempt | Cause | Repair |
|---|---|---|
| `No instance for (Num a)` | Arithmetic on an unconstrained variable | Add `Num a =>` |
| `No instance for (Eq a)` | `==` on an unconstrained variable | Add `Eq a =>` |
| `No instance for (Show Shape)` | A custom, concrete type with no `Show` | Add `deriving (Show)` |
| `No instance for (Eq Direction)` | A custom, concrete type with no `Eq` | Add `deriving (Eq)`, or write the instance by hand |
| `f :: Num a -> a -> a` | The constraint arrow is `=>`, not `->` | `f :: Num a => a -> a` |
| `(Eq a, Ord a) =>` | Redundant; `Ord` implies `Eq` | `Ord a =>` |
| Writing `[Int] -> Int` for a general function | Needlessly narrow | `Num a => [a] -> a` |
| Confusing a variable-missing-constraint error with a type-missing-instance error | Lowercase name vs uppercase name in the message | Lowercase → fix your signature; uppercase → fix that type's instance |
