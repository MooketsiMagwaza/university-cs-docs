You have been using polymorphic functions since Chapter 6 without naming them. `length` works on a list of anything. `fst` works on a pair of anything. This lesson explains how, and — just as importantly — what that "anything" costs the function itself.

## 1. Type variables

A **type variable** is a lowercase name standing for “any type at all”:

```haskell
length :: [a] -> Int
```

Read: “`length` takes a list of `a`, for any type `a`, and returns an `Int`.”

| Convention | Meaning |
|---|---|
| **Uppercase** name, e.g. `Int`, `Bool`, `Shape` | A concrete type |
| **Lowercase** name, e.g. `a`, `b`, `k`, `v` | A type variable — any type |

A function whose type contains a type variable is **polymorphic**, meaning “having many forms”. This particular kind is called **parametric** polymorphism, because the type is parameterised by a variable — the same code, the same single definition, works at every instantiation of that variable. (Chapter 9's second lesson introduces a different kind, where the *implementation itself* changes per type; keep the two apart.)

```haskell
head :: [a] -> a
fst  :: (a, b) -> a
map  :: (a -> b) -> [a] -> [b]
id   :: a -> a
```

Different letters mean the types **may** differ, not that they must. `map` may take `Int -> Int`, in which case `a` and `b` are both `Int`.

### Monomorphic versus polymorphic: the same idea, two signatures

A **monomorphic** signature names one concrete type and accepts only that type. Compare two functions that both return "the first thing":

```haskell
-- Monomorphic: locked to one concrete type.
firstChar :: String -> Char
firstChar (c:_) = c

-- Polymorphic: the same idea, for a list of anything.
headOf :: [a] -> a
headOf (x:_) = x
```

```text
ghci> firstChar "hello"
'h'
ghci> headOf "hello"
'h'
ghci> headOf [1,2,3]
1
ghci> firstChar [1,2,3]
<interactive>: error:
    * No instance for (Num Char) arising from the literal '1'
```

Both give `'h'` on a string — `String` **is** `[Char]`, so `headOf` covers everything `firstChar` covers. But `firstChar` rejects `[1,2,3]` outright: its signature says the argument must be `[Char]`, full stop, so GHC tries to force the numeral `1` to have type `Char`, which needs `Char` to be a `Num` instance, and it is not. `headOf` has no such restriction; it works on the list of `Integer` just as happily.

A monomorphic function is not "worse" — sometimes locking a type down is exactly right, for instance when a function's *whole job* is to be specific to `String`. But when nothing about the logic depends on which type the elements are, a type variable says so precisely, and buys the function every list type at once.

<Callout type="info" title="Reading a signature as a specification">
Before writing a function, ask what its signature permits. If you find yourself needing to compare two values of type `a`, the signature `[a] -> a` is not enough — you need a constraint, which the next lesson introduces.
</Callout>

## 2. What a polymorphic type promises — and forbids

Reading a signature tells you what a function can and cannot do.

```haskell
mystery :: [a] -> Int
```

Whatever `mystery` is, it **cannot look at the elements**. It knows nothing about type `a` — not whether it can be compared, added, or printed. All it can do is count, or otherwise reorder/select structurally without ever asking "what is this element". So it is `length`, or something equivalent to it.

That is the key insight, stated as a rule you can apply to any signature: **a function may only use the operations that its type variables are known to support, and an unconstrained type variable supports none.** The fewer constraints a type variable carries, the fewer things the function can possibly do. A very general type is, paradoxically, a very strong promise about what the function is *not* doing.

```haskell
id :: a -> a
```

There is exactly one function with this type that always terminates: it must return its argument unchanged. It cannot inspect it, transform it, or replace it with something else — there is nothing else of type `a` for it to produce, since `a` could be anything.

A second illustration makes the same point with two type variables instead of one:

```haskell
-- Take two values of possibly different types; keep the first.
pick :: a -> b -> a
pick x _ = x
```

`pick` must return something of type `a`. The only value of type `a` it has ever seen is `x`, so — reasoning exactly as with `id` — `pick x y = x` is the only sensible definition. It is not physically forced to ignore `y` (Haskell will not stop you writing something that never terminates, or that inspects `y` and then discards the result), but no terminating use of `y` can ever contribute to a result of type `a`, because nothing is known about `b`. This is exactly the Prelude's `const`.

```haskell
main :: IO ()
main = do
  print (pick "keep" True)
  print (pick 5 'z')
  print (pick True [1,2,3 :: Int])
```

```text
"keep"
5
True
```

Three calls, three completely unrelated pairs of types for `a` and `b`, and `pick` never had to know what any of them were.

## 3. Every argument of the same variable must agree

Within one signature, a type variable stands for **one** type throughout that application:

```haskell
pairUp :: a -> a -> (a, a)
pairUp x y = (x, y)
```

```text
ghci> pairUp 1 2
(1,2)
ghci> pairUp 'a' 'b'
('a','b')
ghci> pairUp 1 'a'
<interactive>: error:
    * No instance for (Num Char) ...
```

Both arguments are typed `a`, so they must be the same type in any given call. The rule scales to any number of arguments sharing one variable, not just two:

```haskell
tripleUp :: a -> a -> a -> (a, a, a)
tripleUp x y z = (x, y, z)
```

```text
ghci> tripleUp 1 2 3
(1,2,3)
ghci> tripleUp 'x' 'y' 'z'
('x','y','z')
ghci> tripleUp 1 2 'z'
<interactive>: error:
    * No instance for (Num Char) ...
```

Same failure, same reason: three uses of `a`, and the third call tries to make one of them `Char` while the others are numeric. To allow arguments to differ, use separate variables:

```haskell
pairUp2 :: a -> b -> (a, b)
```

## 4. The type inference rule

Chapter 2 said GHC infers types by collecting constraints. The formal rule for **function application** is:

> If `f` is a function mapping arguments of type `A` to results of type `B`, and `e` is an expression of type `A`, then the application `f e` has type `B`.

Written as the course notes do:

```text
f :: A -> B      e :: A
------------------------
       f e :: B
```

<Mermaid chart={`flowchart LR
  A["f :: A -> B"] --> C{"Does e have type A?"}
  E["e :: A?"] --> C
  C -->|"Yes"| D["f e :: B  — valid"]
  C -->|"No"| R["Type error — rejected before evaluation"]`} caption="Type-checking an application is exactly this one comparison: does the thing being supplied have the type the function demands as input?" />

Apply it to a concrete example. Given:

```haskell
pasd :: Bool
neg  :: Bool -> Bool
```

**Is `neg pasd` well typed?**

```text
neg :: Bool -> Bool      pasd :: Bool
-------------------------------------
         neg pasd :: Bool
```

The argument type matches the function's input type, so the application is valid and has type `Bool`.

**Is `neg 3` well typed?**

```text
neg :: Bool -> Bool      3 :: ??
--------------------------------
         neg 3 :: ???
```

`3` is numeric, not `Bool`. The types do not agree, so the application is invalid and is rejected before evaluation.

The rule composes when applications nest. Given `isEven :: Integer -> Bool` and `headOf :: [a] -> a` from earlier, is `isEven (headOf [2,4,6])` well typed?

```text
headOf :: [a] -> a applied to [2,4,6] :: [Integer]
  instantiates a := Integer, so headOf [2,4,6] :: Integer

isEven :: Integer -> Bool      headOf [2,4,6] :: Integer
----------------------------------------------------------
              isEven (headOf [2,4,6]) :: Bool
```

The inner application is checked, and — because it is polymorphic — instantiated first; only then is the outer application checked against the now-concrete result type.

## 5. Instantiating a polymorphic type

When a polymorphic function is applied, each type variable is fixed to a concrete type for that call — this fixing is called **instantiation**:

```haskell
length :: [a] -> Int
```

<Mermaid chart={`flowchart TD
  L["length :: [a] -> Int"] -->|"a := Integer"| C1["length [1,2,3]  =>  3"]
  L -->|"a := Char"| C2["length \"hello\"  =>  5"]
  L -->|"a := Bool"| C3["length [True,False]  =>  2"]`} caption="One signature, three unrelated instantiations. a is fixed separately and independently for each call — the calls never interact." />

```text
ghci> length [1,2,3]      -- a becomes Integer
3
ghci> length "hello"      -- a becomes Char
5
ghci> length [True,False] -- a becomes Bool
2
```

For `map`:

```text
ghci> :type map show
map show :: Show a => [a] -> [String]
```

`map :: (a -> b) -> [a] -> [b]` applied to `show :: Show a => a -> String` fixes `b` to `String`, leaving `a` general but now carrying `show`'s own constraint.

### Seeing it work: one signature, many element types

The clearest way to convince yourself "works for any type" is not abstract — it is running the *same, unmodified* function three times on three unrelated element types and reading the outputs back:

```haskell
main :: IO ()
main = do
  print (fst (1, "one"))
  print (fst ('a', True))
  print (head [10, 20, 30])
  print (head "polymorphism")
  print (head [False, True])
```

```text
1
'a'
10
'p'
False
```

`fst` never changed. `head` never changed. Only the concrete type filling in for each type variable changed, call by call.

The same point, now with a function written for this course rather than borrowed from the Prelude:

```haskell
-- Return the first two elements as a pair. Two equations: the
-- productive case, and the case with too few elements to answer.
firstTwo :: [a] -> (a, a)
firstTwo (x:y:_) = (x, y)

main :: IO ()
main = do
  print (firstTwo [1, 2, 3 :: Int])
  print (firstTwo "hello")
  print (firstTwo [True, False, True])
```

```text
(1,2)
('h','e')
(True,False)
```

`firstTwo` is one definition, written once, with no mention anywhere of `Int`, `Char`, or `Bool`. Each call instantiates `a` independently — to `Int`, then to `Char`, then to `Bool` — exactly as the diagram above shows for `length`.

## 6. Polymorphic data types

Type variables appear in data declarations too. Chapter 8's tree is one:

```haskell
data Tree a = Leaf a | Branch (Tree a) (Tree a)
```

`Tree` is not a type on its own — it is a **type constructor** that becomes a type once applied to one: `Tree Int`, `Tree String`, `Tree Bool`.

The same is true of the list type: `[]` alone is not a type, `[Int]` is. And of `Maybe`, which the fourth lesson covers.

```haskell
-- Works for a tree of anything.
countLeaves :: Tree a -> Int
countLeaves (Leaf _)     = 1
countLeaves (Branch l r) = countLeaves l + countLeaves r

-- Requires a tree of numbers specifically.
sumTree :: Num a => Tree a -> a
sumTree (Leaf n)     = n
sumTree (Branch l r) = sumTree l + sumTree r
```

`countLeaves` ignores the elements, so it needs no constraint. `sumTree` adds them, so it does — again, the next lesson.

A type constructor may take more than one type variable. `Tree` takes one; a type built to hold **two** independent things, of possibly different types, takes two:

```haskell
data Pair a b = MkPair a b
  deriving (Show)

firstOf :: Pair a b -> a
firstOf (MkPair x _) = x

swapPair :: Pair a b -> Pair b a
swapPair (MkPair x y) = MkPair y x
```

```haskell
main :: IO ()
main = do
  print (firstOf (MkPair 1 "one"))
  print (swapPair (MkPair 1 "one"))
  print (swapPair (MkPair 'z' True))
```

```text
1
MkPair "one" 1
MkPair True 'z'
```

`Pair` needs **two** concrete types before it is a type at all — `Pair Int String`, `Pair Char Bool` — exactly as `Tree` needed one. Neither `firstOf` nor `swapPair` cares what `a` and `b` actually are; they only rearrange the box, never open it to inspect what is inside.

## 7. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| `f :: [A] -> Int` | Type variables must be lowercase | `f :: [a] -> Int` |
| `pairUp 1 'a'` with `a -> a -> (a,a)` | One variable means one type per call | Use `a -> b -> (a, b)` |
| Writing `sumList :: [a] -> a` with `+` | `a` permits no arithmetic | Add the constraint `Num a =>` |
| `Tree` or `Pair` used with no type arguments | They are type constructors, not types | `Tree Int`, `Pair Int String` |
| Expecting `a` and `b` to be different | They may coincide | They only *may* differ |
| `firstTwo [1]` | Only one equation, and it needs two elements | Non-exhaustive at run time: `*** Exception: ...: Non-exhaustive patterns in function firstTwo` |
| `firstChar [1,2,3]` for `firstChar :: String -> Char` | The signature is monomorphic — locked to `[Char]` | Use a polymorphic signature like `headOf :: [a] -> a` if any list will do |
