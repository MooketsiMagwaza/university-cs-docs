This lesson is a reference. When GHC reports “No instance for (X)”, this table tells you what `X` wanted — what it provides, why that shape was chosen, when to reach for it, and what it does not guarantee.

## 1. `Eq` — equality

**What.** Provides `==` and `/=`.

```haskell
(==) :: Eq a => a -> a -> Bool
(/=) :: Eq a => a -> a -> Bool
```

**Why.** Membership testing, deduplication, counting occurrences, and "has anything changed" all reduce to one question — "are these the same value" — and `Eq` is the minimal class that answers it, with no ordering or arithmetic assumed on top.

**When.** Reach for `Eq` whenever a type has a sensible, decidable notion of sameness — almost every concrete type in this course. **Not** for function types: there is no general way to decide whether two functions compute the same thing (this would require solving the halting problem in general), so `(+) == (*)` is rejected outright, and functions have no `Eq` instance at all.

```haskell
data Result = Pass | Fail deriving (Eq, Show)

main :: IO ()
main = do
  print (3 == 3)
  print ("cs" /= "sc")
  print (Pass == Fail)
  print (0.1 + 0.2 == (0.3 :: Double))
```

```text
True
True
False
False
```

That last line is not a bug in the program or in Haskell — it is a property of `Double` (and of every language's IEEE-754 floating-point numbers). `0.1` and `0.2` cannot be represented exactly in binary, so `0.1 + 0.2` lands a hair away from the closest `Double` to `0.3`, and `==` reports the honest, bit-for-bit truth: they differ.

<CommonMistake title="Eq compiles for Double; that does not make == the right tool">
`Double` and `Float` are `Eq` instances, so `x == y` always type-checks. But after any arithmetic, rounding error means the "obviously equal" answer is often not bit-for-bit equal. Compare with a tolerance instead: `abs (x - y) < 0.0001`, not `x == y`.
</CommonMistake>

**Properties.** `Eq` guarantees that `==` and `/=` exist and type-check for the instance. It does **not** guarantee that `==` behaves like mathematical equality — reflexive (`x == x`), symmetric (`x == y` implies `y == x`), and consistent with every other function's treatment of the value. A *derived* `Eq` instance does behave this way, because it compares every constructor and every field structurally. A *hand-written* instance might not; Lesson 4 of this chapter writes one on purpose that deliberately treats unequal-looking values as equal, and discusses exactly what that costs you.

## 2. `Ord` — ordering

**What.** Provides `<`, `<=`, `>`, `>=`, `compare`, `max`, and `min`. Requires `Eq`.

```haskell
compare :: Ord a => a -> a -> Ordering
```

`Ordering` is an ordinary three-value type: `LT`, `EQ`, or `GT`.

```text
ghci> compare 3 5
LT
ghci> max 'a' 'z'
'z'
ghci> sort [3,1,2]
[1,2,3]
```

For a derived instance, values are ordered by the **sequence in which the constructors are declared**:

```haskell
data Result = Pass | Fail deriving (Show, Eq, Ord)
```

```text
ghci> Pass < Fail
True
```

Strings and lists compare **lexicographically** — element by element from the left:

```text
ghci> "apple" < "banana"
True
ghci> [1,2,3] < [1,3]
True
```

Tuples extend the same idea structurally rather than sequentially — compare the first components; only if those tie, look at the second:

```haskell
main :: IO ()
main = do
  print (compare (1, "b") (1, "a"))
  print (compare (1, "a") (2, "a"))
```

```text
GT
LT
```

`(1, "b")` and `(1, "a")` agree on the first component, so the comparison falls through to the second, where `"b" > "a"`. `(1, "a")` and `(2, "a")` disagree on the first component alone, so the second is never even inspected.

**When.** Use `Ord` whenever "which one comes first" matters, not just "are they the same" — sorting, finding a maximum or minimum, range checks. **Not** appropriate for a type with no natural order and no sensible one to invent (comparing two arbitrary `Shape`s by, say, memory address would be meaningless and misleading).

**Properties.** A derived `Ord` instance is a genuine total order — every pair of values compares as exactly one of `LT`, `EQ`, `GT`, consistently, and it agrees with the derived `Eq` (`compare x y == EQ` exactly when `x == y`). A *hand-written* `Ord` instance is not automatically consistent with a separately hand-written `Eq` — keeping the two in step is the programmer's job, not the compiler's; Lesson 4 revisits this.

## 3. `Show` and `Read` — text conversion

**What.** `Show` provides `show`, converting a value to a `String`. `Read` provides `read`, converting a `String` to a value.

```haskell
show :: Show a => a -> String
read :: Read a => String -> a
```

```text
ghci> show 42
"42"
ghci> read "42" :: Integer
42
ghci> read "42" :: Double
42.0
```

They are opposites, and `read` is the reason a type annotation is so often needed: the same text could produce several types, so `read` cannot tell which you meant without being told.

`print` is `Show` plus output:

```haskell
print :: Show a => a -> IO ()
```

**Why this shape.** Separating "convert to text" (`Show`) from "print that text" (`print`) means the text form is available for anything else you might want to do with it — write it to a file, compare it, embed it in a larger message — not only for immediate display.

**How they round-trip.** Deriving both on the same type gives you a genuine inverse pair: the text a derived `Show` produces is exactly the text a derived `Read` for the same type can parse back.

```haskell
data Student = Student { name :: String, mark :: Int }
  deriving (Show, Read, Eq)

main :: IO ()
main = do
  let k = Student { name = "Kago", mark = 72 }
  print k
  let parsed = read (show k) :: Student
  print (parsed == k)
```

```text
Student {name = "Kago", mark = 72}
True
```

`show k` produces the record's textual form; `read` parses that exact text back into a `Student`; and `Eq` (also derived) confirms the round trip lost nothing.

<Callout type="warn" title="read is partial">
`read "four" :: Integer` fails at run time with a parse error. This is the same partiality warned about in Chapter 3.
</Callout>

<RecognitionStrategy title="When does read need a type annotation?">
Ask whether the surrounding context already pins the result type down elsewhere. `read "42" + (1 :: Integer)` needs no annotation — the `+` forces the type. `print (read "42")` on its own does need one, because nothing else in the expression says which `Read` instance to use. When in doubt, add `:: Type` and let GHC confirm whether it was actually needed.
</RecognitionStrategy>

## 4. The numeric classes

Numbers form a small hierarchy, which is why `div` and `/` have different constraints.

<Mermaid chart={`flowchart TD
  Num --> Integral
  Num --> Fractional
  Fractional --> Floating`} caption="Integral and Fractional are separate, non-overlapping extensions of Num — no ordinary numeric type is both, which is exactly why div and / are never interchangeable. Floating extends Fractional further, adding sqrt, sin, pi and friends." />

| Class | Provides | Instances include |
|---|---|---|
| `Num` | `+`, `-`, `*`, `abs`, `negate`, `signum` | `Int`, `Integer`, `Float`, `Double` |
| `Integral` | `div`, `mod`, `quot`, `rem`, `toInteger` | `Int`, `Integer` |
| `Fractional` | `/`, `recip` | `Float`, `Double` |
| `Floating` | `sqrt`, `sin`, `cos`, `exp`, `log`, `pi` | `Float`, `Double` |

```text
ghci> :type div
div :: Integral a => a -> a -> a
ghci> :type (/)
(/) :: Fractional a => a -> a -> a
```

This is the mechanism behind the Chapter 2 rule that `div` is for whole numbers and `/` for fractional ones. `7 `div` 2` is `3`; `7 / 2` is `3.5`; and `7.5 `div` 2` is rejected because `Double` is not `Integral`.

### Converting between numeric types

Because the classes are separate, you sometimes need an explicit conversion:

| Function | Type | Use |
|---|---|---|
| `fromIntegral` | `(Integral a, Num b) => a -> b` | Whole number to any numeric type |
| `round` | `(RealFrac a, Integral b) => a -> b` | Nearest whole number |
| `floor` | `(RealFrac a, Integral b) => a -> b` | Greatest integer not greater than the value |
| `ceiling` | `(RealFrac a, Integral b) => a -> b` | Closest integer greater than or equal |
| `truncate` | `(RealFrac a, Integral b) => a -> b` | Discard the fractional part |

**In plain English:** each of these four signatures names *two* independent type variables, each with its own constraint — read exactly as [decoding a signature](/docs/sem3/csi243/decoding-questions) teaches: constraint(s) first, then the arrows. `round :: (RealFrac a, Integral b) => a -> b` says "for any fractional type `a` and any whole-number type `b`, take one value of the fractional type and give back the nearest value of the whole-number type." `fromIntegral` reads the same way in reverse — whole number in, any numeric type out.

```haskell
main :: IO ()
main = do
  print (map ceiling  [2.3, 2.5, -2.3 :: Double] :: [Integer])
  print (map floor    [2.3, 2.5, -2.3 :: Double] :: [Integer])
  print (map round    [2.2, 2.5, 2.7  :: Double] :: [Integer])
  print (map truncate [2.7, -2.7      :: Double] :: [Integer])
```

```text
[3,3,-2]
[2,2,-3]
[2,2,3]
[2,-2]
```

Look closely at `round 2.5`, which gives `2`, not `3`. Haskell's `round` breaks exact ties using **round-half-to-even** ("banker's rounding"): when a value sits precisely halfway between two integers, it rounds to whichever of the two is even. `2.5` rounds to `2`; `3.5` would round to `4`. `2.2` and `2.7` are nowhere near a tie, so they round the way you would expect.

The classic need for `fromIntegral` is an average:

```haskell
-- Rejected: length gives Int, but / needs Fractional.
-- average xs = sum xs / length xs

-- Correct.
average :: [Double] -> Double
average xs = sum xs / fromIntegral (length xs)
```

```text
ghci> average [1,2,3,4]
2.5
```

## 5. `Enum` and `Bounded`

**What.** `Enum` provides `succ`, `pred`, and range notation (`[x..y]`, `[x,y..z]`). `Bounded` provides `minBound` and `maxBound`.

**Why.** Both exist to give a type a notion of "next", "previous", or "extreme value" without requiring full arithmetic — useful for types like `Char` or an enumeration, which are not `Num` at all but still have an obvious sequence.

```haskell
main :: IO ()
main = do
  print ['a' .. 'f']
  print [10, 8 .. 0]
  print (minBound :: Int, maxBound :: Int)
```

```text
"abcdef"
[10,8,6,4,2,0]
(-9223372036854775808,9223372036854775807)
```

`['a'..'f']` and `[10,8..0]` both need only `Enum`; the `Int` bounds need only `Bounded`. `succ`, `pred`, and range syntax read the type's own declared or built-in ordering:

```text
ghci> succ 'a'
'b'
ghci> [Red ..]
[Red,Green,Yellow]
```

That last line requires `deriving (Show, Enum)` on the `TLights` type from Chapter 8.

**When.** Reach for `Enum` whenever you want "the next/previous value" or a range over a type with a natural, discrete sequence — including your own enumerations, once you derive it. Reach for `Bounded` when a type has a definite smallest and largest value to name.

**Properties.** `Bounded` is only meaningful for types with **finitely many values and a fixed minimum and maximum**. `Integer` has neither — it is arbitrary-precision and grows until memory is exhausted — so it has no `Bounded` instance and none could be written honestly. `Int` is fixed-width and does have both.

```text
ghci> maxBound :: Int
9223372036854775807
```

This is the concrete meaning of the Chapter 2 claim that `Int` is bounded and `Integer` is not.

## 6. Which class does an operation need?

<Mermaid chart={`flowchart TD
  Q["What do you want to do with values of type a?"] --> C1{"Compare for equality only?"}
  C1 -->|"Yes"| Eq1["Eq: ==, /="]
  C1 -->|"No"| C2{"Compare for order — sort, maximum, <?"}
  C2 -->|"Yes"| Ord1["Ord: <, compare, sort (implies Eq)"]
  C2 -->|"No"| C3{"Convert to or from text?"}
  C3 -->|"To text"| Show1["Show: show, print"]
  C3 -->|"From text"| Read1["Read: read"]
  C3 -->|"No"| C4{"Arithmetic?"}
  C4 -->|"Whole numbers, div, mod"| Integral1["Integral (needs Num)"]
  C4 -->|"Fractions, /"| Fractional1["Fractional (needs Num)"]
  C4 -->|"No"| C5{"Next/previous value, or a bound?"}
  C5 -->|"Ranges, succ, pred"| Enum1["Enum"]
  C5 -->|"minBound, maxBound"| Bounded1["Bounded"]`} caption="The lookup table below, redrawn as the sequence of questions it actually answers — ask what the operation does, not just what it is called, and the class falls out." />

The lookup table to memorise:

| You want to use | You need |
|---|---|
| `==`, `/=` | `Eq` |
| `<`, `>`, `compare`, `maximum`, `sort` | `Ord` |
| `show`, `print` | `Show` |
| `read` | `Read` |
| `+`, `-`, `*`, numeric literals | `Num` |
| `div`, `mod` | `Integral` |
| `/` | `Fractional` |
| `sqrt`, `pi` | `Floating` |
| `[a..b]`, `succ` | `Enum` |
| `minBound`, `maxBound` | `Bounded` |

## 7. Common errors

| Message | Cause | Repair |
|---|---|---|
| `No instance for (Fractional Int)` | `/` used on `Int` | Use `div`, or convert with `fromIntegral` |
| `No instance for (Integral Double)` | `div` used on `Double` | Use `/` |
| `Couldn't match Int with Double` in an average | `length` gives `Int` | `fromIntegral (length xs)` |
| `Ambiguous type variable` with `read` | The result type is undetermined | Annotate: `read s :: Integer` |
| `No instance for (Eq (a -> b))` | Comparing functions | Not possible; compare results instead |
| `[Red ..]` fails | The type has no `Enum` instance | Add `Enum` to the deriving clause |
| `0.1 + 0.2 == 0.3` is `False` | Binary floating-point rounding, not a bug | Compare with a tolerance: `abs (x - y) < epsilon` |
| `No instance for (Bounded Integer)` | `Integer` has no largest value to report | Use `Int` if a bound is genuinely needed |
