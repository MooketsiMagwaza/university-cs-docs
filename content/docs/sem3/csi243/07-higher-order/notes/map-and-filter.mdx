A **higher-order function** is a function that takes another function as an argument, or returns one as its result. You have already met one: `map`.

This lesson shows that `map` and `filter` are not new machinery. They are the two list recursions from Chapter 6, written once and given a name.

## 1. The shape you already know

Compare two functions from Chapter 6:

```haskell
doubleAll :: [Integer] -> [Integer]
doubleAll []     = []
doubleAll (x:xs) = (x * 2) : doubleAll xs

addTen :: [Integer] -> [Integer]
addTen []     = []
addTen (x:xs) = (x + 10) : addTen xs
```

They are identical except for one expression. Everything else — the base case, the cons, the recursive call — is repeated boilerplate.

`map` abstracts the difference into a parameter:

```haskell
map :: (a -> b) -> [a] -> [b]
map _ []     = []
map f (x:xs) = f x : map f xs
```

Read the signature carefully, argument by argument. `map` takes **a rule for turning one element into a result** — written `(a -> b)` — and **a list of `a`s**, and gives back **a list of `b`s**: the rule applied to every element, in order, one result per input. Plainly: "give me a function that knows what to do with one item, and a list of items, and I will hand back the list of results."

The first argument `(a -> b)` is **itself a function** — that is what makes `map` higher-order. Before watching it get passed to `map`, check that it really is an ordinary value with a type of its own, the same way a number or a string is:

```text
ghci> :type (*2)
(*2) :: Num a => a -> a
ghci> :type show
show :: Show a => a -> String
```

Neither line mentions a list anywhere. `(*2)` and `show` are complete functions on their own, fully formed before `map` ever sees them; `map`'s only job is to apply one of them to every element of a list.

```text
ghci> map (*2) [1,2,3]
[2,4,6]
ghci> map (+10) [1,2,3]
[11,12,13]
ghci> map show [1,2,3]
["1","2","3"]
ghci> map length ["hi", "there"]
[2,5]
```

`map` never changes the number of elements, and it may change the element type: `map show` turns `[Integer]` into `[String]`, which is exactly what `(a -> b)` permits.

Three more calls, each filling `map`'s function slot a different way:

```haskell
square :: Integer -> Integer
square n = n * n
```

```text
ghci> map square [1,2,3,4]
[1,4,9,16]
```

`square` is a function defined the ordinary way, with its own name and type signature, somewhere else in the program. `map` does not care where a function came from, only that it has type `a -> b` — a Prelude function like `show`, a section like `(*2)`, and a hand-written function like `square` all fit the same slot.

```text
ghci> map (\n -> n * n + 1) [1,2,3,4]
[2,5,10,17]
```

Here the rule is a lambda written directly inside the call, because "square it and add one" is needed nowhere else and does not deserve a name of its own — the same judgement call from Lesson 1, now applied to a function that is itself an argument.

```text
ghci> map (`div` 2) [10, 15, 21]
[5,7,10]
```

``(`div` 2)`` is a section: `div` turned into an operator with backticks, then given its right-hand side, so it halves each element and rounds down. A named function, a lambda, and a section — three different ways of writing "a rule from one element to a result" — all satisfy exactly the same `(a -> b)` slot in `map`'s type.

## 2. Tracing `map` by hand, and the laziness it makes possible

`map`'s recursive definition was already given above — repeated here because this section leans on it directly:

```haskell
map :: (a -> b) -> [a] -> [b]
map _ []     = []
map f (x:xs) = f x : map f xs
```

<StepByStep>
  <StepByStepTitle>Tracing map (*2) [3,4,5]</StepByStepTitle>

  <Step number={1}>
  <StepTitle>Unwind</StepTitle>
  `map (*2) [3,4,5]` matches the second equation: `(3*2) : map (*2) [4,5]`, i.e. `6 : map (*2) [4,5]`.
  </Step>

  <Step number={2}>
  <StepTitle>Keep unwinding</StepTitle>
  `map (*2) [4,5]` becomes `8 : map (*2) [5]`, and `map (*2) [5]` becomes `10 : map (*2) []`.
  </Step>

  <Step number={3}>
  <StepTitle>Base case</StepTitle>
  `map (*2) []` matches the first equation directly and returns `[]`. There is no list left to pattern-match, so the recursion stops here.
  </Step>

  <Step number={4}>
  <StepTitle>Rewind</StepTitle>
  Substituting back inward-out: `10 : []` is `[10]`; `8 : [10]` is `[8,10]`; `6 : [8,10]` is `[6,8,10]`.
  </Step>
</StepByStep>

Every step consumes exactly one element from the front of the list and produces exactly one element at the front of the result — which is exactly why `map` never changes a list's length.

### The subtle part: why `map` can work on a list that never ends

Now the genuinely tricky question: can `map` do anything useful with a list that has no end at all, such as `[1..]`? The unwind-then-rewind picture above seems to demand reaching the base case `[]` before anything can be "rewound." An infinite list never reaches `[]`, so on the face of it `map (*2) [1..]` looks like it should never produce anything at all.

It does produce something, and the reason is that Haskell does not actually evaluate by unwinding all the way down and then rewinding. That two-phase picture is a good way to *predict the final value* of a finite computation, but the real evaluation rule is narrower and more patient: **an expression is only evaluated as far as something else actually demands.** This is *laziness*, first previewed as thunks in [Currying and Sections](/docs/sem3/csi243/07-higher-order/notes/currying-and-sections).

Apply that rule to `map f (x:xs) = f x : map f xs`. The right-hand side is a `:` — a cons — whose two parts are `f x` and `map f xs`. Building a cons cell does **not** require either part to be evaluated first; `:` is perfectly happy to exist with both sides still unevaluated. So `map` can hand back the value `f x : map f xs` as soon as it has pattern-matched the *front* of the list into `x` and `xs` — it never needs to look past `xs` to do this, and in particular it never needs `xs` itself to be finite.

`[1..]` is built the same lazy way: it behaves as `1 : [2..]`, where `[2..]` is not pre-computed but sits as an unevaluated placeholder until something asks for more than the first element. Nothing about `[1..]` is infinite *in memory* at any one moment — only the *process* of asking for more of it never runs out.

`take` is written with exactly the same shape, and is the piece that actually decides how much of the infinite list gets forced:

```haskell
take :: Int -> [a] -> [a]
take 0 _      = []
take n (x:xs) = x : take (n - 1) xs
```

`take n xs` only pattern-matches `xs` far enough to get one `x` and one `xs`, exactly like `map` — and once `n` reaches `0`, it matches the wildcard `_` and stops without touching the list argument at all.

Put the two together and run this as a genuine, terminating program:

```haskell
main :: IO ()
main = do
  let firstFiveDoubled = take 5 (map (*2) [1..])
  print firstFiveDoubled
```

```text
[2,4,6,8,10]
```

Trace why this terminates, one demand at a time:

1. `print` needs the value of `take 5 (map (*2) [1..])`, so it forces evaluation to begin.
2. `take 5 (map (*2) [1..])` must pattern-match its second argument to choose between `take 0 _` and `take n (x:xs)`. Since `5` is not `0`, it needs `map (*2) [1..]` to look like `x : xs` for some `x` and `xs`.
3. To produce that shape, `map (*2) [1..]` needs `[1..]` to look like `x' : xs'`. `[1..]` obliges: `x' = 1`, `xs' = [2..]` (still unevaluated beyond its own front). `map` returns `(1*2) : map (*2) [2..]`, i.e. `2 : map (*2) [2..]`, without forcing `map (*2) [2..]` any further.
4. `take` now has its `x : xs`: `x = 2`, `xs = map (*2) [2..]`. It returns `2 : take 4 (map (*2) [2..])`.
5. Steps 2–4 repeat for `take 4`, `take 3`, `take 2`, `take 1`, producing `4`, `6`, `8`, `10` in turn from `[2..]`, `[3..]`, `[4..]`, `[5..]`.
6. `take 0 (map (*2) [6..])` matches the *first* equation, `take 0 _ = []`, immediately — `_` is a wildcard, so the list is not even inspected. The recursion stops here: the sixth element of `[1..]` is never generated, and `map` never does any work on it.

At no point does anything ask for "the whole list" — every stage only ever asks for one more element than it already has, and `take` is the one piece that eventually stops asking. That is the entire mechanism: `[1..]` never terminates on its own, but nothing in this program ever requires it to.

<Callout type="info" title="Confidence check on this trace">
This step-by-step account matches Haskell's standard (non-strict) evaluation semantics, which have not changed across GHC versions — `:`, `map`, and `take` are exactly as lazy in GHC 9.10.3 as in any other GHC release. The printed result `[2,4,6,8,10]` for `print (take 5 (map (*2) [1..]))` is exact and was hand-traced above, not guessed.
</Callout>

## 3. `filter`: the other shape

The second recursion shape from Chapter 6 kept some elements:

```haskell
positiveNumbers :: [Integer] -> [Integer]
positiveNumbers [] = []
positiveNumbers (x:xs)
  | x > 0     = x : positiveNumbers xs
  | otherwise = positiveNumbers xs
```

Abstracting the test gives `filter`:

```haskell
filter :: (a -> Bool) -> [a] -> [a]
filter _ [] = []
filter p (x:xs)
  | p x       = x : filter p xs
  | otherwise = filter p xs
```

Read the signature the same way as `map`'s: `filter` takes **a test that looks at one element and answers yes or no** — written `(a -> Bool)` — and **a list of `a`s**, and gives back **a list of `a`s**: exactly the elements the test said yes to, in their original order, with everything else discarded. Plainly: "give me a yes/no question about one item, and a list of items, and I will hand back only the items that answered yes."

The function argument returns `Bool`, which is why it is called a **predicate**. As with `map`, check that a predicate is an ordinary, complete value in its own right before it is ever handed to `filter`:

```text
ghci> :type even
even :: Integral a => a -> Bool
ghci> :type (>0)
(>0) :: (Num a, Ord a) => a -> Bool
```

Both lines type-check with no list in sight. `even` and `(>0)` are simply functions that happen to return `Bool`; `filter`'s whole job is to run one of them over every element and keep the ones that come back `True`.

```text
ghci> filter (>0) [-1,5,-3,8]
[5,8]
ghci> filter even [1..10]
[2,4,6,8,10]
ghci> filter (`elem` "aeiou") "functional"
"uioa"
```

`filter` never changes the element type, and the result is never longer than the input.

<CommonMistake title="Giving filter a transformer instead of a test">
`filter (*2) xs` is a type error for an ordinary numeric list, because `(*2) :: Num a => a -> a` returns a *number*, not a `Bool`. `filter`'s first argument must answer a yes/no question about one element; if the goal is to *change* each element rather than decide whether to keep it, that is `map`'s job, not `filter`'s. Seeing an arithmetic operator where `filter` expects a predicate is the fastest way to spot this mistake before GHC even reports it.
</CommonMistake>

Three more calls, each filling `filter`'s predicate slot a different way:

```haskell
isTeenager :: Int -> Bool
isTeenager age = age >= 13 && age <= 19
```

```text
ghci> filter isTeenager [8, 13, 19, 20, 45, 15]
[13,19,15]
```

`isTeenager` is a named, top-level predicate. Naming it is worthwhile here — unlike the short tests above — because it combines two comparisons, and the name documents what the combined rule means; that is the same "is it worth naming?" judgement from Lesson 1, and this time the answer is yes.

```text
ghci> filter (\w -> length w > 4) ["a", "cat", "house", "of", "cards"]
["house","cards"]
```

This predicate is a lambda that computes something about each element — its `length` — before comparing it, a shape no section could express: a section only fixes one side of a single operator, and cannot first call another function like `length` on the argument.

```text
ghci> filter (\n -> n `mod` 3 == 0) [1..20]
[3,6,9,12,15,18]
```

Another lambda, needed for the same reason: the test combines two operators (`` `mod` `` and `==`), so it is not a single-operator section either. Whenever a condition needs more than one step, reach for a lambda (or, if it is reused or deserves a name, a top-level function like `isTeenager` above).

<RecognitionStrategy title="How to recognise a predicate">
A predicate always has a return type of `Bool`. If you can imagine asking the test out loud as a yes/no question about a single element — "is it positive?", "is it a vowel?", "is this word longer than four letters?" — it belongs in `filter`. If the question is really "what should this become?", that is `map`'s job instead.
</RecognitionStrategy>

### `filter`'s result doesn't have to be printed — it can feed straight into another function

Every `filter` call so far has had its result shown directly. But `filter p xs` is an ordinary list value like any other, so it can be handed to any function that accepts one — most usefully, `length`, when the actual question is "**how many** elements pass the test," not "**which** elements pass it":

```haskell
-- Is this character a space?
isSpaceChar :: Char -> Bool
isSpaceChar c = c == ' '

-- Count the space characters in a string.
countSpaces :: String -> Int
countSpaces xs = length (filter isSpaceChar xs)
```

```haskell
main :: IO ()
main = do
  print (countSpaces "a b c d")
  print (countSpaces "hello")
  print (filter isSpaceChar "a b c d")
```
```text
3
0
"   "
```

Read `countSpaces` from the inside out, exactly as with any composed pair of function calls: `filter isSpaceChar xs` runs first, producing a *new, shorter string* containing only the space characters found — the third line above shows that intermediate value directly, three literal spaces. `length` then counts how many characters are in *that* string, which is exactly the count of spaces in the original. Nothing here is a new technique — it is `filter` (Section 3) composed with an ordinary Prelude function (`length`), the same composing-by-nesting idea from `putStrLn (show 42)` back in Chapter 3.

<Callout type="info" title="filter then length, not a special counting function">
Haskell has no separate "count how many elements satisfy a test" primitive — `length . filter p` (or, written the other way round, `length (filter p xs)`) **is** that operation, built from two pieces you already have. This is worth recognising by shape: any lab question phrased as "how many elements have property X" is `length (filter X xs)`, whatever `X` happens to be.
</Callout>

## 4. A worked example: grades, using `map` and `filter` as HOFs

Consider a class of eight students and their marks out of 100:

```haskell
marks :: [Int]
marks = [42, 88, 35, 67, 50, 91, 48, 73]
```

Two separate questions can be asked about this list: *who failed?* (a filtering question) and *what does everyone's mark become after a 7% curve?* (a mapping question). Answering both, side by side, makes the difference between `map`'s two arguments and `filter`'s two arguments impossible to blur.

### Filtering: who is below 50?

`filter`'s signature is `(a -> Bool) -> [a] -> [a]`. Its two arguments are not interchangeable, and confusing them is the single most common mistake with `filter`:

- **The first argument is the predicate** — the *rule*, not the data. `(< 50)` is a complete, meaningful yes/no test — "is this number below 50?" — before it has ever been shown a single mark. It gets applied to one mark at a time.
- **The second argument is the list** — the *data*, not the rule. `marks` supplies the eight numbers the predicate is actually run against, one after another, in order.

```haskell
failing :: [Int] -> [Int]
failing = filter (< 50)
```

Read `filter (< 50) marks` as: "take the rule `(< 50)` and the list `marks`, and hand back exactly the marks the rule said yes to." Nothing is added, changed, or reordered — a mark either survives unchanged, or is dropped entirely.

### Mapping: applying a 7% curve

This is a *separate* question from filtering — it does not chain onto the result above, and it starts again from the full, original `marks` list. `map`'s signature is `(a -> b) -> [a] -> [b]`, and again its two arguments play two distinct roles:

- **The first argument is the transformation** — the rule for turning *one* mark into *one new* mark. Here that rule is named `applyBonus`, rather than written inline, because "add a 7% bonus, as a whole number" is worth a name and might plausibly be reused elsewhere in a real gradebook.
- **The second argument is the list** — again the data, `marks`, supplied unchanged. Every element gets the rule applied to it; none are dropped, which is the exact opposite guarantee from `filter`.

```haskell
applyBonus :: Int -> Int
applyBonus mark = mark + (mark * 7) `div` 100

curved :: [Int] -> [Int]
curved = map applyBonus
```

``(mark * 7) `div` 100`` computes 7% of the mark, rounded down to a whole number, and adds it back on. Integer division keeps every result an exact, checkable whole number, with no floating-point rounding to second-guess.

### Running both, on the same data

```haskell
main :: IO ()
main = do
  putStrLn ("Raw marks:       " ++ show marks)

  let failingMarks = failing marks
  putStrLn ("Below 50 (fail): " ++ show failingMarks)

  let curvedMarks = curved marks
  putStrLn ("After 7% bonus:  " ++ show curvedMarks)
```

## 5. Rewriting Chapter 6 with them

Every filter from Lab 03 collapses to one line:

```haskell
largerY :: [Integer] -> Integer -> [Integer]
largerY xs y = filter (> y) xs

positiveNumbers :: [Integer] -> [Integer]
positiveNumbers = filter (> 0)

doubleAll :: [Integer] -> [Integer]
doubleAll = map (* 2)
```

Note the last two: with the list argument dropped from both sides, the definition says directly *what the function is* rather than what it does to an argument. That is legitimate precisely because of currying — `filter (> 0)` is already a complete `[Integer] -> [Integer]` function.

### A conditional transform, three ways: recursion, comprehension, `map`

`doubleAll` applies the *same* rule to every element. A function that applies a *different* rule depending on each element — "add 1 if it's even, add 2 if it's odd" — is still a `map`, because `map` never required the function passed to it to be simple; it only required there to be **one** function, of type `a -> b`, applied to every element:

```haskell
-- The per-element rule: even numbers get +1, odd numbers get +2.
add :: Int -> Int
add x
  | even x    = x + 1
  | otherwise = x + 2
```

**As a hand-written recursion** (the Chapter 6 shape):
```haskell
addAllRec :: [Int] -> [Int]
addAllRec []     = []
addAllRec (x:xs) = add x : addAllRec xs
```

**As a list comprehension:**
```haskell
addAllComp :: [Int] -> [Int]
addAllComp xs = [add x | x <- xs]
```

**As `map`:**
```haskell
addAllMap :: [Int] -> [Int]
addAllMap = map add
```

```haskell
main :: IO ()
main = do
  print (addAllRec  [1, 2, 3, 4])
  print (addAllComp [1, 2, 3, 4])
  print (addAllMap  [1, 2, 3, 4])
```
```text
[3,3,5,5]
[3,3,5,5]
[3,3,5,5]
```

Trace one element to see why all three agree: `1` is odd, so `add 1 = 1 + 2 = 3`. `2` is even, so `add 2 = 2 + 1 = 3`. `3` is odd, `add 3 = 3 + 2 = 5`. `4` is even, `add 4 = 4 + 1 = 5`. All three versions apply exactly this one rule, element by element, in the same order — a comprehension and `map` are not restricted to *simple* per-element functions; `add` itself can be as elaborate as it needs to be, with its own guards, and the comprehension or `map` calling it never changes.

## 7. Taking and dropping by a condition

`take` and `drop` from Chapter 6 work by count. Their higher-order cousins work by test:

```haskell
takeWhile :: (a -> Bool) -> [a] -> [a]
dropWhile :: (a -> Bool) -> [a] -> [a]
```

In words: `takeWhile` keeps grabbing elements from the front for as long as the predicate says yes, and **stops for good the moment it says no** — even if a later element would also have passed. `dropWhile` is the mirror image: it throws elements away from the front for as long as the predicate says yes, then keeps everything from the first no onward, unexamined.

`takeWhile` returns the longest prefix whose elements all satisfy the predicate, and **stops at the first failure**:

```text
ghci> takeWhile (<5) [1,2,3,7,1,2]
[1,2,3]
ghci> dropWhile (<5) [1,2,3,7,1,2]
[7,1,2]
```

Compare with `filter`, which examines the whole list:

```text
ghci> filter (<5) [1,2,3,7,1,2]
[1,2,3,1,2]
```

`takeWhile` stopped at `7` and never looked further; `filter` kept the trailing `1,2` as well. Confusing them is a common source of wrong answers.

The same stop-early behaviour shows up with a predicate on a different kind of data — here, string length instead of a number:

```text
ghci> takeWhile (\w -> length w <= 3) ["cat","dog","mouse","ox"]
["cat","dog"]
```

`"cat"` and `"dog"` both have length 3, so both pass. `"mouse"` has length 5 and fails, and `takeWhile` **stops there permanently** — it never even looks at `"ox"` (length 2), even though `"ox"` would have passed the test. That is exactly the property `filter (\w -> length w <= 3) [...]` would not have: `filter` would still include `"ox"`.

<RecognitionStrategy title="filter vs. takeWhile/dropWhile — how to tell which one you need">
Ask: does the task care about a *prefix* of the list, or about *every* element? "Keep going until the first number greater than 100" is a `takeWhile`/`dropWhile` question — the process is expected to stop at the first failure. "Keep every number greater than 100, wherever it occurs" is a `filter` question — the whole list must be scanned regardless of what came before. If elements after the first failure genuinely do not matter, `takeWhile` is enough; if they might still hold something you want, you need `filter`.
</RecognitionStrategy>

## 8. Combining two lists with `zipWith`

`zipWith` applies a two-argument function to corresponding elements of two lists:

```haskell
zipWith :: (a -> b -> c) -> [a] -> [b] -> [c]
```

In words: `zipWith` takes **a rule for combining one element from the first list with one element from the second list into a single result**, plus the two lists themselves, and walks both lists together, applying the rule pairwise — first with first, second with second, and so on.

```text
ghci> zipWith (+) [1,2,3] [10,20,30]
[11,22,33]
ghci> zipWith (*) [1,2,3] [4,5,6]
[4,10,18]
ghci> zipWith max [1,9,3] [5,2,8]
[5,9,8]
```

It stops when the shorter list runs out:

```text
ghci> zipWith (+) [1,2,3] [10,20]
[11,22]
```

The combining function does not have to keep both inputs' types, or even produce the same type as either of them — a lambda can mix an `Integer` and a `String` into one `String`:

```text
ghci> zipWith (\n s -> s ++ show n) [1,2,3] ["a","b","c"]
["a1","b2","c3"]
```

No operator section could express this: the rule needs to convert the number with `show` and then combine it with `++`, which is two operations on two different types — exactly the shape a lambda (or a small named function) is for.

The related `zip` pairs elements into tuples, and is just `zipWith` with the pairing function:

```text
ghci> zip [1,2,3] "abc"
[(1,'a'),(2,'b'),(3,'c')]
```

### Putting `zipWith` to work: turning the curved marks into report lines

The `curved` marks from the grades example earlier in this lesson pair naturally with the students they belong to:

```haskell
students :: [String]
students = ["Kago", "Naledi", "Thabo", "Lerato", "Mpho", "Boitumelo", "Sipho", "Refilwe"]

curved :: [Int]
curved = [44, 94, 37, 71, 53, 97, 51, 78]

report :: String -> Int -> String
report name mark = name ++ ": " ++ show mark

main :: IO ()
main = do
  putStrLn "Student reports:"
  mapM_ putStrLn (zipWith report students curved)
```

```text
Student reports:
Kago: 44
Naledi: 94
Thabo: 37
Lerato: 71
Mpho: 53

```

`zipWith report students curved` walks the two lists together — `report`'s first argument comes from `students`, its second from `curved`, paired up positionally — producing one `String` per pair. `mapM_ putStrLn` then performs the output action for each of those strings in turn. This is the chapter's first use of an `IO` action itself being built by a higher-order function (`mapM_`) rather than by a `do` block listing each `putStrLn` by hand; it is a brief, self-contained preview, and Chapter 9 covers `mapM_` and its relatives properly.

## 9. Functions as values

The idea underneath all of this is that **functions are first-class values**. A first-class value can be passed to a function, returned from a function, or stored in a data structure — with no restriction on its use.

```text
ghci> let operations = [(*2), (+10), (subtract 1)]
ghci> map (\f -> f 5) operations
[10,15,4]
```

A list of functions, each applied to `5`. Nothing special is required to make that work; functions are values like any other.

## 10. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| `map (*2) 5` | The second argument must be a list | `map (*2) [5]` |
| `map *2 [1,2]` | A bare operator is not an expression | `map (*2) [1,2]` |
| `filter (*2) xs` | `filter` needs a predicate returning `Bool` | `filter even xs` |
| `takeWhile` used where `filter` was meant | It stops at the first failure | Use `filter` to scan the whole list |
| `map` expected to shorten the list | `map` preserves length | Use `filter` to remove elements |
| `zipWith (+) [1,2,3] [1,2]` giving 3 results | It stops at the shorter list | Check the lengths first |
