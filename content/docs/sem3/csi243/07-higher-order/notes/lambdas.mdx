A **lambda expression** is an alternative to defining a function using equations. It comprises a pattern for each of the arguments and a body specifying how the result is computed from them.

Because it has no name, it is an **anonymous function definition**.

## 1. The notation

Mathematical lambda notation writes `λx ● x + x`. Haskell writes the same thing with a backslash, which is meant to resemble a λ:

```haskell
\x -> x + x
```

Read aloud: “lambda `x`, arrow, `x` plus `x`” — or “the function that takes `x` and returns `x + x`.”

| Part | Meaning |
|---|---|
| `\` | Begins a lambda; stands for λ |
| `x` | A pattern for the argument |
| `->` | Separates the arguments from the body |
| `x + x` | The body, computing the result |

Several arguments are listed before the arrow:

```haskell
\x y -> x + y
```

## 2. Applying a lambda directly

A nameless function can be used exactly like a named one. Because a lambda is an expression, applying it needs parentheses:

```text
ghci> (\x -> x + x) 3
6
ghci> (\x y -> x + y) 8 6
14
```

Without the parentheses, Haskell would read `\x -> x + x 3` as a lambda whose body is `x + (x 3)`, which tries to apply `x` as a function.

<Callout type="warn" title="Always parenthesise a lambda you are applying">
The lambda body extends as far to the right as it can. `(\x -> x + 1) 5` gives `6`; `\x -> x + 1 5` is a type error.
</Callout>

## 3. Lambdas are ordinary values

A lambda has a type like any other function, and can be bound to a name:

```text
ghci> :type (\x -> x + x)
(\x -> x + x) :: Num a => a -> a
ghci> let double = \x -> x + x
ghci> double 7
14
```

That last binding shows something important. These two definitions mean the same thing:

```haskell
double x = x + x
double   = \x -> x + x
```

The equation form is shorthand for the lambda form. Every function definition you have written since Chapter 3 has been a lambda underneath.

## 4. Why they exist: avoiding a needless name

A lambda is useful when a function is referenced only once and naming it adds nothing.

Consider a function returning the first `n` odd integers. Written with a local helper:

```haskell
-- Return the first n odd integers.
odds :: Int -> [Int]
odds n = map f [0 .. n - 1]
  where
    f x = x * 2 + 1
```

The helper `f` exists solely to be handed to `map`. Naming it forces the reader to look elsewhere for a one-line rule. A lambda puts the rule where it is used:

```haskell
odds :: Int -> [Int]
odds n = map (\x -> (x * 2) + 1) [0 .. n - 1]
```

```text
ghci> odds 5
[1,3,5,7,9]
```

As a full program, run on two different sizes rather than just one, to see that it is `n` — not the printed example — that is doing the work:

```haskell
main :: IO ()
main = do
  print (odds 5)
  print (odds 8)
```

```text
[1,3,5,7,9]
[1,3,5,7,9,11,13,15]
```

The same pattern applies to `filter`. Keeping only the words longer than three characters needs a one-line test, so a lambda is written right where `filter` needs it, instead of naming a `isLongWord` helper that is used nowhere else:

```haskell
-- Keep only the words with more than three characters.
longWords :: [String] -> [String]
longWords ws = filter (\w -> length w > 3) ws
```

```text
ghci> longWords ["a", "cat", "house", "of", "cards"]
["house","cards"]
```

`"a"` (length 1), `"cat"` (length 3), and `"of"` (length 2) all fail the test `length w > 3`; `"house"` (5) and `"cards"` (5) pass it. The lambda `\w -> length w > 3` is a complete, self-contained rule, so giving it a separate name would only add a layer of indirection between the reader and what the rule actually checks.

Run it on a second, unrelated list of words to confirm the rule, not the specific words above, is what decides the result:

```haskell
main :: IO ()
main = do
  print (longWords ["a", "cat", "house", "of", "cards"])
  print (longWords ["Haskell", "is", "fun", "to", "learn"])
```

```text
["house","cards"]
["Haskell","learn"]
```

In the second list, `"is"` (2), `"fun"` (3), and `"to"` (2) all fail `length w > 3`; only `"Haskell"` (7) and `"learn"` (5) pass.

<Callout type="info" title="A name is not always worse">
If the rule is complicated, or is used more than once, or genuinely deserves explanation, a named `where` helper is clearer. Prefer a lambda only when the rule is short and used once. Clarity comes before cleverness.
</Callout>

## 5. Functions that return functions

Lambdas also matter when a function returns a function by its nature. The Prelude's `const` returns a constant function that always produces a given value:

```haskell
const :: a -> b -> a
const x = \_ -> x
```

Read this as: `const x` produces *a function* which ignores its argument and returns `x`.

```text
ghci> let always5 = const 5
ghci> always5 "anything"
5
ghci> always5 99
5
```

The wildcard in `\_ -> x` says the returned function's argument is deliberately discarded.

`const` is one extreme: the returned function ignores its argument completely. A function that *uses* the argument it is given, while still remembering an earlier one, is just as common:

```haskell
makeAdder :: Integer -> (Integer -> Integer)
makeAdder n = \x -> x + n
```

Read this as: `makeAdder n` produces a function that adds `n` to whatever it is later given. Unlike `const`, the returned lambda's body actually mentions its argument `x`.

```text
ghci> let addFive = makeAdder 5
ghci> addFive 10
15
ghci> (makeAdder 100) 1
101
```

`addFive` **remembers** `n = 5` — that captured value is what makes it different from `always5`, which remembers a value but never looks at what it is given at all.

**This is the same nesting rule from Chapter 3, spelled with `\` and `->` instead of `let` and `in`.** [Input, Bindings, and Processing](/docs/sem3/csi243/03-defining-functions/notes/input-processing) showed that each `let` inside a `do` block opens a new, deeper level of nesting: a name introduced at one level is visible to code written inside it, and never to code outside or before it. A lambda's parameter follows exactly that rule. In `makeAdder n = \x -> x + n`, the argument `n` is bound once, when `makeAdder` is applied; the lambda `\x -> x + n` is then a new, deeper scope nested *inside* that binding, where `n` is visible to be read but not to be rewritten. And because Haskell bindings are immutable — the rule [Functional Thinking](/docs/sem3/csi243/01-functional-thinking/notes/functional-thinking) established for `taxRate` back in Chapter 1 — `n` cannot change between one call of the returned function and the next. `makeAdder 5` and `makeAdder 100` each capture their own fixed `n`, permanently, inside their own separate lambda:

```haskell
main :: IO ()
main = do
  let addFive    = makeAdder 5
  let addHundred = makeAdder 100
  print (addFive 10)
  print (addHundred 10)
  print (addFive 10)
```

```text
15
110
15
```

The third line proves the point: creating `addHundred` and using it does nothing to `addFive`'s captured `n`. `addFive 10` gives `15` both times, for the same reason `taxRate` kept meaning `0.14` after `discountedRate` was defined from it, and `number` kept meaning `4` after `doubled` was computed from it — a binding is read, never rewritten.

## 6. Lambdas make currying precise

A lambda can be used to formalise the meaning of a curried function definition:

```haskell
add x y = x + y
```

means

```haskell
add = \x -> (\y -> x + y)
```

This makes precise that `add` is a function taking a number `x` and returning a **function**, which in turn takes a number `y` and returns `x + y`.

That is not a curiosity — it is how every multi-argument Haskell function actually works, and the next lesson builds on it directly.

## 7. Patterns in lambdas

The argument of a lambda is a pattern, so tuple patterns work:

```text
ghci> (\(x, y) -> x * y) (3, 4)
12
ghci> map (\(name, mark) -> name) [("Kago", 72), ("Naledi", 68)]
["Kago","Naledi"]
```

A lambda cannot have multiple equations or guards, however. When you need those, use a named function or a `case` inside the lambda body.

## 8. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| `\x -> x + 1 5` | The body extends rightwards, so `1 5` is an application | `(\x -> x + 1) 5` |
| `\x = x + 1` | A lambda uses `->`, not `=` | `\x -> x + 1` |
| `lambda x -> x` | The keyword is a backslash | `\x -> x` |
| `\x -> x \| x > 0 = 1` | Lambdas cannot carry guards | Use a named function, or `case` |
| `map \x -> x * 2 xs` | The lambda argument needs parentheses | `map (\x -> x * 2) xs` |
