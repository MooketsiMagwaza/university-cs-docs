`map` and `filter` both return lists. The third recursion shape from Chapter 6 returned a **single value**:

```haskell
sum' []     = 0
sum' (x:xs) = x + sum' xs

product' []     = 1
product' (x:xs) = x * product' xs
```

Again these differ in only two places: the base value, and the operator. Abstracting both gives a **fold**.

## 1. `foldr`

```haskell
foldr :: (a -> b -> b) -> b -> [a] -> b
foldr _ acc []     = acc
foldr f acc (x:xs) = f x (foldr f acc xs)
```

Three arguments: a combining function, a starting value, and the list. In words: `foldr` takes **a rule for combining one element with an already-folded result** — written `(a -> b -> b)` — **a starting value** to use once the list runs out, and **a list**, and collapses the whole list to one value by combining from the right-hand end inward.

Before it is handed to `foldr`, the combining function is an ordinary two-argument value, exactly like any other:

```text
ghci> :type (+)
(+) :: Num a => a -> a -> a
```

`(+) :: Num a => a -> a -> a` matches the shape `(a -> b -> b)` once both type variables are instantiated to the same numeric type — which is also why the starting value and the list elements have to agree in type.

```text
ghci> foldr (+) 0 [1,2,3,4]
10
ghci> foldr (*) 1 [1,2,3,4]
24
ghci> foldr max 0 [3,9,2]
9
```

A combining function does not have to be an arithmetic operator. Supplying `(:)` itself — the list constructor — with `[]` as the starting value reconstructs the original list unchanged:

```text
ghci> foldr (:) [] [1,2,3]
[1,2,3]
```

This is not a curiosity — it is exactly what the substitution picture below says `foldr` always does: replace every `:` with the combining function and the final `[]` with the starting value. Choosing `(:)` and `[]` makes that substitution a no-op, which is why the list reappears unchanged. This identity also matters later in this lesson, when `foldr` on an infinite list is compared with `foldl`.

The `r` means **right**: the combining starts from the right-hand end. `foldr f acc` replaces every `:` with `f` and the final `[]` with `acc`:

```text
     1 : (2 : (3 : (4 : [])))
=>   1 + (2 + (3 + (4 + 0)))
=    10
```

That substitution picture is the fastest way to predict what a `foldr` does.

## 2. Defining Prelude functions as folds

Most of Chapter 6's single-value functions are one-liners once you have `foldr`:

```haskell
sum'     = foldr (+) 0
product' = foldr (*) 1
and'     = foldr (&&) True     -- True when every element is True
or'      = foldr (||) False    -- True when any element is True
length'  = foldr (\_ n -> n + 1) 0
maximum' = foldr max minBound
```

`and = foldr (&&) True` is the definition from the course notes. Note that `(&&)` must be parenthesised, because a bare operator is not a valid expression — the reason sections exist.

Even `map` and `filter` are folds:

```haskell
map' f     = foldr (\x acc -> f x : acc) []
filter' p  = foldr (\x acc -> if p x then x : acc else acc) []
```

You would not normally write them this way, but it shows that `foldr` is the general shape of list recursion, with `map` and `filter` as special cases.

## 3. `foldl`

`foldl` combines from the **left** instead:

```haskell
foldl :: (b -> a -> b) -> b -> [a] -> b
```

```text
     1 : (2 : (3 : []))
=>   ((0 + 1) + 2) + 3
```

For `+` the answer is the same, because addition is associative. For a non-associative operator it is not:

```text
ghci> foldr (-) 0 [1,2,3]
2
ghci> foldl (-) 0 [1,2,3]
-6
```

Because `foldr` gives `1 - (2 - (3 - 0))` = `1 - (2 - 3)` = `1 - (-1)` = `2`, while `foldl` gives `((0 - 1) - 2) - 3` = `-6`.

Run both, on two genuinely different lists, to see the gap in practice rather than only on paper:

```haskell
main :: IO ()
main = do
  print (foldr (-) 0 [1,2,3])
  print (foldl (-) 0 [1,2,3])
  print (foldr (-) 0 [10,2,8,1])
  print (foldl (-) 0 [10,2,8,1])
```

```text
2
-6
15
-21
```

The third line, traced by the same substitution rule: `10 : (2 : (8 : (1 : [])))` becomes `10 - (2 - (8 - (1 - 0)))`. Working from the innermost pair outward: `1 - 0 = 1`, then `8 - 1 = 7`, then `2 - 7 = -5`, then `10 - (-5) = 15`. The fourth line nests the other way: `((0 - 10) - 2) - 8) - 1` is `-10`, then `-12`, then `-20`, then `-21`. Same four numbers, same operator, two different answers — exactly the associativity gap the previous section named, now shown on data that was not already worked out on paper above.

<Callout type="warn" title="Check associativity before choosing">
For `+`, `*`, `max`, `&&`, and `||` the two folds agree. For `-`, `/`, `++`, and anything order-sensitive they do not. When in doubt, write out the substitution picture.
</Callout>

### Beyond associativity: why `foldr` can handle an infinite list and `foldl` cannot

Associativity is not the only difference between the two folds. They also differ in **when** they do their work, and that difference has a consequence associativity alone does not explain.

`foldl` must walk all the way to the end of the list before it can produce anything at all: at each step it builds a larger, still-unevaluated combination — `((0 + 1) + 2) + 3` is a chain of deferred computations (the same *thunks* introduced in [Currying and Sections](/docs/sem3/csi243/07-higher-order/notes/currying-and-sections)) that only starts to reduce once the entire list has been consumed and the final thunk is forced. `foldr`, by contrast, can hand back part of its result as soon as it has looked at the very first element, because `f x (foldr f acc xs)` only needs `foldr f acc xs` to be evaluated as far as `f` actually demands it — and for a combining function like `(:)`, that is "not very far at all."

This lets `foldr` do something `foldl` fundamentally cannot: work on an infinite list, provided the combining function does not insist on seeing the whole thing.

```text
ghci> take 3 (foldr (:) [] [1..])
[1,2,3]
```

`foldr (:) [] [1..]` is the identity fold from earlier, now run on the infinite list `[1..]`. `(:)` can produce its first result — `1 : (foldr (:) [] [2..])` — without forcing the rest of that expression, so `take 3` only ever forces exactly the three cons cells it needs, and the computation finishes. The equivalent `foldl` has no such option:

```haskell
take 3 (foldl (\acc x -> x : acc) [] [1..])
-- never finishes: foldl must walk the entire (infinite) list to build its
-- final accumulator before it can return anything at all, so take 3 never
-- even gets a first element to inspect.
```

Because `foldl` cannot produce even its first piece of output until the whole list has been consumed, handing it an infinite list simply means it never returns — no error, no partial answer, just a computation that runs forever.

<RecognitionStrategy title="foldr or foldl — how to choose">
Default to `foldr`: it agrees with `foldl` whenever the combining operator is associative, and it is the only one of the two that can short-circuit or work on an infinite list. Reach for `foldl` only when the combination is naturally left-to-right and the list is known to be finite — and even then, real code typically prefers `foldl`'s stricter cousin `foldl'` from `Data.List` for performance, a detail covered where the course discusses evaluation cost.
</RecognitionStrategy>

This is a direct consequence of the same evaluation model previewed in [Currying and Sections](/docs/sem3/csi243/07-higher-order/notes/currying-and-sections) and covered in full in [The Cost of a Definition](/docs/sem3/csi243/10-reasoning-revision/notes/complexity) in Chapter 10 — this section is only the specific payoff for choosing between `foldr` and `foldl`; the general theory of laziness lives there.

There is also `foldr1` and `foldl1`, which use the list's first element as the starting value and therefore fail on an empty list:

```text
ghci> foldr1 max [3,9,2]
9
ghci> foldr1 max []
*** Exception: foldr1: empty structure
```

## 4. Scans

A **scan** is a fold that keeps every intermediate result rather than only the last:

```text
ghci> scanl (+) 0 [1,2,3,4]
[0,1,3,6,10]
ghci> foldl (+) 0 [1,2,3,4]
10
```

The final element of a `scanl` is exactly what the corresponding `foldl` returns. Scans are useful for running totals — the kind of thing a real program would print one line at a time, not just inspect as a finished list:

```haskell
dailyExpenses :: [Integer]
dailyExpenses = [120, 45, 78, 200, 15]

main :: IO ()
main = do
  let runningTotal = scanl (+) 0 dailyExpenses
  putStrLn ("Daily expenses: " ++ show dailyExpenses)
  putStrLn ("Running total:  " ++ show runningTotal)
  putStrLn ("Final total:    " ++ show (foldl (+) 0 dailyExpenses))
```

```text
Daily expenses: [120,45,78,200,15]
Running total:  [0,120,165,243,443,458]
Final total:    458
```

`runningTotal` has one more element than `dailyExpenses` — the leading `0` is the starting value, present before any expense has been added — and its last element, `458`, is exactly `foldl (+) 0 dailyExpenses`, matching the rule stated above on different numbers than the `[1,2,3,4]` example.

## 5. Function composition

Composition connects the output of one function to the input of another. Chapter 1 introduced the idea informally; here is the operator.

Mathematically, composition takes two functions `f` and `g` and produces `h = f ∘ g` such that `h(x) = f(g(x))`. In Haskell the operator is a full stop:

```haskell
(.) :: (b -> c) -> (a -> b) -> a -> c
(f . g) x = f (g x)
```

**Read `f . g` from right to left**: first apply `g`, then apply `f`. The types must be compatible — the result of `g` must be acceptable to `f`.

```text
ghci> ((*2) . (+1)) 5
12
ghci> ((+1) . (*2)) 5
11
```

The first adds 1 to get 6, then doubles it. The second doubles to get 10, then adds 1. Order matters.

### Building pipelines

Composition shines when several transformations are chained:

```haskell
-- Sum the squares of the odd numbers in a list.
sumOddSquares :: [Integer] -> Integer
sumOddSquares = sum . map (^2) . filter odd
```

```text
ghci> sumOddSquares [1..10]
165
```

Read right to left: keep the odds, square them, add them up. The list argument is never mentioned, because each stage is already a complete function.

The same pipeline, run as a program on two lists that share no numbers at all, to confirm the pipeline itself — not a coincidence about `[1..10]` — is doing the work:

```haskell
main :: IO ()
main = do
  print (sumOddSquares [1..10])
  print (sumOddSquares [2, 3, 5, 7, 11, 13])
```

```text
165
373
```

For `[2,3,5,7,11,13]`: `filter odd` drops the `2`, leaving `[3,5,7,11,13]`; `map (^2)` gives `[9,25,49,121,169]`; `sum` adds them: `9+25=34`, `34+49=83`, `83+121=204`, `204+169=373`. The pipeline's *shape* never changed between the two calls — only the numbers flowing through it did.

The explicit version says the same thing:

```haskell
sumOddSquares xs = sum (map (^2) (filter odd xs))
```

<Callout type="info" title="Clarity before cleverness">
Point-free style — omitting the argument — is not automatically better. Use composition when it makes a pipeline read clearly, and the explicit version whenever the composed form becomes hard to follow. A readable named function beats a dense chain of operators.
</Callout>

## 6. The `$` operator

A companion to composition, `$` applies a function to an argument with the lowest possible precedence:

```haskell
($) :: (a -> b) -> a -> b
f $ x = f x
```

Its only purpose is to remove nested parentheses:

```text
ghci> sum (map (^2) (filter odd [1..10]))
165
ghci> sum $ map (^2) $ filter odd [1..10]
165
```

Both are correct. Use whichever your reader will find clearer.

## 7. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| `foldr (+) [1,2,3]` | The starting value is missing | `foldr (+) 0 [1,2,3]` |
| `foldr (-) 0 xs` expected to equal `foldl` | `-` is not associative | Choose the fold that matches the specification |
| `foldr1 max []` | `foldr1` has no starting value | Use `foldr max` with an explicit base |
| `foldr && True xs` | A bare operator is not an expression | `foldr (&&) True xs` |
| `(f . g) x` expected to apply `f` first | Composition applies right to left | Swap them, or use `g . f` |
| `sum . map (^2) $ xs` misread | `$` has the lowest precedence | Add parentheses if unsure |
