Functional programming is not “ordinary programming with strange syntax.” It changes how we describe a solution. Instead of listing commands that repeatedly alter program state, we define values and transformations between values.

## The central idea

A mathematical function maps an input to an output. If the function is pure, the same input always produces the same output and evaluating it does not secretly change the outside world.

```haskell
-- A pure function: the result depends only on radius.
circleArea :: Double -> Double
circleArea radius = pi * radius * radius
```

Calling `circleArea 2` produces the same result wherever it appears. It does not modify `radius`, print a message, change a file, or read the clock.

The same idea holds for any pure function, regardless of what it calculates:

```haskell
-- A pure function: the result depends only on the two side lengths.
rectangleArea :: Double -> Double -> Double
rectangleArea width height = width * height

-- A pure function: the result depends only on the score supplied.
isPassingGrade :: Integer -> Bool
isPassingGrade score = score >= 50
```

```text
ghci> circleArea 2
12.566370614359172
ghci> rectangleArea 4.0 5.0
20.0
ghci> isPassingGrade 42
False
ghci> isPassingGrade 73
True
```

Three different result types — `Double`, `Double`, `Bool` — but the same guarantee each time: call any of them twice with the same arguments, and Haskell has no mechanism by which the second call could disagree with the first.

## What, why, when, and how

| Question | Answer |
|---|---|
| **What?** | A style of programming built around expressions, functions, immutable values, and composition |
| **Why?** | It makes individual computations easier to test, reuse, combine, and reason about |
| **When?** | Data transformations, validation, parsers, compilers, calculations, concurrent systems, and any problem that benefits from predictable components |
| **When not alone?** | Real applications still need input, output, storage, time, randomness, and networking; Haskell represents these effects explicitly rather than pretending they do not exist |
| **How?** | Define small transformations, give them types, combine them, and keep effects at a controlled boundary |

### What makes a language “functional”?

There is no single switch that turns a language into a functional language. The label describes which ideas the language makes natural, safe, and central:

| Functional-language idea | What it means in practice | What it does **not** mean |
|---|---|---|
| Functions are values | A function can be stored in a name, passed to another function, or returned as a result | Functions are not limited to top-level procedures that can only be called by name |
| Expressions produce values | `if`, function calls, and arithmetic fit together because each has a result | The program is not merely a list of commands executed for their side effects |
| Immutable bindings | A name keeps one meaning within the scope that introduced it | The program can never process changing real-world information |
| Pure functions | A calculation can depend only on its explicit inputs and return a result without hidden effects | Every line of a real application must be pure, or input/output is forbidden |
| Composition | Small transformations can be connected to make a larger transformation | “Functional” does not mean squeezing everything into one unreadable expression |
| Explicit effects | Types such as `IO String` make interaction visible in the program's structure | Effects disappear; they are represented and controlled instead |

Haskell strongly favours all six ideas. A multi-paradigm language such as JavaScript, Python, or Java can still be written in a functional *style* for part of a program, but those languages also permit changing variables and hidden effects much more freely. The important question is therefore not “does this language have functions?” Almost every modern language does. Ask instead: **does the solution describe stable values and transformations, and are effects visible at the boundary?**

Functional programming is also not synonymous with recursion, `map`, short code, or advanced mathematics. Those are tools or associations. A clear pipeline of named, pure transformations is functional even when it is several readable lines long; an opaque one-liner that reads global state is not made functional merely by calling `map`.

## Expression versus statement

An expression has a value. For example:

```haskell
2 + 3
if score >= 50 then "Pass" else "Fail"
```

Both produce values. That is why Haskell's `if` requires an `else`: the entire expression must have a result whichever branch is chosen.

An imperative statement commonly tells the machine to perform an action such as updating a variable. Haskell can perform actions, but pure calculations remain separate from them.

## Functional and imperative comparison

Consider doubling every number in a list.

### Imperative description

```text
create an empty result
for every number in the input
  calculate number * 2
  append it to the result
return the result
```

This explains the sequence of state changes.

### Functional description

```haskell
-- Apply the doubling function independently to every element.
doubleAll :: [Integer] -> [Integer]
doubleAll numbers = map double numbers
  where
    double number = number * 2
```

Test:

```text
ghci> doubleAll [1, 2, 3, 4]
[2,4,6,8]
```

Line by line:

1. `[Integer] -> [Integer]` says the function transforms a list of integers into another list of integers.
2. `map` captures the reusable pattern “apply one function to every element.” You have not written `map` from scratch yet — that comes in Chapter 7 — but here it means exactly what its name suggests: apply `double` to every element of `numbers` and collect the results in a new list, in the same order.
3. `double` states only the element-level rule.
4. No loop counter or changing result variable is required.

## Immutability

Binding a name does not create a box whose contents are repeatedly replaced.

```haskell
taxRate :: Double
taxRate = 0.14
```

Within the same scope, `taxRate` means `0.14`. A second equation attempting to make it a different constant is not an assignment in the imperative sense.

Why this matters:

- reading `taxRate` cannot secretly return a different value later;
- functions can be evaluated independently when their inputs are known;
- tests do not depend on hidden mutation;
- concurrent computations share fewer changing objects.

### The same rule, two more times

```haskell
-- A different constant, same immutable shape.
maxAttempts :: Integer
maxAttempts = 3

-- A binding built from another binding — still fixed once, not reassigned.
discountedRate :: Double
discountedRate = taxRate - 0.02
```

`discountedRate` is not "taxRate that got changed." It is a separate, independent name whose definition happens to mention `taxRate`. Evaluating `discountedRate` never touches or modifies `taxRate` — it just reads the fixed value `0.14` while computing its own fixed value:

```text
ghci> taxRate
0.14
ghci> discountedRate
0.12
ghci> taxRate
0.14
```

Reading `taxRate` a second time, after `discountedRate` has already used it, gives the same `0.14` as before. Nothing about defining `discountedRate` in terms of `taxRate` put `taxRate` itself at risk of changing.

### Why `let x = 3` followed by `let x = 4` is allowed

This is the point where the word **scope** becomes essential. Immutability says one binding cannot change its value. It does **not** say the same spelling can never be used for a different binding.

At the GHCi prompt, these commands are accepted back to back:

```text
ghci> let x = 3
ghci> let oldX = x
ghci> let x = 4
ghci> x
4
ghci> oldX
3
ghci> (oldX, x)
(3,4)
```

There are now two distinct bindings that happen to use the name `x`. It helps to imagine that the compiler gives them invisible identities:

```text
first command:   x₁ = 3
second command:  oldX = x₁
third command:   x₂ = 4
current lookup:  x means x₂
```

The third command does not perform `x₁ := 4`. It introduces `x₂`, and the newer binding **shadows** the older one: when later text says `x`, name lookup finds the newer binding first. `oldX` proves the difference because it was defined using `x₁`; after `x₂` appears, `oldX` still produces `3`.

The same rule works in nested source-code scopes:

```haskell
example :: (Integer, Integer, Integer)
example =
  let x = 3                 -- outer x
  in ( x
     , let x = 4 in x       -- a new inner x shadows outer x here only
     , x                    -- back outside: outer x is still 3
     )

-- example == (3,4,3)
```

The inner `x` exists only inside its `let ... in ...` expression. Before that inner scope and after it, the outer `x` still means `3`. Nothing travelled backwards and rewrote it.

Sequential `let` statements in a `do` block use the same idea:

```haskell
main :: IO ()
main = do
  let x = 3
  let oldX = x
  let x = 4
  print (oldX, x)  -- (3,4)
```

Each later statement can see names introduced above it. The second `x` begins a newer binding for the statements below; it does not modify the first one. By contrast, writing two definitions for `x` inside the **same declaration group** is not shadowing and is rejected as a duplicate definition:

```haskell
bad =
  let x = 3
      x = 4  -- error: two definitions of x in one binding group
  in x
```

Use shadowing sparingly in ordinary source files. It is legal and sometimes useful, but names such as `originalScore` and `adjustedScore` usually make the data flow clearer than two different bindings both called `score`.

## Pure functions and side effects

| Pure calculation | Effectful action |
|---|---|
| `square 5` | Read a line from the keyboard |
| `length names` | Write to a file |
| `filter even numbers` | Print to the terminal |
| `maximum scores` | Read the current time |

Effects are not bad. Hidden and uncontrolled effects are difficult to reason about. Haskell marks an action with a type such as `IO ()` or `IO String`.

```haskell
-- Pure: creates the message as a String.
greeting :: String -> String
greeting name = "Hello, " ++ name

-- Effectful: sends the pure message to the terminal.
main :: IO ()
main = do
  putStrLn (greeting "Naledi")
```

Expected output:

```text
Hello, Naledi
```

The design keeps the reusable rule `greeting` independent of the terminal. It can be tested without performing input or output.

`greeting` never appears on the effectful side of that boundary, no matter how the program grows. Two more pairs, built the same way:

```haskell
-- Pure: builds the report text from already-known values.
report :: String -> Integer -> String
report name mark = name ++ " scored " ++ show mark

-- Effectful: the only line that touches the terminal.
main :: IO ()
main = putStrLn (report "Naledi" 82)
```

```text
Naledi scored 82
```

```haskell
-- Pure: works out how many days remain, given two day-of-year numbers.
daysRemaining :: Integer -> Integer -> Integer
daysRemaining today examDay = examDay - today

-- Effectful: print is the boundary here, not the subtraction.
main :: IO ()
main = print (daysRemaining 100 130)
```

```text
30
```

In both cases the pure function — `report`, `daysRemaining` — could be tested directly at the GHCi prompt with no `main` involved at all:

```text
ghci> report "Naledi" 82
"Naledi scored 82"
ghci> daysRemaining 100 130
30
```

Only the last line of each program, the one that calls `putStrLn` or `print`, is effectful. Everything feeding into it is an ordinary, testable value.

## Function composition

Composition connects the output of one function to the input of another, using the `.` operator. `(f . g) x` means `f (g x)`: run `g` first, then feed its result into `f`.

```haskell
import Data.Char (toUpper)

-- Add emphasis to an already-uppercased message.
addEmphasis :: String -> String
addEmphasis message = message ++ "!"

-- Compose: first uppercase every character, then add emphasis.
shout :: String -> String
shout = addEmphasis . map toUpper

main :: IO ()
main = putStrLn (shout "training complete")
```

```text
TRAINING COMPLETE!
```

Read `f . g` from right to left: `shout` first applies `map toUpper` (the right-hand function), then feeds that whole result into `addEmphasis` (the left-hand function). `map` reappears here doing the same job as before — applying `toUpper` to every character of the string. Everything in this example is a real Prelude function or an ordinary top-level definition, so it can be typed into a file exactly as shown and run.

At this stage, prefer the clearer explicit version when composition feels mysterious. It calculates exactly the same value:

```haskell
shout' :: String -> String
shout' message = addEmphasis (map toUpper message)
```

```text
ghci> shout' "training complete"
"TRAINING COMPLETE!"
```

Point-free notation is not automatically better. Clarity comes before cleverness — use `shout` when the pipeline reads naturally, and `shout'` when naming the intermediate step helps the reader.

### A second composition, chaining three functions

Composition is not limited to two steps. `words`, `length`, and a Boolean check can be chained to answer "does this sentence have more than three words?":

```haskell
hasManyWords :: String -> Bool
hasManyWords = (> 3) . length . words
```

```text
ghci> hasManyWords "Functional programming changes how we think"
True
ghci> hasManyWords "Short sentence"
False
```

Read right to left again: `words` splits the string into a list of words; `length` counts them; `(> 3)` checks whether that count exceeds three. `(> 3)` is a section — an operator with one side already filled in — which Chapter 7 covers properly; for now, read it exactly as it sounds: "is greater than 3."

## Common misconceptions

### “Haskell has no state or input/output”

False. Haskell represents effectful computations explicitly. Later lessons explain `IO` in detail.

### “Pure means the function is fast”

False. Purity makes behavior predictable; it does not guarantee an efficient algorithm.

### “Functional code means using `map` everywhere”

False. Functional design is about values, types, transformations, and controlled effects. `map` is one reusable pattern.

### “Shorter code is always more functional”

False. A readable named function can be better than a dense chain of operators.
