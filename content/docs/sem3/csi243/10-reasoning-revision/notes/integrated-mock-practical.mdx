## 1. Candidate paper and specification

Allow 90 minutes: 60 for practical questions 1–7 (58 marks), then 30 for written questions 8–12 (42 marks). Stop before section 3, save your attempt, then mark it. Award method marks for a correct policy and reasoning even if a later unrelated part fails. Do not deduct twice for the same carried-forward mistake.

A sensor has a case-sensitive identifier String and a finite list of Double temperature readings. Empty readings mean offline, not zero. A valid identifier is non-empty; whitespace-only identifiers count as non-empty in this mock. Identifiers must be unique. Every reading is finite and lies in the inclusive interval from -40 to 60 Celsius. Validate rows in encounter order; within a row check empty identifier, duplicate identifier, then readings. Return the first reason, exactly as specified below.

A present mean is the sum divided by the number of readings. Bands classify the unrounded mean: at least 30 is Hot, at least 10 is Mild, otherwise Cold. A network mean gives each online sensor equal influence; a pooled mean gives each reading equal influence. No contributing values means Nothing.

An individual line is `id: offline` or `id: value C - band` using show for the Double. The network report is `Network mean: ` followed by show of the optional equal-sensor mean. An invalid dataset instead reports `ERROR: ` followed by the reason. Error reasons are `empty id`, `duplicate id: id` or `invalid reading: id`. A valid empty dataset is reportable. Validation must preserve accepted rows exactly.

## 5. Aggregation, validation and report answers

Aggregation has two levels: readings within a sensor, then sensors within the network. Validation and reporting consume that result without inventing absent values.

**Aggregation template:** calculate each optional local result → collect present payloads → calculate one optional global result. Pooling flattens before calculating instead.

### Variation: empty network

<HaskellTryIt>

```haskell
data Sensor = Sensor
  { sensorId :: String
  , readings :: [Double]
  } deriving (Eq, Show)
meanReading :: [Double] -> Maybe Double
meanReading [] = Nothing
meanReading xs = Just (sum xs / fromIntegral (length xs))
networkMean :: [Sensor] -> Maybe Double
networkMean sensors =
  meanReading [t | Sensor _ xs <- sensors, Just t <- [meanReading xs]]

pooledMean :: [Sensor] -> Maybe Double
pooledMean sensors = meanReading [t | Sensor _ xs <- sensors, t <- xs]

main :: IO ()
main = do
  let sensors = []
  print (networkMean sensors, pooledMean sensors)
```

### Variation: valid endpoints with offline row

```haskell
data Sensor = Sensor

  , readings :: [Double]

validateNetwork :: [Sensor] -> Either String [Sensor]
validateNetwork = go []
  where
    go _ [] = Right []
    go seen (s@(Sensor key xs):rest)
      | null key = Left "empty id"
      | key `elem` seen = Left ("duplicate id: " ++ key)
      | not (all (\t -> t >= -40 && t <= 60) xs) = Left ("invalid reading: " ++ key)
      | otherwise = case go (key:seen) rest of
          Left reason -> Left reason
          Right checked -> Right (s:checked)

main :: IO ()
main = do
  let sensors = [Sensor "A" [-40,60],Sensor "B" []]
```

```haskell
module TestSupport (assertEqual, assertTrue, assertApprox, runTests) where
import System.Exit (exitFailure)

assertEqual :: (Eq a, Show a) => String -> a -> a -> IO Bool
assertEqual label expected actual = do
  let passed = expected == actual
  putStrLn (status passed ++ " " ++ label)
  if passed
    then pure True
    else do
      putStrLn ("    expected: " ++ show expected)
      putStrLn ("    actual:   " ++ show actual)
      pure False
  where
    status True = "PASS"
    status False = "FAIL"

assertTrue :: String -> Bool -> IO Bool
assertTrue label = assertEqual label True

assertApprox :: String -> Double -> Double -> IO Bool
assertApprox label expected actual =
  assertTrue label (abs (expected - actual) < 0.000001)

runTests :: [IO Bool] -> IO ()
runTests tests = do
  results <- sequence tests
  let passed = length (filter id results)
      total = length results
  putStrLn (show passed ++ "/" ++ show total ++ " tests passed")
  if and results then pure () else exitFailure
```

## 8. Cost and explicit duration weighting

**Cost template:** define input sizes and demanded output → count local traversals → sum over sensors → compare growth. Count arithmetic and identifier comparison as unit operations for this model; that assumption is not a claim about arbitrary-precision numbers or long Strings. Keep validation cost separate from aggregation.

The repeated expression under discussion is this plain Haskell definition. It is valid code but violates the specified equal-sensor policy:

```haskell
repeatedMean :: [Sensor] -> Maybe Double
repeatedMean sensors =
  meanReading [t | Sensor _ xs <- sensors, _ <- xs, Just t <- [meanReading xs]]
```

The stated repeated-work cost assumes the invariant mean is recalculated for each candidate. A compiler may float or share that pure calculation; source syntax alone does not establish actual allocation or repeated execution. The following instrumented model makes the intended visit count explicit without pretending to measure GHC optimisation.

The list-based seen-identifier validator has worst-case O(s squared) equality comparisons, independently of the linear arithmetic. Actual String comparisons cost time proportional to the inspected characters. For the small mock, clarity is acceptable; a larger implementation could use a set of identifiers with an appropriate dependency and a stated cost model.

Fully producing a line per sensor requires at least O(s) output work, plus the characters printed. The aggregate returns a constant-size optional result, but its straightforward list code may allocate intermediate lists and retain pending arithmetic. The result text itself needs space for its characters. Do not infer constant auxiliary space just from a tail-looking loop or from the final result type. [Lazy Evaluation](/docs/sem3/csi243/10-reasoning-revision/notes/lazy-evaluation) and [The Cost of a Definition](/docs/sem3/csi243/10-reasoning-revision/notes/complexity) discuss demand and pending work.

### Exam question 11: compare algorithms and policies (10 marks)

Derive the cost of calculating each sensor mean once versus recalculating it for every reading. Do the two forms implement the same policy?

<details>
<summary>Worked answer, with the reasoning</summary>

<Steps title="Answering the question">

<Step title="1. Read the question">

“Derive” needs operation counts and assumptions, not a timing result. “Do” requires a policy comparison as well as cost.

</Step>

<Step title="2. Plan">

Let s be the sensor count, n_i the readings for sensor i, N their total and k the number online. Count each local sum and length as n_i visits. Then count the outer mean over k payloads.

</Step>

<Step title="3. Solution">

Caching one local mean per sensor costs 2N visits to readings plus O(s+k) list work, so aggregation is O(s+N). In the explicit repeated-work model, sensor i performs its length-n_i mean n_i times, giving 2 times the sum of n_i squared reading visits, plus O(s+N) outer work. With one large sensor this is quadratic. The repeated collector emits each sensor mean n_i times, so it weights sensors by reading count; over exact real arithmetic that agrees with pooling, not the equal-sensor policy. With Doubles the summation order can also affect the final bits.

</Step>

<Step title="4. Check">

For counts [1,3], cached local visits are 8 and repeated visits 20. North [40] and South [0,0,0] also give different means: 20.0 versus 10.0. With every n_i bounded by a fixed constant, both visit models are linear in s; the quadratic worst case depends on growing group size.

</Step>

</Steps>

</details>

**Common errors:** saying “two calls means exponential” ignores subproblem sizes and local work. Claiming this complete application is O(s+N) ignores duplicate validation, which is quadratic in the worst case here and is performed twice by the simple app/report boundary. Benchmarks alone would not discharge the derivation.

</details>

A duration-weighted mean models unequal observation time. It is an explicit third policy, not an accidental side effect of duplicate readings.

**Weighting template:** pairs of temperature and hours → validate bounded inputs → require positive total duration → divide summed temperature-hours by total hours. Zero-hour pairs are accepted but have no influence. Hours need not sum to 24; each pair individually lies in 0 through 24.

### Variation: unequal durations

<HaskellTryIt>

```haskell
durationMean :: [(Double,Double)] -> Maybe Double
durationMean pairs
  | null pairs = Nothing
  | not (all valid pairs) = Nothing
  | total <= 0 = Nothing
  | otherwise = Just (sum [t*h | (t,h) <- pairs] / total)
  where
    total = sum [h | (_,h) <- pairs]
    valid (t,h) = t >= -40 && t <= 60 && h >= 0 && h <= 24

main :: IO ()
main = print (durationMean [(0,1),(40,3)])
```

```text
Just 30.0
```

</HaskellTryIt>

Four total hours, with 120 temperature-hours, give 30.0. The 40-degree reading has three times the influence.
