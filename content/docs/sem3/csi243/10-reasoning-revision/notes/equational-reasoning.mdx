A dry run shows what happens for **one** input. Equational reasoning argues about **all** of them.

It is possible because Haskell is pure. In an imperative language, `x` may mean different things at different moments, so you cannot simply replace an expression by its value. In Haskell you can.

## 1. Referential transparency

An expression is **referentially transparent** when it can be replaced by its value without changing observable program behaviour.

**In plain English:** if two things compute to the same value, you can swap one for the other anywhere in the code and the program still does exactly what it did before — the same "restate the dense wording plainly first" habit [Decoding Exam and Lab Language](/docs/sem3/csi243/decoding-questions) teaches for lab and exam phrasing generally.

```haskell
square :: Integer -> Integer
square n = n * n
```

```text
ghci> square 6
36
ghci> square (-4)
16
```

Any occurrence of `square 6` may be replaced by `36`, and any occurrence of `36` by `square 6`. This holds because `square` is pure: its result depends only on its argument, and evaluating it causes no effect. It works just as well for `square (-4)`: replace it by `16` anywhere it occurs, or replace `16` by `square (-4)` — both directions are licensed, and both give the same running program.

Contrast the imperative assignment:

```text
x = x + 1
```

This changes the value assigned to `x`, so the expression is **not** referentially transparent — the same text means different things before and after. Functional programs have no assignment statements; if a value must be kept, a new name is defined instead. The state of any variable is constant at any instant.

<Callout type="info" title="Why this matters here">
Referential transparency is what licenses the whole technique. Every step below replaces a subexpression with something equal to it, and purity guarantees that nothing else changes as a result.
</Callout>

## 2. Definitions are equations

A Haskell definition is a genuine equation, usable in either direction:

```haskell
double x = x + x
```

means `double x` **equals** `x + x`. So in any expression you may replace `double 5` with `5 + 5`, or `5 + 5` with `double 5`.

Reasoning proceeds by chaining such replacements, justifying each step:

```text
double (double 2)
= double (2 + 2)      -- definition of double, inner
= double 4            -- arithmetic
= 4 + 4               -- definition of double, outer
= 8                   -- arithmetic
```

```text
ghci> double (double 2)
8
```

Seen inside a program rather than only at the prompt, alongside a second, independently-traceable call so the pattern isn't tied to one number:

```haskell
-- File: DoubleDemo.hs
double :: Integer -> Integer
double x = x + x

main :: IO ()
main = do
  print (double (double 2))   -- traced above: = double 4 = 4 + 4 = 8
  print (double (double 5))   -- trace it yourself before checking: = double 10 = 10 + 10 = 20
```

```text
8
20
```

Every line names the rule used. That justification is what makes it reasoning rather than guessing, and it is what earns marks.

The same chain reads backwards too, because `=` is symmetric: `8 = 4 + 4 = double 4 = double (2 + 2) = double (double 2)`. Nothing about the direction matters — only that each step is a legal substitution of equals for equals.

## 3. Proving a property for all inputs

Take two definitions from Chapter 6:

```haskell
length :: [a] -> Int
length []     = 0        -- (L1)
length (_:xs) = 1 + length xs  -- (L2)

(++) :: [a] -> [a] -> [a]
[] ++ ys     = ys        -- (A1)
(x:xs) ++ ys = x : (xs ++ ys)  -- (A2)
```

**Claim:** `length (xs ++ ys) = length xs + length ys`, for every pair of lists.

Testing a few examples gives evidence. Proving it needs **induction over the structure of `xs`** — which is exactly the `[]` and `(x:xs)` split you already use for writing recursive functions.

<StepByStep>
  <StepByStepTitle>Structural induction over a list</StepByStepTitle>

  <Step number={1}>
  <StepTitle>Base case: xs = []</StepTitle>

  ```text
  length ([] ++ ys)
  = length ys              -- (A1)
  ```
  and
  ```text
  length [] + length ys
  = 0 + length ys          -- (L1)
  = length ys              -- arithmetic
  ```
  Both sides reduce to `length ys`, so the claim holds for `[]`.
  </Step>

  <Step number={2}>
  <StepTitle>Inductive hypothesis</StepTitle>
  Assume the claim holds for some list `xs`:
  ```text
  length (xs ++ ys) = length xs + length ys
  ```
  </Step>

  <Step number={3}>
  <StepTitle>Inductive step: show it holds for (x:xs)</StepTitle>

  ```text
  length ((x:xs) ++ ys)
  = length (x : (xs ++ ys))        -- (A2)
  = 1 + length (xs ++ ys)          -- (L2)
  = 1 + (length xs + length ys)    -- inductive hypothesis
  = (1 + length xs) + length ys    -- associativity of +
  = length (x:xs) + length ys      -- (L2), backwards
  ```
  </Step>

  <Step number={4}>
  <StepTitle>Conclude</StepTitle>
  The claim holds for `[]`, and holds for `(x:xs)` whenever it holds for `xs`. Since every finite list is built from `[]` by consing, it holds for every finite list.
  </Step>
</StepByStep>

Notice the shape: **the proof follows the same two cases as the function definition.** If you can write the recursion, you can structure the proof.

  B --> C["Inductive step: (x:xs)\nUse the hypothesis to show it then holds for x:xs"]
  C --> D["Conclusion\nHolds for every finite list —\neach one is built from [] by a finite number of conses"]

## 4. A second example

**Claim:** `sum (map (*2) xs) = 2 * sum xs`.

```haskell
sum []     = 0            -- (S1)
sum (x:xs) = x + sum xs   -- (S2)

map _ []     = []         -- (M1)
map f (x:xs) = f x : map f xs  -- (M2)
```

**Base case,** `xs = []`:

```text
sum (map (*2) [])
= sum []            -- (M1)
= 0                 -- (S1)

2 * sum []
= 2 * 0             -- (S1)
= 0                 -- arithmetic
```

**Inductive step,** assuming `sum (map (*2) xs) = 2 * sum xs`:

```text
sum (map (*2) (x:xs))
= sum ((x*2) : map (*2) xs)      -- (M2)
= (x*2) + sum (map (*2) xs)      -- (S2)
= (x*2) + 2 * sum xs             -- inductive hypothesis
= 2 * (x + sum xs)               -- distributivity
= 2 * sum (x:xs)                 -- (S2), backwards
```

The claim holds for every finite list.

```text
ghci> sum (map (*2) [1,2,3])
12
ghci> 2 * sum [1,2,3]
12
```

```haskell
-- File: SumMapDemo.hs
main :: IO ()
main = do
  print (sum (map (*2) [1, 2, 3]))   -- left side of the claim
  print (2 * sum [1, 2, 3])          -- right side of the claim
  print (sum (map (*2) [1, 2, 3]) == 2 * sum [1, 2, 3])  -- the claim itself, checked for this one list
```

```text
12
12
True
```

That final `True` is still only evidence for `[1,2,3]` — one data point, exactly as Section 3's proof warned. The completed induction above is what makes it true for every finite list, not just this one.

Both sides agree on a concrete list, exactly as the proof said they must for every list.

## 5. Using reasoning to find a fault

Reasoning also exposes errors. Suppose someone claims `reverse (reverse xs) = xs` for their definition:

```haskell
myReverse []     = []
myReverse (x:xs) = myReverse xs      -- fault: [x] is missing
```

```text
ghci> myReverse [1,2,3]
[]
ghci> myReverse [7]
[]
```

That single test is already damning — `myReverse` never returns anything but `[]`, for any argument. But a test only shows *that* it is wrong; the inductive proof below shows *why*, line by line.

Check the base case — it holds. Check the inductive step:

```text
myReverse (myReverse (x:xs))
= myReverse (myReverse xs)     -- definition
= xs                            -- inductive hypothesis
```

But the claim required `(x:xs)`, and we obtained `xs`. The step fails, and the line where it fails names the faulty equation. The missing `++ [x]` is exactly what the proof could not supply.

<CommonMistake title="Stopping at 'the proof failed' instead of reading where">
A failed inductive step is not a dead end — it is a diagnostic. Here, the step produced `xs` where the claim needed `(x:xs)`: the difference is exactly one missing element, at exactly the position `myReverse` recurses. That is what points straight at the fix, `myReverse (x:xs) = myReverse xs ++ [x]`, without any further guessing.
</CommonMistake>

<Callout type="warn" title="Reasoning assumes termination">
These arguments hold for finite lists and terminating definitions. A definition that loops forever satisfies its equations vacuously while being useless, so termination must be argued separately — as in Chapter 5.
</Callout>
