Every laboratory in this course has asked you to "specify the function" before implementing it. This lesson explains what a specification is and why the implementation is derived from it, not the other way round.

## 1. What a specification states

A specification says **what** a function computes, without saying **how**. It has three parts:

| Part | States |
|---|---|
| **Purpose** | What the function represents, in one sentence |
| **Precondition** | What must be true of the arguments before the function is applied |
| **Postcondition** | What is true of the result afterwards |

An **algorithm** is a routine that accepts a set of inputs and, for each, gives an output after a finite number of steps. It should terminate, and it should do what it is intended to do. Preconditions are assertions that must be valid before execution; postconditions are assertions that must be valid after it.

A worked example, in the notation the course lectures use:

```text
isDigit : Char -> Boolean
isDigit (Char c) : Boolean
Purpose: report whether c is one of the decimal digits.
Prec:    none; every Char is acceptable.
Postc:   result = ('0' <= c <= '9')
```

The implementation then follows directly:

```haskell
isDigit :: Char -> Bool
isDigit c = ('0' <= c) && (c <= '9')
```

```text
ghci> isDigit '5'
True
ghci> isDigit 'a'
False
```

Trace the second call, because it is the one people get wrong: `'0' <= 'a'` compares character codes, and `'0'` (code 48) really is less than `'a'` (code 97), so that half is `True`. But `'a' <= '9'` is `97 <= 57`, which is `False`. `&&` needs both sides `True`, so the whole expression is `False` — exactly what the postcondition `result = ('0' <= c <= '9')` demands, because `'a'` is not a decimal digit.

Two more from the same source:

```haskell
-- Postc: result = ((c mod 2) /= 0)
isOdd :: Integral a => a -> Bool
isOdd c = (mod c 2) /= 0

-- Postc: result = (first n elements, remaining elements)
splitAt' :: Int -> [a] -> ([a], [a])
splitAt' n xs = (take n xs, drop n xs)
```

```text
ghci> isOdd 7
True
ghci> isOdd 4
False
ghci> splitAt' 2 [10,20,30,40]
([10,20],[30,40])
```

All three specified functions, exercised together inside one real program rather than three separate prompt lines:

```haskell
-- File: SpecDemo.hs
isDigit :: Char -> Bool
isDigit c = ('0' <= c) && (c <= '9')

isOdd :: Integral a => a -> Bool
isOdd c = (mod c 2) /= 0

splitAt' :: Int -> [a] -> ([a], [a])
splitAt' n xs = (take n xs, drop n xs)

main :: IO ()
main = do
  print (isDigit '5')             -- an ordinary digit
  print (isDigit 'a')             -- the boundary-adjacent counter-example from the trace above
  print (isOdd 7)
  print (isOdd 4)
  print (splitAt' 2 [10, 20, 30, 40])
```

```text
True
False
True
False
([10,20],[30,40])
```

Each line's output is exactly what that function's own postcondition promises — that correspondence, checkable line by line, is the entire point of writing the postcondition down before the code.

<Callout type="info" title="Specification first, always">
A function's implementation is derived from its specification. Writing code first and then describing what it happens to do reverses the dependency — and means you have no independent standard against which to judge the code correct.
</Callout>

### Three more worked variations, chosen to vary the shape of `Prec` and `Postc`

`isDigit`, `isOdd`, and `splitAt'` above all have `Prec: none` and a `Postc` that is one closed formula. Three more, deliberately different in shape:

**A variation: a precondition on two arguments, not one**
```text
isDiv : Int -> Int -> String
Purpose: report whether m is divisible by n.
Prec:    m > n.
Postc:   result = "Yes, m is divisible by n" if (m mod n = 0),
                  else "No, m is not divisible by n"
```
```haskell
isDiv :: Int -> Int -> String
isDiv m n
  | m == n          = "m and n are equal"
  | m < n           = "m should be greater than n"
  | m `mod` n == 0  = "Yes, m is divisible by n"
  | otherwise       = "No, m is not divisible by n"
```
```text
ghci> isDiv 8 4
"Yes, m is divisible by n"
ghci> isDiv 3 8
"m should be greater than n"
```
`Prec` here is a *relationship between* `m` and `n`, not a limit on either one alone — `m = 3` is fine on its own, `n = 8` is fine on its own, but the pair `(3, 8)` violates `m > n`. The two extra guards, `m == n` and `m < n`, exist purely to give the out-of-precondition pair a defined, honest answer instead of silently misapplying the divisibility check to it.

**A variation: a postcondition defined inductively, not by one formula**
```text
isSorted : [Integer] -> Bool
Purpose: report whether a list is sorted in descending order.
Prec:    none.
Postc:   result = True, if xs = [] or xs has exactly one element;
         result = True, if head xs >= head (tail xs) and isSorted (tail xs) is True;
         result = False, otherwise.
```
```haskell
isSorted :: [Integer] -> Bool
isSorted []       = True
isSorted [_]      = True
isSorted (x:y:ys) = x >= y && isSorted (y:ys)
```
```text
ghci> isSorted [5,3,1]
True
ghci> isSorted [3,1,5]
False
```
`isDigit`'s postcondition names one Boolean expression that can be checked directly against `c`, with no reference to `isDigit` itself. `isSorted`'s postcondition is **recursive** — the second line's condition mentions `isSorted (tail xs)`, the very function being specified — which is exactly why the implementation below it is a recursion, not a single expression: the postcondition and the base-case/recursive-case template from Chapter 5 are stating the same structure twice, once in prose and once in code.

**A variation: a postcondition stated behind a class constraint**
```text
containsValue : Eq a => a -> [a] -> Bool
Purpose: report whether v occurs anywhere in xs.
Prec:    none on the values of v or xs — but the constraint Eq a => is doing
         precondition-like work on the type itself: a must support ==.
Postc:   result = True, if v equals some element of xs; False, otherwise.
```
```haskell
containsValue :: Eq a => a -> [a] -> Bool
containsValue _ []     = False
containsValue v (x:xs)
  | v == x    = True
  | otherwise = containsValue v xs
```
```text
ghci> containsValue 3 [1,2,3]
True
ghci> containsValue 5 [1,2,3 :: Int]
False
```
This one is worth pausing on, because it is tempting to write `Prec: none` and stop there — no numeric range or list-emptiness condition restricts `v` or `xs` the way `average`'s precondition restricts its list. But `Eq a =>` is restricting something all the same: not which *values* are acceptable, but which *types* are — the same constraint-first reading [Decoding Exam and Lab Language](/docs/sem3/csi243/decoding-questions) and Chapter 9 both build on. A specification's `Prec` line can state a condition on the type variable itself, not only on the values that variable's arguments happen to take.

## 2. Partitioning the input and output

This is the formal version of the domain idea from Chapter 5.

The input set **I** comprises a valid subset **Iv** and an invalid subset **Ie**:

```text
I = Iv ∪ Ie    where   Iv = I \ Ie
```

The output set **O** comprises a valid subset **Ov** and an erroneous subset **Oe**:

```text
O = Ov ∪ Oe    where   Ov = O \ Oe
```

Read the symbols literally, since the rest of the lesson leans on them: `∪` is set union — "every element that is in either set" — and `\` is set difference — "this set, with that one's elements taken out." So `I = Iv ∪ Ie` says every input falls into one of the two subsets, and `Iv = I \ Ie` says the valid inputs are exactly what remains of `I` once the invalid ones are removed. The output set is split the same way.

A function `f` acts on arguments from **Iv** (the precondition state) to give output in **Ov** (the postcondition state):

<SiteDiagram chart={`flowchart LR
  Iv["Iv — valid inputs\n(precondition holds)"] -->|"f — intended behaviour"| Ov["Ov — valid outputs\n(postcondition holds)"]
  Ie["Ie — invalid inputs\n(precondition fails)"] -.->|"? — not specified"| Oe["Oe — erroneous outputs"]
`} caption="The specification only ever promises the solid arrow, Iv → Ov. Section 3 below is precisely the decision about what the dotted arrow does." />

Two things follow, and both should now be familiar:

- **A type is usually wider than Iv.** `fac :: Integer -> Integer` accepts every integer, but the specification's `Iv` is only the non-negative ones. That gap is where `fac (-1)` looped forever in Chapter 5.
- **A function may still produce an anomaly on valid input.** `f` may give output in `Oe` even for arguments from `Iv` — through a coding fault, an overflow, or a division that was not guarded.

## 3. Making the precondition explicit

Once you have written the precondition, you have three choices for what lies outside it. You met all three in Chapter 5 and Chapter 9:

| Choice | Mechanism | Effect |
|---|---|---|
| Reject it | `error "..."` | Stops with a message; not recoverable |
| Define it | Extend the base case | The value gets a documented answer |
| Report it | Return `Maybe` | Failure visible in the type; caller must handle it |

```haskell
-- Precondition rejected.
fac :: Integer -> Integer
fac n
  | n < 0            = error "fac: only defined for non-negative integers"
  | n >= 0 && n <= 1 = 1
  | otherwise        = n * fac (n - 1)

-- Precondition reported.
facMaybe :: Integer -> Maybe Integer
facMaybe n
  | n < 0     = Nothing
  | n <= 1    = Just 1
  | otherwise = fmap (n *) (facMaybe (n - 1))
```

```text
ghci> fac 5
120
ghci> fac 0
1
ghci> fac (-1)
*** Exception: fac: only defined for non-negative integers
```

The otherwise branch of `facMaybe` uses `fmap`, which has not been introduced yet in this course — so it earns an explanation before moving on. Read `fmap (n *) (facMaybe (n - 1))` left to right: `fmap` takes a function — here the section `(n *)`, "multiply by `n`" — and applies it *inside* whatever `facMaybe (n - 1)` turns out to be, without you having to pattern-match on `Just`/`Nothing` by hand. Concretely, for `Maybe`: `fmap f (Just x) = Just (f x)`, and `fmap f Nothing = Nothing`. So if the recursive call fails, the failure passes straight through — `n` is never multiplied by anything, and no exception is raised. This is Haskell's `Functor` interface applied to `Maybe`; see [A First Glimpse of Functor](/docs/sem3/csi243/09-polymorphism/notes/maybe-and-instances) in Chapter 9 for where `fmap` and `Functor` themselves come from.

Hand-tracing `facMaybe 3` shows the chain building up, one `fmap` per recursive call:

```text
facMaybe 3
= fmap (3 *) (facMaybe 2)
= fmap (3 *) (fmap (2 *) (facMaybe 1))
= fmap (3 *) (fmap (2 *) (Just 1))       -- facMaybe 1 = Just 1, base case
= fmap (3 *) (Just 2)                    -- fmap (2*) (Just 1) = Just (2*1)
= Just 6                                 -- fmap (3*) (Just 2) = Just (3*2)
```

```text
ghci> facMaybe 5
Just 120
ghci> facMaybe (-1)
Nothing
```

<CommonMistake title="Choosing a mechanism without recording it">
Writing `facMaybe` and leaving the specification untouched hides the decision. `facMaybe`'s precondition is actually **none** — every `Integer` is acceptable, because failure is now reported in the type instead of rejected. State which of the three mechanisms was chosen, in the specification text itself, not only in the code.
</CommonMistake>

Whichever you choose, **state it in the specification**. An unstated precondition is a defect waiting to surface.

## 4. What correctness claims

A function is **correct with respect to its specification** when, for every argument satisfying the precondition, it terminates and produces a result satisfying the postcondition.

Three things follow, and all three are examinable:

1. **Correctness is relative.** There is no such thing as correct code in the abstract — only code correct against a stated specification. Change the specification and the same code may become wrong.
2. **Type checking is not correctness.** A well-typed function may compute the wrong value, or never terminate. `fac 0 = 0` type checks perfectly and is wrong.
3. **Testing is evidence, not proof.** Passing tests shows the function worked for those inputs. Only reasoning over the definition — the next lesson — argues about all inputs.

<Callout type="warn" title="A compiler proves consistency, not intent">
GHC verifies that types are used consistently. It cannot know what you meant. The specification is the only record of intent, which is why it is worth writing down.
</Callout>

## 5. Cohesion: one function, one task

A function should do **one and only one logical task**. This is the functional-programming form of cohesion.

Functional programming focuses on the model of the problem domain: a collection of data types, plus user-defined functions and types over them. Functions focus on **what** is to be computed, not **how** — and small, single-purpose functions are then combined by composition and recursion.

```haskell
-- Two tasks in one function: harder to specify, test, and reuse.
reportAverage :: [Double] -> String
reportAverage xs = "Average: " ++ show (sum xs / fromIntegral (length xs))

-- Two functions, each with a clean specification.
average :: [Double] -> Double
average xs = sum xs / fromIntegral (length xs)

report :: Double -> String
report x = "Average: " ++ show x
```

```text
ghci> average [2,4,6]
4.0
ghci> report (average [2,4,6])
"Average: 4.0"
ghci> reportAverage [2,4,6]
"Average: 4.0"
```

Run both routes side by side to see them agree exactly, which is the whole argument for why the split version is preferred despite producing an identical string:

```haskell
-- File: Cohesion.hs
average :: [Double] -> Double
average xs = sum xs / fromIntegral (length xs)

report :: Double -> String
report x = "Average: " ++ show x

reportAverage :: [Double] -> String
reportAverage xs = "Average: " ++ show (sum xs / fromIntegral (length xs))

main :: IO ()
main = do
  putStrLn (report (average [2, 4, 6]))   -- the two-function route
  putStrLn (reportAverage [2, 4, 6])       -- the one-function route
  print (average [2, 4, 6])                -- only possible because average returns a Double, not a String
```

```text
Average: 4.0
Average: 4.0
4.0
```

The third line is the practical payoff of the split: `average [2, 4, 6]` on its own is a genuine `Double` that anything expecting a number can use directly — feed it into a further calculation, compare it, average a list of averages. `reportAverage [2, 4, 6]` can never produce that `4.0` on its own; its result is permanently locked inside the string `"Average: 4.0"`.

Both routes give the same string. The difference is not in what they compute, but in what you can test and reuse: `average` alone can be checked against a numeric postcondition (`result = sum / length`) without ever inspecting a string, and it can be reused anywhere a `Double` is needed — inside a report, a comparison, another calculation. `reportAverage` can only ever be tested by string comparison, and can only ever be reused as a full report.

The second version can be tested without inspecting strings, and `average` is reusable. Each has a postcondition you could actually write down.

## 6. Composition and specifications

Composition connects specifications as well as code. Given

```text
∘ :: ((A → C), (B → A)) → (B → C)
(f ∘ g) x = f (g x)
```

the type of `∘` requires functions of **compatible types**: the result type of `g` must be the argument type of `f`.

The same holds for the specifications. To compose `f` after `g` safely, the postcondition of `g` must guarantee the precondition of `f`:

```haskell
average :: [Double] -> Double   -- Prec: the list is non-empty
report  :: Double -> String     -- Prec: none
```

`report . average` is safe because `report` has no precondition. But `average . someFilter` is only safe if that filter can never return an empty list — which is exactly the kind of question a specification lets you ask before the failure happens.

A composition that gets this wrong fails at run time, not compile time, because `head`'s precondition is not visible to the type checker:

```text
ghci> (head . sort) [3,1,2]
1
ghci> (head . sort) []
*** Exception: Prelude.head: empty list
```

`sort` accepts `[]` happily — its postcondition never guarantees a non-empty result — so `head . sort` inherits `head`'s precondition unchanged. The type `[a] -> a` type checks either way; only reasoning about the preconditions predicts which call will crash.

<RecognitionStrategy title="Checking whether a composition is safe">
To check `f . g`, do not look at the types alone — they will always line up if `g`'s result type matches `f`'s argument type. Instead ask: does `g`'s **postcondition** guarantee `f`'s **precondition**? If yes, the composition is safe for every input `g` accepts. If no, find the input to `g` that breaks it.
</RecognitionStrategy>
