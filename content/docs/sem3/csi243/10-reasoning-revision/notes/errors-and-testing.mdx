A great deal of laboratory time is lost to errors that would take a minute to fix if their category were recognised. This lesson classifies them.

## 1. Two stages of analysis

When an expression is submitted for evaluation, there are **two stages** before anything runs.

<StepByStep>
  <StepByStepTitle>What happens before evaluation</StepByStepTitle>

  <Step number={1}>
  <StepTitle>Syntax analysis</StepTitle>
  The expression is checked against the syntax laid down for expressions. If it does not conform, the computer signals a **syntax error**.
  </Step>

  <Step number={2}>
  <StepTitle>Type analysis</StepTitle>
  If the syntax is correct, the expression is analysed to see whether it possesses a sensible type. If it fails, the computer signals a **type error**.
  </Step>

  <Step number={3}>
  <StepTitle>Evaluation</StepTitle>
  Only if the expression passes **both** stages does evaluation begin. Similar remarks apply to definitions before a script is accepted.
  </Step>
</StepByStep>

This is why Chapter 2 insisted on asking "is it well typed?" before "what value does it produce?" A type error prevents evaluation entirely.

**Strong typing** is important because adherence to the discipline helps in designing clear, well-structured programs, and because a wide range of logical errors can be trapped by a computer that enforces it.

`} caption="Both gates must pass before a single reduction step happens. A semantic error can only occur inside the third box." />

## 2. Syntax errors versus semantic errors

The two classes of error, with examples from the course notes:

| Class | Concerns | Examples |
|---|---|---|
| **Syntax errors** | The structure or syntax of the language | Type mismatch; unbalanced parentheses; a missing `else`; `if (2 = "tree")` |
| **Semantic errors** | The interpretation or meaning of the program | Division by zero; list index out of range; using an uninitialised value |

The practical difference is **when** they surface:

- A syntax or type error is caught **before the program runs**. GHC refuses to load the module.
- A semantic error is caught **while it runs**, if at all. `head []` compiles perfectly and fails only when reached.

<Callout type="info" title="Which is better to have?">
A compile-time error, every time. It is found immediately, on your machine, with a message pointing at the line. This is why widening a partial function into a total one — with `Maybe`, or an extra pattern — converts a run-time failure into something the compiler can check.
</Callout>

<CommonMistake title="'Syntax error' is used two ways — know which one you mean">
The table above uses "syntax error" loosely, for **anything** caught before the program runs — which is why it lists a type mismatch alongside a missing `else`. Section 3 below is more precise: it splits that broad compile-time bucket into **Syntax** (structural only — parentheses, keywords, layout), **Scope**, **Type**, **Class constraint**, **Module**, and **Import** categories. When precision matters, as it does on an exam, a type mismatch is a **type error**, not a syntax error in the strict sense — even though both are compile-time and both stop the module from loading.
</CommonMistake>

## 3. The standard CSI243 errors

Collected from every chapter, with the category and the question to ask.

### Compile-time

| Message | Category | Ask |
|---|---|---|
| `parse error on input ...` | Syntax | Is an `else` missing? Are the parentheses balanced? Is the indentation consistent? |
| `Variable not in scope: x` | Scope | Spelling and case. `score`, `Score`, and `scores` are three different names. |
| `Couldn't match expected type 'Bool' with actual type 'Int'` | Type | Which subexpression must produce `Bool`? |
| `No instance for (Num a)` | Class constraint | Which class does the operation need? Add it before `=>`. |
| `No instance for (Show Shape)` | Class constraint | Add `deriving (Show)`. |
| `Ambiguous type variable` | Type | Does an annotation express the intended type, as in `read s :: Integer`? |
| `File name does not match module name` | Module | Do the file and the `module` line agree exactly? |
| `Ambiguous occurrence 'nub'` | Import | Use `hiding`, or a qualified import. |

### Run-time

| Message | Category | Ask |
|---|---|---|
| `Non-exhaustive patterns in function f` | Semantic | Which input matches no equation? Add a catch-all. |
| `Non-exhaustive guards` | Semantic | Is `otherwise` missing? |
| `Prelude.head: empty list` | Semantic | Was the empty case handled before calling a partial function? |
| `Prelude.!!: index too large` | Semantic | Is the index within `0 .. length - 1`? |
| `Prelude.read: no parse` | Semantic | Can the input text really denote that type? |
| `divide by zero` | Semantic | Is the divisor guarded? |
| Session hangs | Semantic | Is the recursive argument shrinking towards the base case? |

## 4. Choosing test cases

Chapter 3 gave three categories. Use all three, every time:

| Category | Means | Example for `absoluteValue` |
|---|---|---|
| **Normal** | An ordinary representative input | `absoluteValue (-5)` |
| **Boundary** | Zero, an empty structure, a decision edge | `absoluteValue 0` |
| **Invalid** | Outside the mathematical domain, where the signature permits it | Depends on the precondition |

A weak suite tests only the normal case. A strong one tests the edges, because that is where faults concentrate:

```text
ghci> absoluteValue (-5)
5
ghci> absoluteValue 0
0
ghci> absoluteValue 5
5
```

Boundary tests are not a formality — they are where a specific, common class of bug hides:

```haskell
-- A tempting but wrong version: strict inequalities instead of <=.
isDigitBad :: Char -> Bool
isDigitBad c = ('0' < c) && (c < '9')
```

```text
ghci> isDigitBad '5'
True
ghci> isDigitBad '0'
False
ghci> isDigitBad '9'
False
```

The full suite, run together, is what actually exposes the pattern — normal cases hiding the fault, boundary cases catching it:

```haskell
-- File: BoundaryTest.hs
isDigitBad :: Char -> Bool
isDigitBad c = ('0' < c) && (c < '9')

main :: IO ()
main = do
  putStrLn "Normal cases (all look correct):"
  print (isDigitBad '3')
  print (isDigitBad '5')
  print (isDigitBad '7')
  putStrLn "Boundary cases (both wrong):"
  print (isDigitBad '0')
  print (isDigitBad '9')
```

```text
Normal cases (all look correct):
True
True
True
Boundary cases (both wrong):
False
False
```

Read top to bottom: three normal digits, three `True` results, everything looking fine. Then the two boundary digits, both `False` — both wrong, since `'0'` and `'9'` are digits. A test run stopped after the first block would have shipped this bug.

`isDigitBad` passes every normal test — `'5'` looks perfectly fine — and fails on **both** boundary digits, `'0'` and `'9'`, because `<` excludes the very endpoints that the postcondition `'0' <= c <= '9'` includes. A suite of `'3'`, `'5'`, `'7'` never finds this fault; a suite that also tries `'0'` and `'9'` finds it on the first run.

### Boundaries worth testing by type

| Argument type | Test at least |
|---|---|
| A whole number | `0`, a negative, a positive, and the precondition edge |
| A list | `[]`, a singleton, and a list of two or more |
| A `Char` | The characters immediately **outside** each range boundary |
| Two arguments | The equal case, and each ordering |

The `Char` row is the one most often skipped. Chapter 3's `isDigitChar` used `'/'` and `':'` — the characters immediately either side of `'0'` and `'9'` — precisely because a mistaken strict comparison passes ordinary examples while rejecting the boundary digits.

## 5. A diagnostic procedure

When something fails, work through this rather than changing code at random.

<StepByStep>
  <StepByStepTitle>Diagnosing a failure</StepByStepTitle>

  <Step number={1}>
  <StepTitle>Read the whole message</StepTitle>
  GHC names the file, the line, the expected type, and the actual type. Most of the answer is already there.
  </Step>

  <Step number={2}>
  <StepTitle>Classify it</StepTitle>
  Compile-time or run-time? Syntax, type, class, or semantic? The table above narrows it immediately.
  </Step>

  <Step number={3}>
  <StepTitle>Find the smallest failing subexpression</StepTitle>
  Enter parts of the expression at the prompt separately, and use `:type` on each until one disagrees with your expectation.
  </Step>

  <Step number={4}>
  <StepTitle>Compare against the specification</StepTitle>
  If it compiles and runs but the answer is wrong, the fault is in the formula, not the syntax. Return to the examples and dry run.
  </Step>

  <Step number={5}>
  <StepTitle>Fix the cause, not the symptom</StepTitle>
  Adding a catch-all to silence a non-exhaustive warning hides the fault if the missing case was genuinely reachable.
  </Step>
</StepByStep>

## 6. Turning run-time failures into compile-time ones

The single most valuable habit, and the tools you now have for it:

| Run-time failure | Prevented by |
|---|---|
| Non-exhaustive patterns | `:set -Wincomplete-patterns` |
| `head []` | Match `[]` yourself, or return `Maybe` |
| `read: no parse` | Validate before parsing |
| Wrong constructor handled | One equation per constructor, warnings on |
| Non-terminating recursion | Confirm the argument shrinks; dry run two steps |

```text
ghci> :set -Wincomplete-patterns
ghci> :reload
```

Turn this on for every laboratory. With the flag set, a function missing a case for negative arguments produces a warning naming the unmatched pattern **as soon as the module loads** — before you ever supply the input that would otherwise have crashed it at run time with `Non-exhaustive patterns in function f`.
