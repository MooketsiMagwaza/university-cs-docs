For each ambiguity, use this procedure: quote the ambiguous phrase, state the chosen interpretation, list disjoint input partitions, then implement and test. ## 1. Invalid parity for an Int

Lab 02's isEven task mentions an invalid-input response, but every defined Int or Integer is even or odd, including zero and negative values. Text that has not been parsed, a missing input and a negative value rejected by an application are three different concerns. They must not be silently called a third parity.

### Template

```text
Core policy: every defined Int accepted
  even n -> even label; otherwise -> odd label
Extra application policy, only if stated: n >= 0
Missing-data policy: Nothing means no number supplied
```

Start with the core policy. The three worked variations keep the same total Int domain and change the representation of the answer. Later validation may wrap this core; that does not change parity itself.

### Worked variation: signed inputs with labels

Use the exact even/odd labels from Lab 02 and test all sign partitions.

<HaskellTryIt>

```haskell
isEven :: Int -> String
isEven n = if n `mod` 2 == 0 then "The number is even" else "The number is odd"
main :: IO ()
main = print (map isEven [-3,-2,0,1,2])
```

```text
["The number is odd","The number is even","The number is even","The number is odd","The number is even"]
```

</HaskellTryIt>

The disjoint partitions are negative odd, negative even, zero, positive odd and positive even. -3 has a non-zero remainder, -2 and zero have zero remainder. There is no remaining defined Int for an invalid-parity branch.

### Worked variation: guards with the same contract

Change the syntax, keeping the input domain and labels identical.

<HaskellTryIt>

```haskell
isEven :: Int -> String
isEven n
  | even n = "The number is even"
  | otherwise = "The number is odd"
main :: IO ()
main = print (isEven (-1), isEven 0, isEven 7)
```

```text
("The number is odd","The number is even","The number is odd")
```

</HaskellTryIt>

The negative and positive odd cases choose otherwise; zero chooses the first guard. The guard rewrite preserves the total parity contract. It cannot create a meaningful third case.

### Worked variation: count even inputs without labels

Change the result representation to the bothEven task's count.

<HaskellTryIt>

```haskell
bothEven :: Int -> Int -> Int
bothEven x y = (if even x then 1 else 0) + (if even y then 1 else 0)
main :: IO ()
main = print (bothEven 3 5, bothEven 2 5, bothEven 3 4, bothEven 0 (-2))
```

```text
(0,1,1,2)
```

</HaskellTryIt>

All four Boolean parity combinations are covered. Zero and -2 are both even, so the count is 2. Exactly-one corresponds to XOR of the even tests.

### Optional application policies, stated before implementation

The core policy above accepts every defined Int. Suppose a separate application explicitly requires non-negative values: its reporting wrapper returns Nothing for a negative and Just a parity label otherwise. Alternatively an application may permit a missing number: it accepts Maybe Int, with Nothing reporting absence and Just n retaining signed parity. These two wrappers have different domains and meanings. Both are total on their respective defined input types; they must not turn rejection or absence into a false arithmetic result.

```text
nonNegativeParity:
  n < 0 -> Nothing; n >= 0 -> Just (core parity label)
suppliedParity:
  Nothing -> Nothing; Just n -> Just (core parity label)
```

### Worked variation: application policies on negative input

Now compare the extra non-negative restriction with a present signed value.

<HaskellTryIt>

```haskell
parity :: Int -> String
parity n = if even n then "even" else "odd"
nonNegativeParity :: Int -> Maybe String
nonNegativeParity n = if n < 0 then Nothing else Just (parity n)
suppliedParity :: Maybe Int -> Maybe String
suppliedParity input = case input of
  Nothing -> Nothing
  Just n -> Just (parity n)
main :: IO ()
main = print (nonNegativeParity (-2), suppliedParity (Just (-2)), suppliedParity Nothing)
```

```text
(Nothing,Just "even",Nothing)
```

</HaskellTryIt>

The restriction rejects -2. The missing-data wrapper accepts the supplied -2 and classifies it as even. Nothing means absence, not an odd number. This is the first worked case for each wrapper policy.

### Worked variation: application policies at zero

Now both wrapper policies have an ordinary defined zero.

<HaskellTryIt>

```haskell
parity :: Int -> String
parity n = if even n then "even" else "odd"
nonNegativeParity :: Int -> Maybe String
nonNegativeParity n = if n < 0 then Nothing else Just (parity n)

  Nothing -> Nothing
  Just n -> Just (parity n)
main :: IO ()
main = print (nonNegativeParity 0, suppliedParity (Just 0), suppliedParity Nothing)
```

```text
(Just "even",Just "even",Nothing)
```

</HaskellTryIt>

Zero is allowed under non-negative validity and has even parity. A missing value still reports Nothing. Returning Nothing for zero would be a different, positive-only policy.

### Worked variation: application policies on an ordinary odd number

Now both wrappers succeed with an odd input.

<HaskellTryIt>

```haskell

nonNegativeParity :: Int -> Maybe String
nonNegativeParity n = if n < 0 then Nothing else Just (parity n)

  Nothing -> Nothing
  Just n -> Just (parity n)
main :: IO ()
main = print (nonNegativeParity 3, suppliedParity (Just 3), nonNegativeParity (-3))
```

```text
(Just "odd",Just "odd",Nothing)
```

</HaskellTryIt>

Both successful paths preserve the odd label at 3, while the non-negative policy rejects -3. Together these three comparisons cover rejection, the zero boundary, success and absence.

### Common errors

Treating negative values as invalid without saying so changes the task. GHC gives no error for such a guard. `undefined :: Int` is not a third integer parity: it is a non-value whose evaluation fails. Do not use it as a normal invalid-input test. A parser's error is also separate from the mathematical classifier.

### Practice with answers

Specify a non-negative-only application wrapper. **Answer:** P is every defined Int for the wrapper; Q reports a validation failure for `n < 0` and otherwise returns the core parity label. If the wrapper instead has P: `n >= 0`, its contract makes no promise for negatives. Do not confuse the two designs.

## 2. Divisor zero, equality and order

Lab 02 says test divisibility only when m is greater than n, with separate equality and less-than labels. That does not settle zero: (5,0) satisfies m > n but mod by zero is undefined. Choose precedence for overlaps. Here the reporting policy is zero first, then equality, then less-than, then divisibility.

### Template

```text
Disjoint partitions under zero-first policy:
1. n == 0 -> zero-divisor message
2. n /= 0 and m == n -> equality message
3. n /= 0 and m < n -> order message
4. n /= 0 and m > n and m mod n == 0 -> divisible
5. n /= 0 and m > n and m mod n /= 0 -> not divisible
```

Each branch excludes earlier branches, so these partitions cover all pairs. The executable versions use Integer to avoid bounded quotient overflow; the same reporting policy applies to Int with its arithmetic limits stated. The zero-divisor text is our explicit addition because the old task does not specify it. Equality-first is another defensible reporting policy if zero is still checked before mod; it differs at (0,0).

### Worked variation: ordinary quotient branches

Start with the two specified greater-than cases.

<HaskellTryIt>

```haskell
isDiv :: Integer -> Integer -> String
isDiv m n
  | n == 0 = "Zero divisor"
  | m == n = "m and n are equal"
  | m < n = "m should be greater than n"
  | m `mod` n == 0 = "Yes, m is divisible by n"
  | otherwise = "No, m is not divisible by n"
main :: IO ()
main = print (isDiv 8 4, isDiv 8 3)
```

```text
("Yes, m is divisible by n","No, m is not divisible by n")
```

</HaskellTryIt>

Eight exceeds both divisors. Its remainder is 0 with 4 and 2 with 3. Only these final two partitions execute mod.

### Worked variation: overlapping error conditions

Now zero overlaps equality and the less-than report.

<HaskellTryIt>

```haskell

  | otherwise = "No, m is not divisible by n"
main :: IO ()

```

```text
("Zero divisor","Zero divisor","Zero divisor")
```

</HaskellTryIt>

All three calls select zero first. (0,0) would otherwise select equality; (-2,0) would otherwise select order. Precedence affects the reported reason, so include these overlap tests.

### Worked variation: non-zero equality, order and negative values

Now test the remaining partitions without confusing mathematical divisibility and the lab's extra ordering policy.

<HaskellTryIt>

```haskell

  | n == 0 = "Zero divisor"
  | m == n = "m and n are equal"
```

```text

```

</HaskellTryIt>

Equality and less-than never execute mod. -4 is mathematically divisible by -2, but `-4 < -2`, so the lab's ordered policy reports order. Four exceeds -2 and is divisible. This is a policy for reporting, not a new definition of divisibility.

### Alternative reporting precedence

A relation-first reporter is also safe if its zero check precedes every mod call. It preserves the lab's equality/order responses even when the divisor is zero. Its effective partitions are equality, strict less-than, then zero with m greater than n, then the two remainder cases. Both reporters use short labels below to make the differing reasons easy to compare.

```text
Zero-first: n==0 before all relationships
Relation-first: m==n, then m<n, then n==0, then mod
Restricted arithmetic core: P(m,n) = m>n and n/=0
```

### Worked variation: two policies at equality with zero

Now the guards overlap at the same input.

<HaskellTryIt>

```haskell
zeroFirst :: Integer -> Integer -> String
zeroFirst m n
  | n == 0 = "zero"
  | m == n = "equal"
  | m < n = "order"
  | m `mod` n == 0 = "divisible"
  | otherwise = "not divisible"
relationFirst :: Integer -> Integer -> String
relationFirst m n
  | m == n = "equal"
  | m < n = "order"
  | n == 0 = "zero"
  | m `mod` n == 0 = "divisible"
  | otherwise = "not divisible"
main :: IO ()
main = print (zeroFirst 0 0, relationFirst 0 0, 0 > (0 :: Integer) && 0 /= (0 :: Integer))
```

```text
("zero","equal",False)
```

</HaskellTryIt>

Both reporters avoid mod. Their reason differs by the documented precedence. The restricted arithmetic core has no promised numeric result for this pair, as its precondition is False.

### Common errors

The old precondition m > n is insufficient for safe mod: (5,0) is a valid pair under it. GHC accepts a mod expression with zero and fails when it is evaluated; the key run-time phrase is `divide by zero`. Do not run that case. Repair the restricted arithmetic precondition to `m > n && n /= 0`, or use the total reporter above. ## 3. Index equal to length and the original index

Lab 03 says indices start at zero, gives the example (3,10), and says reject y greater than the length. The boundary y equal to length is also invalid: a length-n list has positions 0 through n-1. The example establishes result order as (index,element), despite prose that can sound reversed. We choose an explicit safe result.

### Template

```text
Purpose: return (original index, element at that index)
P for a numeric result: 0 <= i and i < length xs
Reporting contract: Nothing outside that subset
                   Just (i, xs !! i) inside it
```

The finite-list assumption makes length terminate. This lesson checks the boundary policy; [Recursive List Design](/docs/sem3/csi243/06-lists-tuples/notes/recursive-list-design) derives the recursive algorithm without repeating it here.

### Worked variation: last valid and first invalid

Now compare adjacent positions around length.

<HaskellTryIt>

```haskell
atPosition :: [a] -> Int -> Maybe (Int,a)
atPosition xs i
  | i < 0 || i >= length xs = Nothing
  | otherwise = Just (i, xs !! i)
main :: IO ()
main = print (atPosition [3,5,2,10 :: Int] 3, atPosition [3,5,2,10 :: Int] 4)
```

```text
(Just (3,10),Nothing)
```

</HaskellTryIt>

Length is 4. Index 3 selects 10 and preserves 3; index 4 is equal to length and has no element. Rejecting only greater-than would miss it.

### Worked variation: empty and singleton boundaries

Now length can be zero or one.

<HaskellTryIt>

```haskell
atPosition :: [a] -> Int -> Maybe (Int,a)
atPosition xs i
  | i < 0 || i >= length xs = Nothing
  | otherwise = Just (i, xs !! i)
main :: IO ()
main = print (atPosition ([] :: [Int]) 0, atPosition [7 :: Int] 0, atPosition [7 :: Int] 1)
```

```text
(Nothing,Just (0,7),Nothing)
```

</HaskellTryIt>

No index is valid for []. A singleton has exactly index 0; 1 equals its length and is rejected. The same strict upper bound handles both.

### Worked variation: negative and far oversize

Now invalid positions occur on either side of the valid subset.

<HaskellTryIt>

```haskell
atPosition :: [a] -> Int -> Maybe (Int,a)
atPosition xs i
  | i < 0 || i >= length xs = Nothing
  | otherwise = Just (i, xs !! i)
main :: IO ()
main = print (atPosition "ab" (-1), atPosition "ab" 1, atPosition "ab" 8)
```

```text
(Nothing,Just (1,'b'),Nothing)
```

</HaskellTryIt>

The disjoint categories are negative, valid, equal-to-length and greater-than-length. The string variation shows the element type need not be numeric. Validation prevents !! from seeing a missing position.

## 4. A square specially defined at zero

The Making Choices example explicitly defines square 0 = 1 and square y = y*y elsewhere. Ordinary mathematical squaring gives zero at zero. The implementation is correct only relative to the chosen specification: do not 'fix' the special case by silently substituting ordinary mathematics.

### Template

```text
specialSquare n = if n == 0 then 1 else n*n
ordinarySquare n = n*n
Partitions: zero; negative non-zero; positive non-zero
```

Use Integer here to give the mathematical product without overflow. An Int version promises bounded machine arithmetic unless the contract restricts values enough to avoid overflow.

### Worked variation: zero reveals the specification

Now compare the same input under two contracts.

<HaskellTryIt>

```haskell
specialSquare :: Integer -> Integer
specialSquare 0 = 1
specialSquare n = n * n
main :: IO ()
main = print (specialSquare 0, (0 :: Integer) * 0)
```

```text
(1,0)
```

</HaskellTryIt>

The outputs differ because the specifications differ. The name square cannot override an explicit zero case.

### Worked variation: positive non-zero input

Now guards implement the same special specification.

<HaskellTryIt>

```haskell
specialSquare :: Integer -> Integer
specialSquare n
  | n == 0 = 1
  | otherwise = n * n
main :: IO ()
main = print (map specialSquare [1,2,5])
```

```text
[1,4,25]
```

</HaskellTryIt>

All inputs use the ordinary-product branch. Testing only these values would fail to detect a missing special zero case.

### Worked variation: negative non-zero input

Now both the sign partition and an independent postcondition are checked.

<HaskellTryIt>

```haskell
specialSquare :: Integer -> Integer
specialSquare n = if n == 0 then 1 else n * n
post :: Integer -> Integer -> Bool
post n r = if n == 0 then r == 1 else r == n * n
main :: IO ()
main = print (specialSquare (-3), post (-3) 9, post 0 0)
```

```text
(9,True,False)
```

</HaskellTryIt>

-3 uses the non-zero branch and returns 9. A result of 0 for input 0 fails the special contract even though it is the ordinary square.

## 5. Negative bounds, inclusivity and reversed ranges

A requirement saying 'sum a range' leaves the endpoints, signs and reversed order unsettled. Negative bounds do not inherently make a finite sum invalid. Here the primary policy is an inclusive ascending range, accepting signed bounds and treating lo > hi as empty. Two explicit alternatives are shown for comparison: reject negative bounds, or traverse downwards when reversed.

### Template

```text
Primary: signedRange lo hi = sum of integers lo through hi inclusive
         lo > hi means empty sum 0
Alternative A: nonNegativeRange rejects either negative bound with Nothing
Alternative B: directedRange includes both endpoints and travels towards hi
```

These are different contracts, not interchangeable implementations. A one-argument sum from 1 to n likewise needs a policy for `n < 1`. For a product, the empty identity is 1 rather than 0; the proof section uses that distinction.

### Worked variation: negative to positive

Now the same negative bounds are accepted or rejected under different policies.

<HaskellTryIt>

```haskell
signedRange :: Integer -> Integer -> Integer
signedRange lo hi = sum [lo..hi]
nonNegativeRange :: Integer -> Integer -> Maybe Integer
nonNegativeRange lo hi
  | lo < 0 || hi < 0 = Nothing
  | otherwise = Just (sum [lo..hi])
directedRange :: Integer -> Integer -> Integer
directedRange lo hi = if lo <= hi then sum [lo..hi] else sum [lo,lo-1..hi]
main :: IO ()
main = print (signedRange (-2) 2, nonNegativeRange (-2) 2, directedRange (-2) 2)
```

```text
(0,Nothing,0)
```

</HaskellTryIt>

The primary and directed sums are -2-1+0+1+2 = 0. The non-negative-only policy rejects the bounds instead of inventing a numeric answer. Include negative-negative ranges such as [-3..-1] when extending the tests.

### Worked variation: equal endpoints including zero

Now a range has exactly one member, under all three policies.

<HaskellTryIt>

```haskell
signedRange :: Integer -> Integer -> Integer
signedRange lo hi = sum [lo..hi]
nonNegativeRange :: Integer -> Integer -> Maybe Integer
nonNegativeRange lo hi
  | lo < 0 || hi < 0 = Nothing
  | otherwise = Just (sum [lo..hi])

main :: IO ()
main = print (signedRange 0 0, nonNegativeRange 0 0, directedRange 0 0, signedRange (-3) (-3), nonNegativeRange (-3) (-3), directedRange (-3) (-3))
```

```text
(0,Just 0,0,-3,Nothing,-3)
```

</HaskellTryIt>

[0..0] contains zero, while [-3..-3] contains -3. A singleton is not an empty range. The rejection policy still rejects the negative singleton. Both endpoint inclusivity and sign policy are visible.

### Worked variation: reversed positive bounds

Now direction changes the mathematical task.

<HaskellTryIt>

```haskell

  | lo < 0 || hi < 0 = Nothing
```

## 7. Correctness against a mathematical product

A positivity proof shows only that the result exceeds zero. A function returning 1 everywhere would satisfy that property and still fail the factorial specification. The ho7 homework obligation is stronger: **prove the factorial implementation computes the specified product**. Use the existing [Proofs of Programs I](/docs/sem3/csi243/10-reasoning-revision/notes/proofs-of-programs-i) layout and the narrated method in [Lab: Proofs of Programs I](/docs/sem3/csi243/10-reasoning-revision/notes/lab-proofs-of-programs-i). Other proof techniques and counterexample construction remain in [Proof Patterns](/docs/sem3/csi243/10-reasoning-revision/notes/proof-patterns).

### Template

```text
Purpose and P: identify the intended product and accepted arguments
Claim: implementation input = independently specified mathematical product
Induct on: the argument or range width controlling recursion
Base: use the empty product identity, with a reason on each line
Hypothesis: equality for the smaller valid input
Step: unfold implementation, apply IH, use the product extension identity
Conclusion: equality for every valid input
Termination separately: a non-negative measure decreases on each call
```

The mathematical product of no factors is 1. This convention makes the extension identity work at the first step too. All proofs use Integer and fully defined finite inputs, so they are not relying on overflowed Int arithmetic.

### Factorial: the exact homework claim

Purpose: return the factorial of a non-negative integer. P: `n >= 0`. Define `F(n)` independently as the product of the integers 1 through n, with `F(0)=1`. The postcondition is `result = F(n)`, not just `result > 0`. The implementation uses the usual guarded factorial equations, with negative rejection outside the proof's domain.

```haskell
fact :: Integer -> Integer
fact n
  | n < 0 = error "negative factorial argument"
  | n == 0 = 1                    -- (F0)
  | otherwise = n * fact (n - 1)  -- (FS), here n > 0
```

The rejection branch is not a returned mathematical factorial. A negative call is deliberately excluded from runnable tests. A version using `n <= 1` as its base branch has equivalent non-negative equations: at 1 the recursive form gives `1 * fact 0 = 1`.

**Claim:** `fact n = F(n)` for every non-negative Integer n. **Induct on:** n. The product identity is `F(k+1) = (k+1) * F(k)`: separate the last factor from `1*2*...*k*(k+1)`, using associativity and commutativity of integer multiplication. It also holds for k=0 by the empty-product convention.

```text
Base n = 0:
  fact 0
  = 1                         -- (F0)
  = F(0)                      -- empty product definition

Hypothesis:
  fact k = F(k) for an arbitrary k >= 0

Step, goal fact (k+1) = F(k+1):
  fact (k+1)
  = (k+1) * fact ((k+1)-1)    -- (FS), k+1 > 0
  = (k+1) * fact k            -- integer arithmetic
  = (k+1) * F(k)              -- IH
  = F(k+1)                    -- product extension identity

Conclusion:
  base and step establish equality for all n >= 0 by induction.
```

**Termination, separately:** choose measure n. At n=0 return directly. At n>0 the next input n-1 remains non-negative and is strictly smaller. Therefore every valid call reaches zero in finitely many recursive steps; multiplication of the resulting finite Integers terminates. Together with the equality proof, this establishes total correctness against the product specification. The negative rejection branch terminates with an exception, not a normal numeric result.

## 8. Range products: induct on remaining width

An inclusive range product may have a negative lower bound; its termination depends on width, not the sign of lo. Adopt the ascending policy: reversed bounds give the empty product 1. Let R(lo,hi) be the independent mathematical product of the ascending integers lo through hi.

### Template

```text
rp lo hi = 1                         if lo > hi
rp lo hi = lo * rp (lo+1) hi         otherwise
Claim: rp lo hi = R(lo,hi)
Measure: max 0 (hi-lo+1)
R(lo,hi) = 1                         if lo > hi
R(lo,hi) = lo * R(lo+1,hi)           if lo <= hi
```

The specification describes the product's factors; the implementation chooses left-to-right recursion. The product identity is obtained by separating the first factor. For the proof, fix hi and induct on the natural width; lo then determines which factors remain.

**Claim:** rp equals R for all defined Integer bounds. **Induct on:** width `w=max 0 (hi-lo+1)`.

```text
Base w = 0, so lo > hi:
  rp lo hi
  = 1                            -- empty-range equation
  = R(lo,hi)                     -- empty product

Hypothesis:
  rp a hi = R(a,hi) for bounds with width k

Step w = k+1, so lo <= hi:
  rp lo hi
  = lo * rp (lo+1) hi            -- non-empty-range equation
  = lo * R(lo+1,hi)              -- IH: next width is k
  = R(lo,hi)                     -- first-factor product identity

Conclusion:
  equality holds at width 0 and is preserved by each width step,
  hence it holds for all finite ranges.
```

**Termination, separately:** in the non-empty branch, lo+1 reduces width by exactly one and leaves another legitimate pair of Integer bounds. Width cannot decrease indefinitely in the naturals. At width zero the base returns 1. This works even when the range crosses zero; a zero factor changes the result, not the termination argument.

## 9. Shifted products and double factorial

A change to the factors changes the specification identity. A shifted factorial product multiplies 2 through n+1; a double factorial multiplies n,n-2,n-4 and so on, ending at 2 or 1. These are siblings of factorial, not synonyms for it. Double factorial needs both zero and one base cases.

### Template

```text
shifted 0 = 1
shifted n = (n+1) * shifted (n-1)       for n > 0
S(n) = product of integers 2 through n+1

doubleFact 0 = 1
doubleFact 1 = 1
doubleFact n = n * doubleFact (n-2)     for n >= 2
D(n) = product n*(n-2)*... of positive factors with n's parity
```

P is n >= 0 for both functions. S(0) and D(0) are empty products. For double factorial, D(1) is the singleton product 1. Two different parity chains require two starting cases.

**Shifted-product claim:** shifted n = S(n). **Induct on:** n.

```text
Base:
  shifted 0 = 1                    -- shifted base
            = S(0)                 -- empty product 2 through 1

Hypothesis: shifted k = S(k), k >= 0

Step:
  shifted (k+1)
  = (k+2) * shifted k              -- shifted recursive equation
  = (k+2) * S(k)                   -- IH
  = S(k+1)                        -- append last factor k+2

Conclusion: equality for all n >= 0 by induction.
```

**Double-factorial claim:** doubleFact n = D(n). **Induct on:** n using the existing strong-induction template from Proof Patterns (the needed smaller argument is n-2).

```text
Base n=0:
  doubleFact 0 = 1                 -- base equation
               = D(0)             -- empty product
Base n=1:
  doubleFact 1 = 1                 -- base equation
               = D(1)             -- singleton product 1

Hypothesis:
  doubleFact j = D(j) for every 0 <= j < n

Step n >= 2:
  doubleFact n
  = n * doubleFact (n-2)           -- recursive equation
  = n * D(n-2)                     -- IH, 0 <= n-2 < n
  = D(n)                           -- separate largest factor n

Conclusion:
  both bases and the step cover every non-negative n.
```

**Termination, separately:** shifted decreases n to n-1 for n>0. doubleFact decreases n to n-2 for n>=2; both 0 and 1 stop. Both preserve non-negativity, so n is a natural-number measure for each. Negative input policy is deliberately not used to fabricate a product.

## 10. Functional, procedural, object-oriented and declarative descriptions

A paradigm is a style of organising computation. A procedural description gives ordered steps and updates; object-oriented design groups state and operations around objects; a functional description uses functions and values; a declarative description states wanted relationships. Functional programming is commonly declarative, but a recursive function still specifies an algorithm. A language can support several styles.

### Template

```text
1. State the common input/output contract
2. Identify the organising unit: procedure, object, function or relation
3. Explain state changes or value construction
4. Check the same example under each description
5. Do not infer speed from the category
```

OO code may use pure methods and a functional application may perform IO. Encapsulation is not unique to objects. Haskell's parametric and type-class polymorphism do not require inheritance. These programs are functional reference results; the alternative descriptions are designs, not claims that Haskell has changed paradigms.

```haskell
main = print (eligible [20,17,18,20], eligible [])
```

```text
([20,18,20],[])
```

</HaskellTryIt>

Functional: construct a list by comprehension. Procedural: visit inputs and append qualifying values. OO: a Roster offers an eligibleMembers query. Declarative: select exactly qualifying members in original order with duplicates retained. Replacing the result with a set changes this contract.

### Worked variation: polymorphism without inheritance

Now reuse occurs across different types.

<HaskellTryIt>

```haskell
swap :: (a,b) -> (b,a)
swap (x,y) = (y,x)
main :: IO ()
main = print (swap (3 :: Integer,True), swap ('x',"ok"))
```

```text
((True,3),("ok",'x'))
```

</HaskellTryIt>

The function works at multiple types through type variables. A procedural routine can also be generic; an OO generic method need not use subclass overriding. Declaratively the first result field is the old second and vice versa. Parametric polymorphism and OO subtype polymorphism are different mechanisms.

## 11. Markup, programming and a declared mini-language

Markup describes document structure or presentation, such as headings and paragraphs. A general programming language expresses computation through variables, selection and repetition or recursion. A notation may combine markup with embedded executable expressions. Classify capabilities and semantics, rather than treating angle brackets as proof either way.

### Template

```text
What do the constructs mean?
Do tags describe structure or execute operations?
Where does evaluation occur: browser, template engine, or nowhere?
Which inputs determine the output?
```

The following Haskell programs manipulate markup as strings and interpret a tiny command language. Printing a string with a tag does not execute a browser. The generating program, its string result and a renderer's later action are separate layers.

### Worked variation: a heading string

Now the output describes document structure.

<HaskellTryIt>

```haskell
heading :: String -> String
heading title = "<h1>" ++ title ++ "</h1>"
main :: IO ()
main = print (heading "Exam")
```

```text
"<h1>Exam</h1>"
```

</HaskellTryIt>

The Haskell function computes a string; h1 denotes a heading when interpreted as HTML. The tag alone does not calculate a grade or visit a list. This toy builder assumes trusted literal titles; arbitrary HTML escaping is outside its stated contract.

### Worked variation: selection in the generator

Now code chooses which markup string to produce.

<HaskellTryIt>

```haskell
badge :: Integer -> String
badge mark = if mark >= 50 then "<p>Pass</p>" else "<p>Fail</p>"
main :: IO ()
main = print (badge 49, badge 50)
```

```text
("<p>Fail</p>","<p>Pass</p>")
```

</HaskellTryIt>

Under P: marks 0..100, Haskell performs selection. The p tags describe paragraphs in the generated output. Markup inside a program does not remove the computation.

### Worked variation: an interpreted command

Now strings are explicitly given operational meanings.

<HaskellTryIt>

```haskell
applyCommand :: String -> Integer -> Integer
applyCommand command n
  | command == "double" = 2 * n
  | command == "increment" = n + 1
  | otherwise = n
main :: IO ()
main = print (applyCommand "double" 4, applyCommand "increment" 4, applyCommand "<h1>" 4)
```

```text
(8,5,4)
```

</HaskellTryIt>

Double and increment compute because this interpreter defines their meanings. The h1 string is unknown here and leaves n unchanged under the stated default. Text has meaning relative to a language's rules.

### Worked variation: a template combines structure and values

Now a calculation is inserted into document structure.

<HaskellTryIt>

```haskell
report :: [Integer] -> String
report xs = "<p>Total: " ++ show (sum xs) ++ "</p>"
main :: IO ()
main = print (report [2,3], report [])
```

```text
("<p>Total: 5</p>","<p>Total: 0</p>")
```

</HaskellTryIt>

The sum is demanded while the string is produced; markup surrounds its representation. A template system with executable expressions combines computation and markup. A static paragraph skeleton alone does not compute the total.

Calling every notation with tags non-programming ignores embedded computation. Calling static HTML a general algorithm language ignores its semantics. There is no GHC diagnostic for these classifications. State the evaluator. print adds string quotes; putStrLn prints contents without them.

### Practice with answers

Does a Haskell string containing `2+3` evaluate to 5? **Answer:** no. It remains text unless an interpreter explicitly evaluates it. The same distinction applies to code displayed inside a document.

## 12. Referential transparency, optimisation and concurrency

Referential transparency permits replacing a pure expression by its equal value without changing meaning. This supports local reasoning and can permit sharing or compiler transformations. Independent pure computations are easier to run concurrently because they do not race to update shared mutable state. None of this guarantees parallel execution, smaller cost or automatic speed-up.

### Template

```text
1. State the pure function's contract
2. Identify equal expressions or independent computations
3. State the legal substitution or possible scheduling
4. State demand, cost and execution assumptions
5. Conclude an opportunity, not a timing promise
```

Concurrency is overlapping progress; parallelism is simultaneous execution. Scheduling, runtime support, workload size, communication, laziness and retained data affect performance. See [Lazy Evaluation](/docs/sem3/csi243/10-reasoning-revision/notes/lazy-evaluation) and [Complexity by Recurrence](/docs/sem3/csi243/10-reasoning-revision/notes/complexity-by-recurrence) for the mechanisms.

### Worked variation: substitution of equals

Now compare a pure expression before and after substitution.

<HaskellTryIt>

```haskell
cube :: Integer -> Integer
cube n = n * n * n
main :: IO ()
main = print (cube 3 + cube 3, 27 + 27 :: Integer)
```

```text
(54,54)
```

</HaskellTryIt>

cube 3 equals 27, so replacement preserves the answer. A compiler may exploit this, but the output does not show whether the call ran once or twice.

### Worked variation: independent subtotals

Now two results read separate immutable lists.

<HaskellTryIt>

```haskell
totals :: [Integer] -> [Integer] -> (Integer,Integer)
totals xs ys = (sum xs,sum ys)
main :: IO ()
main = print (totals [1,2] [10,20], totals [] [4])
```

```text
((3,30),(0,4))
```

</HaskellTryIt>

Neither sum needs the other's result or updates shared state. This exposes possible parallel work; pair construction and printing do not by themselves schedule the sums in parallel.

### Worked variation: a dependent next computation

Now an earlier result determines the branch.

<HaskellTryIt>

```haskell
pipeline :: [Integer] -> Integer
pipeline xs = let total = sum xs in if total > 5 then total * total else total + 1
main :: IO ()
main = print (pipeline [1,2], pipeline [3,4])
```

```text
(4,49)
```

</HaskellTryIt>

The totals 3 and 7 choose different branches. This dependency remains in pure code: purity does not remove the need to compute total to choose the branch.

### Worked variation: sharing a named result

Now one pure binding is used twice.

<HaskellTryIt>

```haskell
shared :: [Integer] -> Integer
shared xs = let total = sum xs in total + total
main :: IO ()
main = print (shared [1,2,3], 2 * sum [1,2,3 :: Integer])
```

```text
(12,12)
```

</HaskellTryIt>

Both return 12. A shared binding supports reuse under lazy evaluation; an optimiser may transform it further. Printed values establish neither exact allocation nor relative execution time.

A student says functional code is always faster because the compiler automatically runs every function in parallel. Which benefits are defensible?

GHC accepts pure but expensive algorithms. No diagnostic rejects an unmeasured speed promise. Repair to state an opportunity and its assumptions. Reading or printing IO actions cannot generally be replaced with their past results because interaction with the world matters.

### Practice with answers

## Summary

<Callout type="key" title="Remember">

State assumptions before code. Int has no third parity; zero divisors need explicit handling; a zero-based index equal to length is invalid. A special square may return 1 at zero. Range signs, direction, empty identities and grade boundaries belong in the contract. Prove the specified product equality, then termination separately. Paradigm labels describe organisation and capabilities. Purity supports reasoning and opportunities for optimisation and concurrency without guaranteeing speed.

</Callout>
