All mathematical claims below concern finite, fully defined inputs. A typed Haskell value may also contain an unevaluated failure or infinite structure; the finite-domain assumptions matter. An `Integer` calculation avoids bounded-integer overflow. A predicate is a function returning `Bool`; a relation can be represented by a predicate with several arguments.

## 1. Purpose, precondition and relational postcondition

A purpose names the task, a precondition restricts when its promise applies, and a postcondition relates the original arguments to the returned result. Write the relation before the implementation. Merely saying that the result is positive usually leaves many wrong answers possible.

### Template

```text
f :: A -> B
Purpose: intended task
P x: valid-input predicate
Q x r: result r has the required relationship to x
Obligation: if P x holds and f x returns r, then Q x r
```

A and B are the input and result types. P is not code that must run first: it states the assumption. Q mentions both input x and candidate result r. A total-correctness contract also requires termination on P.

### Worked variation: cube, with an exact result

Change from recognising an input to checking a proposed output.

<HaskellTryIt>

```haskell
cube :: Integer -> Integer
cube n = n * n * n
post :: Integer -> Integer -> Bool
post n r = r == n * n * n
main :: IO ()
main = print (cube (-2), post (-2) (cube (-2)), post (-2) 8)
```

```text
(-8,True,False)
```

</HaskellTryIt>

Purpose: compute the cube; P: every defined Integer; Q: r equals n cubed. Substituting n = -2 gives -8. Positivity would reject the correct answer and accept the wrong 8.

### Worked variation: maximum of two arguments

Now Q uses inequalities and membership, rather than restating a formula.

<HaskellTryIt>

```haskell
larger :: Integer -> Integer -> Integer
larger x y = if x >= y then x else y
post :: Integer -> Integer -> Integer -> Bool
post x y r = r >= x && r >= y && (r == x || r == y)
main :: IO ()
main = print (larger 4 4, post 2 5 5, post 2 5 6)
```

```text
(4,True,False)
```

</HaskellTryIt>

Both arguments are allowed, including ties. The bound alone accepts 6 for inputs 2 and 5; the last clause requires a supplied value. Q describes the answer without copying the algorithm.

### Worked variation: a paired result

Now one result has two related components.

<HaskellTryIt>

```haskell
addAndDifference :: Integer -> Integer -> (Integer, Integer)
addAndDifference x y = (x + y, abs (x - y))
post :: Integer -> Integer -> (Integer, Integer) -> Bool
post x y (s,d) = s == x + y && d == abs (x - y)
main :: IO ()
main = print (addAndDifference (-3) 5, post (-3) 5 (2,8), post (-3) 5 (8,2))
```

```text
((2,8),True,False)
```

</HaskellTryIt>

The sum is 2 and the absolute difference is 8. Both constraints must hold in their named positions. Swapping the fields type checks but fails the contract.

### Worked variation: a restricted discount

Now both inputs carry restrictions; use whole cents to avoid floating approximation.

<HaskellTryIt>

```haskell
finalPrice :: Integer -> Integer -> Integer
finalPrice cents percent = cents * (100 - percent) `div` 100
pre :: Integer -> Integer -> Bool
pre cents percent = cents >= 0 && percent >= 0 && percent <= 100
main :: IO ()
main = print (pre 2500 20, finalPrice 2500 20, pre 2500 101)
```

```text
(True,2000,False)
```

</HaskellTryIt>

Purpose: discounted whole cents, rounding down through integer division. P: non-negative price and percent from 0 to 100 inclusive. Q: the displayed formula. The invalid percentage is classified, not evaluated as though it met P.

### Common errors

Writing `post r = r >= 0` for a distance loses the inputs. GHC gives no error because this is a valid Boolean expression. Repair Q to relate r to both inputs. A type checks shapes, not intended arithmetic.

### Practice with answers

Specify a function returning ten times an integer. **Answer:** purpose: multiply by ten; P: all defined integers; Q: `r == 10 * n`. For -2 the answer is -20, so an unconditional positive-result clause is wrong.

## 2. Types, domains, codomains and valid subsets

The input type describes representable inputs; the mathematical domain of a restricted contract is the subset on which its promise applies. The codomain is the declared set of possible result values; the image is the set actually produced. Output validity usually relates a result to its input, rather than to one global set.

### Template

```text
I = input type's defined values
Iv = { x in I : P x }; Ie = I minus Iv
O = result type's defined values
Allowed(x) = { r in O : Q x r }
Image(f) = { f x : x in Iv and evaluation returns }
```

Set braces here mean collections satisfying a condition. Iv and Ie are disjoint and cover I. Nothing can be a correct result of a total validator; it is not automatically an erroneous output.

### Worked variation: non-zero denominator subset

The type permits zero but a quotient contract excludes it.

<HaskellTryIt>

```haskell
validDivisor :: Integer -> Bool
validDivisor d = d /= 0
main :: IO ()
main = print (map validDivisor [-2,0,2])
```

```text
[True,False,True]
```

</HaskellTryIt>

I is Integer; Iv excludes zero; Ie contains zero. Negative divisors are valid for integer division. Non-zero and positive are different preconditions.

### Worked variation: output depends on input

Two results have the same type, but only one is correct for this input.

<HaskellTryIt>

```haskell
post :: Integer -> Integer -> Bool
post n r = r == n + 1
main :: IO ()
main = print (post 2 3, post 2 4, post 3 4)
```

```text
(True,False,True)
```

</HaskellTryIt>

Four is wrong for n = 2 and right for n = 3. A single set of good Integer outputs cannot express this distinction.

### Worked variation: failure as a specified result

Extend a numeric task to all integers by reporting absence.

<HaskellTryIt>

```haskell
nonNegative :: Integer -> Maybe Integer
nonNegative n = if n < 0 then Nothing else Just n
main :: IO ()
main = print (map nonNegative [-1,0,2])
```

```text
[Nothing,Just 0,Just 2]
```

</HaskellTryIt>

The new domain is every defined Integer; the codomain is Maybe Integer. Q requires Nothing exactly for negative inputs, otherwise Just the original number. Ie is empty for this reporting contract.

### Worked variation: image narrower than codomain

Now the function always returns one of two numbers.

<HaskellTryIt>

```haskell
parityCode :: Integer -> Integer
parityCode n = if even n then 0 else 1
main :: IO ()
main = print (map parityCode [-3,-2,0,5])
```

```text
[1,0,0,1]
```

</HaskellTryIt>

The codomain Integer includes 20, but the image is 0 and 1. No Int or Integer has an invalid parity. Restricting an application to non-negative inputs would be an extra policy.

### Common errors

Confusing codomain with image, or calling every Nothing an error, changes the contract. GHC cannot reject these prose mistakes. Name the result type, then state Q for each partition. An `Eq a` constraint is a static type requirement, separate from a Boolean condition on an input value.

### Practice with answers

For `positive :: Integer -> Bool`, True exactly when the input exceeds zero, what is Ie? **Answer:** empty if every integer is accepted. False for -2 is a correct result.

## 3. Partial correctness and total correctness

Partial correctness says: whenever a valid call terminates normally, its result satisfies Q. Total correctness additionally requires every valid call to terminate normally. Partial here does not mean that only some tests pass; it differs from a partial function lacking a result for some typed inputs.

### Template

```text
Partial correctness: P x and f x returns r imply Q x r
Termination: P x implies f x returns normally in finite time
Total correctness: partial correctness plus termination
```

A loop cannot violate a returned-value clause because it returns nothing. An exception is not a normal numeric result. Termination is a separate obligation.

### Worked variation: terminating countdown

Begin with both obligations satisfied on non-negative inputs.

<HaskellTryIt>

```haskell
down :: Integer -> Integer
down n = if n == 0 then 0 else down (n - 1)
main :: IO ()
main = print (map down [0,1,4])
```

```text
[0,0,0]
```

</HaskellTryIt>

P: n >= 0; Q: r = 0. Each call decreases n towards zero and zero returns 0. No claim is made for negative inputs.

### Worked variation: a terminating wrong answer

Now termination holds but Q fails.

<HaskellTryIt>

```haskell
badCube :: Integer -> Integer
badCube n = n * n
main :: IO ()
main = print (badCube 3, badCube 3 == 3 * 3 * 3)
```

```text
(9,False)
```

</HaskellTryIt>

The call returns immediately but Q for a cube requires 27. Termination alone does not establish partial correctness.

### Worked variation: failure reported normally

Now failure is a specified constructor.

<HaskellTryIt>

```haskell
safePred :: Integer -> Maybe Integer
safePred n = if n <= 0 then Nothing else Just (n - 1)
main :: IO ()
main = print (map safePred [-1,0,1,4])
```

```text
[Nothing,Nothing,Just 0,Just 3]
```

</HaskellTryIt>

Every defined integer terminates. Q requires Nothing for `n <= 0` and Just (n-1) otherwise. Absence can be totally correct.

### Worked variation: finite lists as an assumption

The input structure supplies termination.

<HaskellTryIt>

```haskell
count :: [a] -> Integer
count [] = 0
count (_:xs) = 1 + count xs
main :: IO ()
main = print (count ([] :: [Int]), count [7], count [2,3,4])
```

```text
(0,1,3)
```

</HaskellTryIt>

A finite list's spine decreases by one per call. Q is its mathematical number of elements. This does not claim a finite result for an infinite list; see Lazy Evaluation.

### Common errors

GHC accepts `spin n = spin n`; no type error diagnoses non-termination. Do not run it. Missing cases can also type check. Repair the cases and prove valid branches reach a base. See [Proof Patterns](/docs/sem3/csi243/10-reasoning-revision/notes/proof-patterns) for refuting claims.

### Practice with answers

Do the three down tests prove total correctness for all non-negative integers? **Answer:** no. A decreasing-n argument proves termination; induction on the equations establishes the returned result.

## 4. Decreasing termination measures

A termination measure assigns every valid recursive call a natural number. It must strictly decrease on every recursive edge. A smaller integer alone is insufficient: integers continue downwards forever. A multi-argument algorithm may need a combined measure.

### Template

```text
Choose mu(input) in {0,1,2,...}
Show: base branch returns
Show: recursive calls preserve validity
Show: mu(next input) < mu(current input)
Conclude: no infinite descending chain of natural numbers
```

mu is a mathematical function of the arguments. The returned value need not decrease. Check every recursive call, even when there are several.

### Worked variation: subtracting two

Change from unit countdown to two base values.

<HaskellTryIt>

```haskell
steps :: Integer -> Integer
steps n = if n <= 1 then 0 else 1 + steps (n - 2)
main :: IO ()
main = print (map steps [0,1,2,5])
```

```text
[0,0,1,2]
```

</HaskellTryIt>

For n >= 0 use n. The recursive branch has n >= 2, so n-2 remains non-negative and smaller. Both 0 and 1 stop.

### Worked variation: remaining range width

Now the first argument increases while the measure decreases.

<HaskellTryIt>

```haskell
rangeSum :: Integer -> Integer -> Integer
rangeSum lo hi = if lo > hi then 0 else lo + rangeSum (lo + 1) hi
main :: IO ()
main = print (rangeSum (-2) 1, rangeSum 4 3, rangeSum 3 3)
```

```text
(-2,0,3)
```

</HaskellTryIt>

Use max 0 (hi-lo+1). For [-2..1] it follows 4,3,2,1,0. Increasing lo is harmless. Reversed bounds are explicitly empty.

### Worked variation: consuming a list

Now use a structural measure.

<HaskellTryIt>

```haskell
removeZeros :: [Integer] -> [Integer]
removeZeros [] = []
removeZeros (x:xs) = if x == 0 then removeZeros xs else x : removeZeros xs
main :: IO ()
main = print (removeZeros [0,2,0,3], removeZeros [])
```

```text
([2,3],[])
```

</HaskellTryIt>

Both recursive branches use the shorter xs. Number of zeros is a bad measure: keeping 2 does not reduce it, although recursion progresses.

### Worked variation: division by two

Now the decrease can exceed one.

<HaskellTryIt>

```haskell
halvings :: Integer -> Integer
halvings n = if n <= 1 then 0 else 1 + halvings (n `div` 2)
main :: IO ()
main = print (map halvings [0,1,2,8])
```

```text
[0,0,1,3]
```

</HaskellTryIt>

For n >= 0 use n. When n > 1, n div 2 is non-negative and smaller. Eight follows 8,4,2,1: three recursive steps.

### Exam question: choose a measure (4 marks)

An inclusive range recurses on (lo+1,hi) while `lo <= hi`. Give a measure working even when lo is negative.

### Common errors

'n gets smaller, so it stops' omits a lower bound. GHC cannot diagnose that proof gap. Negative countdown n-1 never reaches zero. Restrict P or implement a signed policy moving towards zero. Int overflow may invalidate an arithmetic measure; these examples use Integer.

### Practice with answers

For recursion consuming two lists until either is empty, suggest a measure. **Answer:** min of their finite lengths decreases by one in the two-cons branch. Their sum also decreases, by two; show the base branch separately.

## 5. Conjunction, inclusive choice and negation

Conjunction `p && q` requires both conditions. Inclusive disjunction `p || q` requires at least one, and permits both. Negation `not p` reverses a Boolean answer. Write parentheses to show which complete predicate is negated. These operations join assertions; they do not join arbitrary numbers.

### Template

```text
both p q = p && q
atLeastOne p q = p || q
opposite p = not p
```

p and q stand for Bool expressions. A range uses conjunction: both endpoints must be respected. Alternatives use disjunction. Saying neither means negating the whole alternative.

### Worked variation: all four truth pairs

Start with the complete truth table for all three operations.

<HaskellTryIt>

```haskell
main :: IO ()
main = print [(p,q,p && q,p || q,not p) | p <- [False,True], q <- [False,True]]
```

```text
[(False,False,False,False,True),(False,True,False,True,True),(True,False,False,True,False),(True,True,True,True,False)]
```

</HaskellTryIt>

The last row has both True: both && and inclusive || return True. not p depends only on the first column.

### Worked variation: an inclusive interval

Now the Booleans come from numeric comparisons.

<HaskellTryIt>

```haskell
inside :: Integer -> Bool
inside x = x >= 0 && x <= 100
outside :: Integer -> Bool
outside x = not (inside x)
main :: IO ()
main = print [(x,inside x,outside x) | x <- [-1,0,100,101]]
```

```text
[(-1,False,True),(0,True,False),(100,True,False),(101,False,True)]
```

</HaskellTryIt>

Zero and 100 satisfy both bounds. Outside is the complement. Replacing && with || would admit every integer: one bound or the other always holds.

### Worked variation: alternative permissions

Now either permission suffices, including possession of both.

<HaskellTryIt>

```haskell
access :: Bool -> Bool -> Bool
access card guest = card || guest
main :: IO ()
main = print (access True False, access False True, access True True, not (access False False))
```

```text
(True,True,True,True)
```

</HaskellTryIt>

A card or a guest pass permits entry. Both are allowed. With neither, access is False and its negation is True. This requirement is inclusive, unlike XOR.

### Worked variation: neither of two faults

Now a single not covers a compound condition.

<HaskellTryIt>

```haskell
healthy :: Bool -> Bool -> Bool
healthy overheating leaking = not (overheating || leaking)
main :: IO ()
main = print [healthy a b | (a,b) <- [(False,False),(False,True),(True,False),(True,True)]]
```

```text
[True,False,False,False]
```

</HaskellTryIt>

Only the first pair has no fault. not overheating || leaking would accept any leaking machine, which reverses the requirement.

`x >= 0 || x <= 100` is a logical error, so GHC gives no error. `1 && True` instead is ill-typed; the key diagnostic is `Couldn't match`. Repair by comparing a number to obtain a Bool, then combine it. Keep faulty programs in plain fences when experimenting.

### Practice with answers

## 6. Implication: if, sufficient conditions and unless

`p` implies `q` says that whenever p holds, q must hold. It fails only when p is True and q is False. It does not assert that p actually happens. In 'if p then q', p is sufficient for q; q is necessary for p. A rule 'q unless p' is normally formalised as 'if not p then q'; record that interpretation when wording is unclear.

### Template

```text
implies p q = not p || q
if p then q: implies p q
q unless p: implies (not p) q
```

This is a Boolean encoding of logical implication, not the Haskell conditional expression, which needs an else branch. A false antecedent makes the implication true without asserting the consequent.

### Worked variation: complete implication table

Begin with both possible values for each assertion.

<HaskellTryIt>

```haskell
implies :: Bool -> Bool -> Bool
implies p q = not p || q
main :: IO ()
main = print [(p,q,implies p q) | p <- [False,True], q <- [False,True]]
```

```text
[(False,False,True),(False,True,True),(True,False,False),(True,True,True)]
```

</HaskellTryIt>

Rows with p False have no obligation to check. The only prohibited row has p True and q False.

### Worked variation: passing requires a threshold

Now p is a claim made by a report and q is a numeric fact.

<HaskellTryIt>

```haskell
consistent :: Integer -> Bool -> Bool
consistent mark passed = not passed || mark >= 50
main :: IO ()
main = print (consistent 49 True, consistent 50 True, consistent 70 False)
```

```text
(False,True,True)
```

</HaskellTryIt>

Saying passed at 49 breaks the implication. At 70, saying not passed does not break this one-way rule; an iff rule would be needed to force that classification.

### Worked variation: restricting a universal statement

Now implication selects which members owe a property.

<HaskellTryIt>

```haskell
main :: IO ()
main = print (all (\n -> not (n > 0) || n >= 1) [-2,0,1,4 :: Integer])
```

```text
True
```

</HaskellTryIt>

Every positive listed integer is at least 1. The -2 and 0 cases are outside the antecedent, so they do not refute the statement. Do not use && here: that would demand all numbers be positive.

### Worked variation: unless as an exception

Now an exception cancels an obligation.

<HaskellTryIt>

```haskell
rule :: Bool -> Bool -> Bool
rule emergency wearsBadge = emergency || wearsBadge
main :: IO ()
main = print [rule e b | (e,b) <- [(False,False),(False,True),(True,False),(True,True)]]
```

```text
[False,True,True,True]
```

</HaskellTryIt>

Read the policy as 'wear a badge unless there is an emergency': not emergency implies wearsBadge. The emergency rows impose no badge requirement, so this rule does not prohibit wearing one during an emergency.

### Exam question: translate a conditional requirement (4 marks)

Every registered student must have a mark. Given pairs (registered,hasMark), write the predicate for a list.

### Common errors

`p && q` requires p, so it is not implication. `q implies p` is the converse, not an equivalent rewrite. GHC cannot spot either semantic mistake. The contrapositive, `not q` implies `not p`, is equivalent; the inverse is not in general.

## 7. Only if: necessary conditions and direction

'p only if q' means p is permitted only when q holds: p implies q. The words only if introduce the necessary condition. 'p if q' reverses the arrow: q implies p. Neither one-way assertion automatically gives equivalence.

### Template

```text
p only if q = not p || q
p if q      = not q || p
contrapositive of p only if q = q || not p
```

The final line encodes 'not q implies not p'. It is the same Boolean formula with the alternatives reordered. Name p and q before translating prose.

### Worked variation: entry only if ticketed

Now translate a permission rule.

<HaskellTryIt>

```haskell
rule :: Bool -> Bool -> Bool
rule entered ticket = not entered || ticket
main :: IO ()
main = print [rule e t | (e,t) <- [(False,False),(False,True),(True,False),(True,True)]]
```

```text
[True,True,False,True]
```

</HaskellTryIt>

Entering without a ticket fails. Owning a ticket without entering is allowed. The rule does not force ticket-holders to enter.

### Worked variation: a reversed arrow exposed

Now compare only if with if on an asymmetric row.

<HaskellTryIt>

```haskell
main :: IO ()
main = do
  let passed = False
  let submitted = True
  print (not passed || submitted, not submitted || passed)
```

```text
(True,False)
```

</HaskellTryIt>

'Passed only if submitted' holds: nobody passed without submitting. 'Passed if submitted' fails here because submission did not produce a pass.

### Worked variation: contrapositive check

Now test an equivalent rewrite on every truth pair.

<HaskellTryIt>

```haskell
main :: IO ()
main = print (all (\(p,q) -> (not p || q) == (q || not p)) [(False,False),(False,True),(True,False),(True,True)])
```

```text
True
```

</HaskellTryIt>

The two formulas agree in all four cases. In words, p only if q is equivalent to no q implies no p. A finite truth table is exhaustive for these two Boolean variables.

### Worked variation: a numeric necessary condition

Now only if constrains a label's relationship to a value.

<HaskellTryIt>

```haskell
sound :: Integer -> Bool -> Bool
sound n labelledPositive = not labelledPositive || n > 0
main :: IO ()
main = print (sound 0 True, sound 4 False, sound (-1) False)
```

```text
(False,True,True)
```

</HaskellTryIt>

## 8. If and only if: soundness and completeness

A biconditional requires both directions. 'p if and only if q' says p and q have the same truth value. For a classifier, one direction prevents false positives and the other prevents false negatives. For defined Booleans it can be written as equality.

### Template

```text
iff p q = p == q
iff p q = (not p || q) && (not q || p)
```

The first implication says p only if q. The second says p if q. The mathematical equivalence sign is not Haskell syntax; use == on Bool expressions.

## 9. Exclusive or and exactly one

Exclusive or (XOR) means exactly one assertion holds. Inclusive or permits both; XOR forbids both. For two defined Booleans, inequality expresses XOR. For more than two values, repeated XOR means an odd number of truths, not exactly one overall.

```text
xor p q = p /= q
xor p q = (p || q) && not (p && q)
exactlyOne flags = length (filter id flags) == 1
```

The inequality is on Bool values. The last formula counts truths in a finite list; do not replace it with a fold of XOR for a list of arbitrary length.

## 10. De Morgan laws and negated requirements

Negating a compound requirement changes both its connective and its components. Not both means at least one fails; it does not mean both fail. Not either means neither. This is useful for turning a requirement into a search for a violating input.

### Template

```text
not (p && q) = not p || not q
not (p || q) = not p && not q
not (x < bound) = x >= bound
```

These are equalities of truth values for defined operands. The last line includes equality at the boundary; negating a strict comparison yields a non-strict one for ordinary integers.

## 11. Every: universal quantification

'Every member satisfies P' is a universal statement. On a finite list use all. One counterexample makes it False. If the requirement applies only to members satisfying R, either filter by R first or use implication inside all.

### Template

```text
every P over xs = all P xs = and (map P xs)
every R-member satisfies P = all (\x -> not (R x) || P x) xs
                         = all P (filter R xs)
```

xs is the finite domain and P is a Bool-valued function. Restricted quantification does not require every x to satisfy R; R selects which x owe P.

## 13. None, not every and quantified negation

```text
all P [] = True

none P [] = True
```

## 15. Quantifier order and dependent domains

Nested quantifiers have an order. Every student has some permitted slot allows each student a different witness. Some slot works for every student demands one shared witness. Reordering a comprehension changes enumeration; reordering all and any can change truth.

### Template

```text
for every x in xs, some y in ys: all (\x -> any (R x) ys) xs
some y in ys, for every x in xs: any (\y -> all (\x -> R x y) xs) ys
for every x, some y in choices x: all (\x -> any (R x) (choices x)) xs
```

R x y is the relation being checked. The first existential witness can depend on x; in the second it is chosen before examining x. Dependent choices must be computed for the current x.

### Worked variation: individual witnesses versus one shared witness

Now different members need different matching values.

<HaskellTryIt>


```text
(True,False)
```

</HaskellTryIt>

For x=1 choose 1; for x=2 choose 2. No single y equals both 1 and 2. The witness dependency explains the changed answer.

Now one upper bound works for every member.

```haskell
main = print (all (\x -> any (\y -> x <= y) [2,3 :: Integer]) [1,2], any (\y -> all (\x -> x <= y) [1,2 :: Integer]) [2,3])
```

```text
(True,True)
```

</HaskellTryIt>

The second predicate can choose y=2 for both x values. Agreement in this example does not make the forms generally equivalent.

### Worked variation: empty outer versus empty witness domain

Now emptiness interacts with order.

<HaskellTryIt>

```haskell
main :: IO ()
main = print (all (\x -> any (== x) ([] :: [Integer])) [], any (\y -> all (== y) ([] :: [Integer])) [])
```

```text
(True,False)
```

</HaskellTryIt>

The first all has no x to oblige, so True. The second any has no y to choose, so False, even though its inner all would be True.

### Worked variation: dependent choices

Now each input has its own candidate list.

<HaskellTryIt>

```haskell
choices :: Integer -> [Integer]
choices x = [x,x+1]
main :: IO ()
main = print (all (\x -> any (\y -> y > x) (choices x)) [-1,0,2])
```

```text
True
```

</HaskellTryIt>

Each input x chooses x+1, which is strictly larger. The candidate lists are [ -1,0 ], [0,1] and [2,3]. The witness is explicitly allowed to depend on x.

### Exam question: one examiner or one per student? (6 marks)

Translate 'every student has an available examiner' and 'there is an examiner available for every student', using available student examiner.

<details>
<summary>Worked answer, with the reasoning</summary>

<Steps title="Answering the question">

  <Step title="1. Read the question">

Both contain every and some, but the witness is chosen at a different level.

  </Step>

  <Step title="2. Plan">

Put the first English quantifier on the outside.

  </Step>

  <Step title="3. Solution">

`all (\s -> any (available s) examiners) students` and `any (\e -> all (\s -> available s e) students) examiners`. A shared examiner implies individual availability, but the converse need not hold.

  </Step>

  <Step title="4. Check">

Two students with disjoint singleton examiner choices satisfy the first and fail the second. Check empty lists separately before assuming the shared-to-individual implication; with an empty examiner domain the antecedent is False.

  </Step>

</Steps>

</details>

### Common errors

Swapping all and any can strengthen a requirement. GHC sees both as Bool and gives no error. Repair by naming when a witness is chosen and whether it may depend on the outer variable. Do not accidentally shadow the outer variable in a nested lambda.

### Practice with answers

Does every x having some larger y mean one y is larger than every x in an unbounded integer domain? **Answer:** no. Each x has x+1, but there is no greatest integer. Our runnable examples use finite lists, not an attempted enumeration of all integers.

## 16. Composing contracts and strengthening a precondition

For `f . g`, compatible types are necessary, but g must also return values admitted by f. Under the composite's precondition P, prove that g terminates and that every result permitted by g's postcondition satisfies f's precondition. If this fails, strengthen P, change g's guarantee, or use an explicit safe result.

### Template

```text
g :: A -> B with Pg and Qg
f :: B -> C with Pf and Qf
For P x: establish Pg x
For every b: P x and Qg x b imply Pf b
Composite Q: there exists b with Qg x b and Qf b r
Also establish termination of both calls on these domains
```

Quantifying over every intermediate result matters if a specification permits more than one. Checking one observed output is weaker than proving the postcondition implies the next precondition.

### Worked variation: non-zero denominator produced by construction

Now the earlier result guarantees a later numeric precondition.

<HaskellTryIt>

```haskell
positiveDenominator :: Integer -> Integer
positiveDenominator n = abs n + 1
quotient :: Integer -> Integer
quotient d = 12 `div` d
main :: IO ()
main = print (map (quotient . positiveDenominator) [-2,0,3])
```

```text
[4,12,3]
```

</HaskellTryIt>

abs n + 1 is at least 1, so it satisfies quotient's d /= 0 precondition. For the chosen inputs the denominators are 3,1,4. Integer avoids overflow of abs n + 1.

### Worked variation: filtering does not preserve existence

Now the earlier function can destroy a needed property.

<HaskellTryIt>

```haskell
main :: IO ()
main = print (filter (> 0) [-2,0 :: Integer], not (null (filter (> 0) [-2,0 :: Integer])), not (null (filter (> 0) [-2,3 :: Integer])))
```

```text
([],False,True)
```

</HaskellTryIt>

A non-empty input is insufficient before taking the head of positive results. The correct strengthened precondition is any (>0) xs. The example tests the gate without calling head on [].

### Worked variation: safe composition reports absence

Now the combined contract covers missing intermediates explicitly.

<HaskellTryIt>

```haskell
firstPositive :: [Integer] -> Maybe Integer
firstPositive xs = case filter (> 0) xs of
  [] -> Nothing
  (x:_) -> Just x
main :: IO ()
main = print (firstPositive [-2,0], firstPositive [-2,3,4], firstPositive [])
```

```text
(Nothing,Just 3,Nothing)
```

</HaskellTryIt>

Every finite list is allowed. Q requires the earliest positive member wrapped in Just, or Nothing when none exists. This changes the result type instead of fabricating a first element.

### Worked variation: a weak postcondition cannot establish a strong precondition

Now observed outputs pass but the advertised guarantee is too weak.

<HaskellTryIt>

```haskell
weakGuarantee :: Integer -> Bool
weakGuarantee r = r >= 0
nextPre :: Integer -> Bool
nextPre r = r > 0
main :: IO ()
main = print [(r,weakGuarantee r,nextPre r) | r <- [0,1,2]]
```

```text
[(0,True,False),(1,True,True),(2,True,True)]
```

</HaskellTryIt>

A first contract promising merely r >= 0 permits 0, which violates r > 0. A stronger implementation might never produce 0, but the composition cannot be justified from that weak contract alone.

### Exam question: derive a composite precondition (6 marks)

Given g xs = filter even xs and f = head, derive the weakest precondition for f . g on finite defined integer lists.

<details>
<summary>Worked answer, with the reasoning</summary>

<Steps title="Answering the question">

  <Step title="1. Read the question">

Derive means express exactly when the intermediate value exists.

  </Step>

  <Step title="2. Plan">

head requires a non-empty result; filter even retains exactly the even members.

  </Step>

  <Step title="3. Solution">

The precondition is `any even xs`. It is sufficient because an even member survives filtering, and necessary because with no even member the result is []. The result is the first even element of xs.

  </Step>

  <Step title="4. Check">

[] and [1,3] fail P; [1,2,4] satisfies P and produces 2. A safe alternative returns Maybe rather than inheriting head's restricted domain.

  </Step>

</Steps>

</details>

### Common errors

Type compatibility does not establish value compatibility. The composition can compile and fail later, so there is no compile-time message to quote for the contract error. Repair by proving the intermediate precondition, strengthening the input assumption, or reporting absence. See [Specification Exam Practice](/docs/sem3/csi243/10-reasoning-revision/notes/specification-exam-practice) for ambiguous requirements.

### Practice with answers

g promises its output is even; f requires positive. Is composition justified? **Answer:** no. Zero and negative even outputs satisfy g's promise but violate f's. Require a stronger guarantee or add an explicit validation step.

## Summary

<Callout type="key" title="Remember">

A contract relates an input to an allowed result. Types alone do not enforce numeric domains or intent. Total correctness needs both the right result and termination. Implication forbids only True-to-False; only if gives a necessary condition; iff adds both directions; XOR means exactly one of two. Every uses all, some uses any, and none negates any. Empty universals are True, empty existentials False. Witness order matters. Compose contracts by establishing the next precondition from the preceding guarantee.

</Callout>
