---

Conditional expressions choose on a **Boolean test**. Pattern matching chooses on the **shape of the argument itself** — its literal value, or the structure it was built from.

The result is code that is neater, more readable, and simpler than the equivalent nest of conditionals.

### Naming the parts of a function definition, once and for all

Every pattern-matched function you will see in this course has the same skeleton. Learning to name each piece pays off immediately, because the same names are used to talk about every example from here on:

```haskell
funcName :: InputType -> OutputType     -- Type signature
funcName pattern1 = expression1         -- Equation 1
funcName pattern2 = expression2         -- Equation 2
funcName _        = fallbackExpression  -- Catch-all
```

| Placeholder | What it stands for | An example you have already seen |
|---|---|---|
| `funcName` | The name you give the function | `isZero`, `dayName`, `square` |
| `pattern` | A literal value, a variable, `_`, or a structure (tuple/list/cons) to match the argument against | `0`, `n`, `_`, `(x, _)`, `(x:xs)` |
| `expression` | What the function evaluates to when that equation's pattern matches | `1`, `n * n`, `True` |

Each line of the template above is one **equation** — a complete `funcName pattern = expression` definition. A function is the set of all its equations together, tried in order. This vocabulary — equation, pattern, expression — is not decoration. "Which pattern matched?" and "which equation is this?" are the exact questions you ask when debugging a pattern-matching function that returns the wrong answer, and Section 2 below is built entirely around asking them correctly.

## 1. The idea

Write several equations for the same function. Haskell tries them **in order**, top to bottom, and uses the first one whose pattern matches.

```haskell
-- Negate a Boolean value.
negateBool :: Bool -> Bool
negateBool True  = False
negateBool False = True
```

Line by line:

1. The signature says the function takes a `Bool` and returns a `Bool`.
2. The first equation matches the literal `True`, and returns `False`.
3. The second equation matches the literal `False`, and returns `True`.

```text
ghci> negateBool True
False
ghci> negateBool False
True
```

As a program:

```haskell
main :: IO ()
main = do
  print (negateBool True)
  print (negateBool False)
```

```text
False
True
```

There are only two `Bool` values, so these two patterns cover everything.

<Callout type="info" title="Why patterns instead of nested if">
`negateBool` could be written as `if b then False else True`. For two outcomes that is no worse. But once a decision has three or more *exact* values to distinguish — a day number, a specific character, a specific list shape — pattern matching states each case as its own equation, aligned and independently checkable, where a chain of nested `if`/`else` would drift rightwards with every case added (see the previous lesson, Section 4). Patterns are the right tool exactly when the cases are literal values or structural shapes, not ranges — ranges are what guards, next lesson, are for.
</Callout>

## 2. Matching is sequential, and order matters

Arguments are matched against patterns **in sequence**, and the first equation that applies is used. The compiler starts at the top and takes the first match.

> Always list multiple definitions starting with the **most specific** and proceeding to the **most general**.

```haskell
-- Square a number, but treat 0 as a special case returning 1.
square :: Int -> Int
square 0 = 1     -- most specific: the literal 0
square y = y * y -- most general: a variable matching anything
```

```text
ghci> square 0
1
ghci> square 5
25
```

As a program, adding a negative number to confirm the general equation handles it correctly too:

```haskell
main :: IO ()
main = do
  print (square 0)
  print (square 5)
  print (square (-3))
```

```text
1
25
9
```

<SiteDiagram chart={`flowchart TD
  Start["Call f with an argument"] --> E1{"Matches equation 1's pattern?"}
  E1 -- Yes --> R1["Run equation 1's right-hand side"]
  E1 -- No --> E2{"Matches equation 2's pattern?"}
  E2 -- Yes --> R2["Run equation 2's right-hand side"]
  E2 -- No --> E3{"...more equations..."}
  E3 -- "No pattern matches at all" --> Crash["Non-exhaustive patterns: runtime crash"]`} caption="This is the mechanism behind every equation-based function: try patterns top to bottom, stop at the first match, crash only if none match." />

Reverse those two lines and the function breaks:

```haskell
-- WRONG: the variable pattern swallows every argument.
square y = y * y
square 0 = 1     -- unreachable
```

If a module contained only this reversed version, here is exactly what running it prints:

```haskell
main :: IO ()
main = do
  print (square 0)
  print (square 5)
```

```text
0
25
```

`square 0` would now return `0` — silently wrong, not crashed and not refused. GHC does notice, though, and says so at the exact moment it compiles the file, before you ever call anything:

```text
Pattern.hs:3:1: warning: [-Woverlapping-patterns]
    Pattern match is redundant
    In an equation for `square': square 0 = ...
  |
3 | square 0 = 1
  | ^^^^^^^^^^^^
```

Read this literally: **redundant**, not "wrong" or "unreachable" in so many words, but that is exactly what it means — GHC is telling you that every value `square 0` could ever match is already claimed by an earlier equation, so this one can never fire. It is a warning, not an error — the module still compiles and `square 0` still (wrongly) returns `0` — which is exactly why it is worth turning warnings on and reading them, rather than treating a successful compile as proof the function is right. **A variable pattern matches anything, so nothing below it is ever reached.**

<Callout type="info" title="Naming the parts, precisely">
`_` specifically is called the **wildcard pattern** (Section 3 gives it its own row). A bare name like `y` in `square y = y * y` is a **variable pattern** — it also matches anything, but *binds* what it matches to a name you can use on the right-hand side, unlike `_`, which matches anything and throws the value away. Both are "catch-all" in the sense that neither can ever fail to match; that shared property is exactly why either one, placed too early, swallows every equation below it.
</Callout>

## 3. The kinds of pattern

| Pattern | Matches | Example |
|---|---|---|
| **Literal** | An argument equal to that value | `fac 0 = 1` |
| **Variable** | Any argument at all, binding it to the name | `fac n = n * fac (n - 1)` |
| **Wildcard** `_` | Any argument, without binding a name | `isZero _ = False` |
| **Tuple** | A tuple of the same arity whose components all match | `fst (x, _) = x` |
| **List** | A list of matching structure and length | `stW ['b', _, _] = True` |
| **Cons** `(x:xs)` | A non-empty list, splitting head from tail | `head1 (x:_) = x` |

### The wildcard

`_` is the catch-all. Use it when a position must match but its value is not needed:

```haskell
isZero :: Int -> Bool
isZero 0 = True
isZero _ = False   -- anything else
```

```text
ghci> isZero 0
True
ghci> isZero 7
False
```

```haskell
main :: IO ()
main = do
  print (isZero 0)
  print (isZero 7)
```

```text
True
False
```

Writing `isZero n = False` would work identically, but `_` documents that the value is deliberately ignored, and avoids an unused-name warning.

## 4. Exhaustiveness

A set of patterns is **exhaustive** when every possible argument matches at least one of them. Leaving a gap does not fail at compile time by default — it fails at *run* time, when an unmatched argument arrives:

```haskell
-- Not exhaustive: nothing matches 3.
dayName :: Int -> String
dayName 1 = "Monday"
dayName 2 = "Tuesday"
```

On inputs that do match, it behaves normally:

```haskell
main :: IO ()
main = do
  putStrLn (dayName 1)
  putStrLn (dayName 2)
```

```text
Monday
Tuesday
```

But `dayName` has no equation for `3` or above. Calling it on such an input crashes the whole program, not just that call — best seen directly at the `ghci` prompt rather than guessed at as compiled output:

```text
ghci> dayName 3
*** Exception: Non-exhaustive patterns in function dayName
```

Always finish with a catch-all so the program cannot crash:

```haskell
dayName :: Int -> String
dayName 1 = "Monday"
dayName 2 = "Tuesday"
dayName 3 = "Wednesday"
dayName 4 = "Thursday"
dayName 5 = "Friday"
dayName 6 = "Saturday"
dayName 7 = "Sunday"
dayName _ = "Not a day number"
```

```text
ghci> dayName 3
"Wednesday"
ghci> dayName 9
"Not a day number"
```

```haskell
main :: IO ()
main = do
  putStrLn (dayName 3)
  putStrLn (dayName 9)
  putStrLn (dayName 1)
```

```text
Wednesday
Not a day number
Monday
```

<Callout type="warn" title="-Wincomplete-patterns is a warning, not a rejection">
Start GHCi with `ghci -Wincomplete-patterns`, or enter `:set -Wincomplete-patterns`, and GHC will print a **compile-time warning** that names exactly which patterns are missing — for the two-equation `dayName` above, something like:

```text
dayName.hs:2:1: warning: [-Wincomplete-patterns]
    Pattern match(es) are non-exhaustive
    In an equation for `dayName': Patterns not matched: ...
```

(the precise wording varies by GHC version). This is a **warning, not a rejection**: the module still compiles, and `dayName` is still callable. Crucially, it still **crashes at run time** if the missing case is actually reached — the warning only helps you *notice* the gap while reading the compiler's output, before a user's input finds it for you. Turn it on for laboratory work so gaps are visible while you are still writing the function, not as a substitute for adding the catch-all case.
</Callout>

## 5. Tuple patterns

A tuple of patterns is itself a pattern. It matches any tuple of the same arity whose components all match in order. In plain English: line up the pattern's slots against the tuple's slots one by one, and the whole thing matches only if every slot's own piece matches whatever is sitting in that same slot — [Decoding Exam and Lab Language](/docs/sem3/csi243/decoding-questions) works through several dense definitions exactly this way, one phrase at a time. This is how the Prelude defines `fst` and `snd`:

```haskell
fst :: (a, b) -> a
fst (x, _) = x

snd :: (a, b) -> b
snd (_, x) = x
```

They behave exactly as this definition promises:

```haskell
main :: IO ()
main = do
  print (fst (3, "abc"))
  print (snd (3, "abc"))
```

```text
3
"abc"
```

The pattern destructures the pair and names only the component that is wanted.

```haskell
-- Add the two components of a pair.
addPair :: (Integer, Integer) -> Integer
addPair (x, y) = x + y
```

```text
ghci> addPair (3, 4)
7
```

```haskell
main :: IO ()
main = do
  print (addPair (3, 4))
  print (addPair (-2, 5))
```

```text
7
3
```

### A second tuple example: which axis

A different domain, still tuple and wildcard patterns, no arithmetic needed:

```haskell
-- Classify a 2D point by which axis it lies on.
axisOf :: (Int, Int) -> String
axisOf (0, 0) = "origin"
axisOf (0, _) = "on the y-axis"
axisOf (_, 0) = "on the x-axis"
axisOf (_, _) = "off both axes"
```

```haskell
main :: IO ()
main = do
  putStrLn (axisOf (0, 0))
  putStrLn (axisOf (0, 5))
  putStrLn (axisOf (3, 0))
  putStrLn (axisOf (2, 3))
```

```text
origin
on the y-axis
on the x-axis
off both axes
```

The order is forced exactly as it was for `square`: `(0, 0)` also matches the pattern `(0, _)`, so the literal-tuple case `(0, 0)` must come first, or it would never be reached.

## 6. List patterns

A list of patterns matches a list of the **same length** whose elements match in order:

```haskell
-- True for exactly three characters starting with 'b'.
stW :: [Char] -> Bool
stW ['b', _, _] = True
stW _           = False
```

```text
ghci> stW "bat"
True
ghci> stW "cat"
False
ghci> stW "boat"
False
```

```haskell
main :: IO ()
main = do
  print (stW "bat")
  print (stW "cat")
  print (stW "boat")
```

```text
True
False
False
```

`stW "boat"` is `False` because `"boat"` has four characters — the list pattern `['b', _, _]` only matches lists of exactly three elements.

### The cons pattern

A list is built one element at a time from the empty list `[]` using the `:` operator, called **cons**:

```text
[1,2,3]
= 1 : [2,3]
= 1 : (2 : [3])
= 1 : (2 : (3 : []))
```

So `[1,2,3]` is an abbreviation of `1:(2:(3:[]))`. The cons operator associates to the right.

This gives the most important pattern in Haskell: `(x:xs)` matches a **non-empty** list, binding `x` to the head and `xs` to the tail. It lets the Prelude's basic list functions be defined directly:

```haskell
null :: [a] -> Bool
null []    = True
null (_:_) = False

head :: [a] -> a
head (x:_) = x

tail :: [a] -> [a]
tail (_:xs) = xs
```

```text
ghci> null []
True
ghci> null [1,2,3]
False
ghci> head [5,9,2]
5
ghci> tail [5,9,2]
[9,2]
```

```haskell
main :: IO ()
main = do
  print (null [])
  print (null [1,2,3])
  print (head [5,9,2])
  print (tail [5,9,2])
```

```text
True
False
5
[9,2]
```

`[]` and `(x:xs)` between them cover every possible list, which makes that pair the standard exhaustive split.

<Callout type="warn" title="Cons patterns must be parenthesised">
Function application binds more tightly than any operator, so `tail _:xs = xs` is read as `(tail _):xs = xs` — a different and invalid meaning. Always write `tail (_:xs) = xs`.
</Callout>

### Nested patterns: a pattern can sit inside another pattern

Every pattern in Sections 3–6 above was one level deep — a tuple of variables, or a list of literals. Nothing stops a pattern from nesting a *second* structural pattern inside the first: a tuple inside a cons, a list inside a tuple, and so on, matched all in one go against however many layers the argument actually has.

**Template:**
```haskell
funcName :: (OuterType) -> ResultType
funcName (outerPattern innerPattern) = expression
funcName fallbackPattern             = fallbackExpression
```
Read it exactly the way Section 5's tuple patterns were read, just one layer deeper: line up `outerPattern` against the argument's outer shape, and wherever that outer shape has a "slot," `innerPattern` gets to describe *that slot's own* internal shape, instead of only a bare variable or wildcard.

**Example:**
```haskell
-- Sum the two numbers in the first pair of a list of pairs.
firstPairSum :: [(Int, Int)] -> Int
firstPairSum ((x, y):_) = x + y
firstPairSum []         = 0
```
```text
ghci> firstPairSum [(3,4),(1,1)]
7
ghci> firstPairSum []
0
```
`((x, y):_)` is two patterns nested together: the outer pattern is the familiar cons `(_:_)` from Section 6, splitting a non-empty list into a head and a tail; but where the head would ordinarily be a bare variable, it is instead the tuple pattern `(x, y)` from Section 5, destructuring that head element too. Both layers are matched at once — the list must be non-empty, *and* its first element must be a pair — before `x` and `y` are bound to anything.

**A variation: the nesting the other way round — a list inside a tuple**
```haskell
-- Describe a (list, number) pair by the list's own shape.
describePair :: ([Int], Int) -> String
describePair ([], _)    = "empty list paired with a number"
describePair ((x:_), n) = "list starting with " ++ show x ++ ", paired with " ++ show n
```
```text
ghci> describePair ([], 5)
"empty list paired with a number"
ghci> describePair ([9,2,3], 5)
"list starting with 9, paired with 5"
```
Here the outer pattern is the tuple `(_, _)`, and the *first slot* of that tuple is where the nested pattern lives — either the literal empty list `[]`, or a cons `(x:_)`. Nesting has no preferred direction: Section 5's tuples and Section 6's lists can sit inside each other however the data is actually shaped.

**A variation: nested pattern combined with guards**
```haskell
-- Compare the two numbers in the first pair of a list of pairs.
closestPairFirst :: [(Int, Int)] -> String
closestPairFirst ((x, y):_)
  | x == y    = "first pair is balanced"
  | x > y     = "first pair leans left"
  | otherwise = "first pair leans right"
closestPairFirst [] = "no pairs"
```
```text
ghci> closestPairFirst [(3,3),(1,9)]
"first pair is balanced"
ghci> closestPairFirst [(5,1)]
"first pair leans left"
ghci> closestPairFirst [(1,5)]
"first pair leans right"
ghci> closestPairFirst []
"no pairs"
```
Exactly the same combination the next lesson calls out in full (Guarded Equations, Section 4): the nested pattern `((x, y):_)` selects the equation and destructures two layers deep in one step, and once inside that equation, the guards decide *which* of several results to give based on a range-style comparison (`==`, `>`) that no pattern, nested or otherwise, could express on its own.

## 7. Worked example: recognising a vowel

Specify, then implement.

```text
isVowel :: Char -> Bool
Purpose: report whether a character is a vowel, in either case.
```

```haskell
isVowel :: Char -> Bool
isVowel 'a' = True
isVowel 'e' = True
isVowel 'i' = True
isVowel 'o' = True
isVowel 'u' = True
isVowel 'A' = True
isVowel 'E' = True
isVowel 'I' = True
isVowel 'O' = True
isVowel 'U' = True
isVowel _   = False
```

```text
ghci> isVowel 'a'
True
ghci> isVowel 'A'
True
ghci> isVowel 't'
False
```

```haskell
main :: IO ()
main = do
  print (isVowel 'a')
  print (isVowel 'A')
  print (isVowel 't')
```

```text
True
True
False
```

Ten literal patterns is verbose. This is precisely the shape of decision that guards handle better, and the next lesson rewrites it in two lines. Recognising *which* form suits a decision is the real skill of this chapter.

## 8. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| Variable pattern placed above a literal | The variable matches everything; later equations are unreachable | Put the most specific pattern first |
| No catch-all | `Non-exhaustive patterns` at run time | End with `_`, or cover every constructor |
| `tail _:xs = xs` | Parsed as `(tail _):xs` | Parenthesise: `tail (_:xs)` |
| `f (x:xs)` applied to `[]` | The cons pattern requires at least one element | Add a separate `f [] = …` equation |
| Equations with different arities | Every equation must take the same number of arguments | Make the argument counts agree |
