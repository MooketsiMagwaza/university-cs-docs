Pattern matching chooses on the **shape** of an argument. But many decisions are about a **range** — is the mark above 50, is the number negative, is the value between 13 and 19? A literal pattern cannot express that, and nested conditionals become unreadable.

**Guarded equations** are the answer. A guard is a Boolean expression that tests whether a property of some value holds.

## 1. The form

```haskell
functionName parameters
  | condition1 = result1
  | condition2 = result2
  | otherwise  = defaultResult
```

The rules:

- Start with the function name and its parameters, then **no `=` sign** on that line.
- Move to a new line and use the pipe `|` character to introduce each option.
- Each `|` line is a different option, written as a Boolean expression.
- The last option should catch everything remaining, using the keyword `otherwise`.
- There must be at least two guards; there may be many.

| Placeholder | Stands for | Example |
|---|---|---|
| `functionName` | The function's name | `getSign`, `grade`, `bmiTell` |
| `parameters` | The argument(s), named but with no pattern to match on | `n`, `mark`, `weight height` |
| `condition` | A Boolean test — an expression that evaluates to `True` or `False` | `n < 0`, `mark >= 80` |
| `result` | What the function evaluates to if that guard is the first one to succeed | `-1`, `"A"` |
| `otherwise` | A keyword, not a placeholder — it is literally `True`, used as the final, always-succeeding guard | (written exactly as `otherwise`) |

`otherwise` is worth pausing on: it is not special syntax reserved for this position. It is an ordinary Prelude binding, `otherwise = True`, and it works as the last guard for the same reason `True` would — a guard list is read top to bottom, and the first one that evaluates to `True` wins. Writing `otherwise` instead of `True` is a readability convention, not a language requirement.

<QuizRef src="sem3/csi243/04-making-choices/notes/guards" id="check-what-otherwise-really-is" />

Compare the two forms of the same function:

```haskell
-- With nested conditionals.
getSign :: Integral a => a -> a
getSign n =
  if n < 0 then -1 else
    if n > 0 then 1 else 0

-- With guards: the cases are aligned and readable.
getSign :: Integral a => a -> a
getSign n
  | n < 0     = -1
  | n > 0     = 1
  | otherwise = 0
```

```text
ghci> getSign (-7)
-1
ghci> getSign 0
0
ghci> getSign 42
1
```

The guarded version reads as a table of cases, which is exactly what the specification was.

As a full program that runs all three branches:

```haskell
main :: IO ()
main = do
  print (getSign (-7))
  print (getSign 0)
  print (getSign 42)
```

```text
-1
0
1
```

## 2. Guards are sequential

Options are checked **in the order they are listed**. The first guard that evaluates to `True` supplies the result, and the rest are never examined. Careful ordering is therefore essential — the same discipline as pattern matching.

```haskell
-- Convert a mark to a letter grade.
grade :: Int -> String
grade score
  | score >= 90 = "A"
  | score >= 80 = "B"
  | score >= 70 = "C"
  | otherwise   = "F"
```

```text
ghci> grade 95
"A"
ghci> grade 85
"B"
ghci> grade 42
"F"
```

Wrapped in a program that exercises every letter, including the one the transcript above skips:

```haskell
main :: IO ()
main = do
  putStrLn (grade 95)
  putStrLn (grade 85)
  putStrLn (grade 72)
  putStrLn (grade 42)
```

```text
A
B
C
F
```

Now reverse the order:

```haskell
-- WRONG: every passing mark is caught by the first guard.
grade score
  | score >= 70 = "C"
  | score >= 80 = "B"
  | score >= 90 = "A"
  | otherwise   = "F"
```

Run as a program, this is exactly what happens — no error, no warning, just the wrong answer:

```haskell
main :: IO ()
main = do
  putStrLn (grade 95)
```

```text
C
```

`grade 95` now returns `"C"`, because `95 >= 70` is the first `True` guard. The function compiles and runs; it is simply wrong. **Order the guards from the most restrictive condition to the least.**

### A second example, a different domain

The same discipline — most restrictive condition first — applies wherever ranges are compared, not just to exam marks:

```haskell
-- Classify the physical state of water at standard pressure, by Celsius temperature.
waterState :: Double -> String
waterState temp
  | temp <= 0   = "solid"
  | temp < 100  = "liquid"
  | otherwise   = "gas"
```

```haskell
main :: IO ()
main = do
  putStrLn (waterState (-5))
  putStrLn (waterState 25)
  putStrLn (waterState 100)
```

```text
solid
liquid
gas
```

`waterState 100` falls all the way to `otherwise`: `100 <= 0` is `False`, and `100 < 100` is also `False` (100 is not *less than* 100), so `"gas"` is the only guard left standing.

## 3. `otherwise`

`otherwise` is not special syntax. It is an ordinary name defined in the Prelude as:

```haskell
otherwise :: Bool
otherwise = True
```

Because it is always `True`, a final `| otherwise = …` always matches. That is what makes it the catch-all.

The `otherwise` guard is optional, but it is good practice to have one. Without it, an argument satisfying no guard produces a run-time failure:

```haskell
-- No catch-all.
classify :: Int -> String
classify n
  | n > 0 = "positive"
  | n < 0 = "negative"
```

On inputs that do match a guard, `classify` behaves like any other function:

```haskell
main :: IO ()
main = do
  putStrLn (classify 5)
  putStrLn (classify (-3))
```

```text
positive
negative
```

But `classify` is a **partial function** — it has no guard for zero. Calling it on an input that no guard covers crashes the whole program, not just that one call, which is why this specific case is best seen at the `ghci` prompt rather than guessed at as compiled output:

```text
ghci> classify 0
*** Exception: Non-exhaustive guards in function classify
```

## 4. Guards combine with pattern matching

The two forms are not rivals; an equation can use both. Patterns select the equation, guards then choose among results within it:

```haskell
-- Describe a list by its length and contents.
describe :: [Int] -> String
describe []  = "empty"
describe (x:xs)
  | null xs   = "one element"
  | x > 0     = "starts positive"
  | otherwise = "starts with zero or a negative"
```

```text
ghci> describe []
"empty"
ghci> describe [5]
"one element"
ghci> describe [7, 1, 2]
"starts positive"
ghci> describe [-3, 1]
"starts with zero or a negative"
```

Wrapped in a program that runs all four cases:

```haskell
main :: IO ()
main = do
  putStrLn (describe [])
  putStrLn (describe [5])
  putStrLn (describe [7, 1, 2])
  putStrLn (describe [-3, 1])
```

```text
empty
one element
starts positive
starts with zero or a negative
```

If every guard in an equation fails, matching **falls through to the next equation** rather than failing immediately.

### A variation: a nested pattern selects the equation, guards do the rest

Section 4's `describe` combined a one-level cons pattern with guards. The same combination works just as well when the pattern nests two layers deep — a tuple inside a tuple — which is worth seeing once here, since [Pattern Matching](/docs/sem3/csi243/04-making-choices/notes/pattern-matching#nested-patterns-a-pattern-can-sit-inside-another-pattern) introduces nested patterns properly but pairs them with a list, not with a run of guards this long.

**Template:**
```haskell
funcName (outerPattern innerPattern)
  | condition1 = expression1
  | condition2 = expression2
  | otherwise  = defaultExpression
```

**Example:**
```haskell
-- Classify a rectangle given as two opposite corners.
rectShape :: ((Int, Int), (Int, Int)) -> String
rectShape ((x1, y1), (x2, y2))
  | x1 == x2 && y1 == y2           = "degenerate: both corners the same point"
  | x1 == x2 || y1 == y2           = "degenerate: a straight line, not a rectangle"
  | abs (x2 - x1) == abs (y2 - y1) = "square"
  | otherwise                      = "rectangle"
```
```text
ghci> rectShape ((0,0), (0,0))
"degenerate: both corners the same point"
ghci> rectShape ((0,0), (5,0))
"degenerate: a straight line, not a rectangle"
ghci> rectShape ((0,0), (4,4))
"square"
ghci> rectShape ((0,0), (4,7))
"rectangle"
```
`((x1, y1), (x2, y2))` is one pattern, matched once: a pair of pairs, immediately naming all four coordinates. That single match is what a pattern is *for* — stating the argument's shape. Everything the pattern cannot express — is one corner directly above or beside the other, are the two side lengths equal — is exactly what the four guards below it are for. Notice the same most-restrictive-first discipline as `grade` and `isDiv`: a degenerate rectangle (`x1 == x2 && y1 == y2`) also satisfies the second guard's `||`, so it must be checked first or it would be wrongly reported as merely "a straight line."

## 5. Sharing work with `where`

Guards often test the same calculated value several times. Recomputing it in each guard is wasteful and repetitive. A `where` clause makes definitions local to the whole equation, including all its guards:

```haskell
-- Classify a body mass index calculated from weight and height.
bmiTell :: Double -> Double -> String
bmiTell weight height
  | bmi <= 18.5 = "underweight"
  | bmi <= 25.0 = "normal weight"
  | bmi <= 30.0 = "overweight"
  | otherwise   = "obese"
  where
    bmi = weight / (height ^ 2)
```

```text
ghci> bmiTell 60 1.7
"normal weight"
ghci> bmiTell 100 1.7
"obese"
```

As a program spanning three of the four bands — underweight, normal, and obese:

```haskell
main :: IO ()
main = do
  putStrLn (bmiTell 50 1.7)
  putStrLn (bmiTell 60 1.7)
  putStrLn (bmiTell 100 1.7)
```

```text
underweight
normal weight
obese
```

`bmi` is computed once and is visible to every guard and every result in that equation. It is not visible outside it.

A `where` clause may define several names, and even local functions:

```haskell
-- Report the area and perimeter of a rectangle as a labelled string.
rectangleReport :: Double -> Double -> String
rectangleReport len wid
  | isSquare  = "Square with area " ++ show area
  | otherwise = "Rectangle with area " ++ show area ++ " and perimeter " ++ show perimeter
  where
    area      = len * wid
    perimeter = 2 * (len + wid)
    isSquare  = len == wid
```

```text
ghci> rectangleReport 4 4
"Square with area 16.0"
ghci> rectangleReport 4 6
"Rectangle with area 24.0 and perimeter 20.0"
```

As a program:

```haskell
main :: IO ()
main = do
  putStrLn (rectangleReport 4 4)
  putStrLn (rectangleReport 4 6)
```

```text
Square with area 16.0
Rectangle with area 24.0 and perimeter 20.0
```

<Callout type="warn" title="Indentation carries meaning">
The `where` keyword and its definitions must be indented **to the right of the start of the equation** they belong to, and the definitions must be aligned with each other. Mixing tabs and spaces very often causes compiler errors. Use spaces only.
</Callout>

### `where` versus `let`

Both introduce local definitions, but they attach to different things:

## 6. Rewriting the vowel test

The previous lesson needed eleven equations. One guard does it:

```haskell
import Data.Char (toLower)

-- Report whether a character is a vowel, in either case.
isVowel :: Char -> Bool
isVowel c = toLower c `elem` "aeiou"
```

```text
ghci> isVowel 'a'
True
ghci> isVowel 'E'
True
ghci> isVowel 'z'
False
```

```haskell
main :: IO ()
main = do
  print (isVowel 'a')
  print (isVowel 'E')
  print (isVowel 'z')
```

```text
True
True
False
```

Or, staying with guards and no import:

```haskell
isVowel :: Char -> Bool
isVowel c
  | c `elem` "aeiou" = True
  | c `elem` "AEIOU" = True
  | otherwise        = False
```

```text
ghci> isVowel 'a'
True
ghci> isVowel 'A'
True
ghci> isVowel 'x'
False
```

```haskell
main :: IO ()
main = do
  print (isVowel 'a')
  print (isVowel 'A')
  print (isVowel 'x')
```

```text
True
True
False
```

### What the backticks actually do

`elem` is an ordinary function, applied like any other: `elem x ys` asks whether `x` occurs in the list `ys`, exactly the way `isDigitChar character` applies `isDigitChar` to `character`. Wrapping a **two-argument** function's name in backticks does not change what it computes — it only changes *where you write the arguments*, turning a **prefix** function (name first, both arguments after) into an **infix** operator (name written between its two arguments):

```text
ghci> elem 'a' "aeiou"
True
ghci> 'a' `elem` "aeiou"
True
```

Both lines call the exact same function on the exact same two arguments, in the exact same order — `elem 'a' "aeiou"` and `` 'a' `elem` "aeiou" `` are two spellings of one call, mechanically:

```text
elem x ys   =====>   x `elem` ys
```

Take the function name that sat *before* both arguments, and move it to sit *between* them, wrapped in backticks. Nothing else changes. The backtick form exists purely because `` c `elem` "aeiou" `` reads closer to the English sentence "c is an element of aeiou" than `elem c "aeiou"` does. Any two-argument function can be made infix this way. Chapter 7 explores the reverse direction — turning an infix operator such as `+` into an ordinary prefix function by parenthesising it, `(+)`.

## 7. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| `f n = \| n > 0 = 1` | An `=` was written before the guards | Remove it: `f n` then the guard lines |
| Guards ordered least-restrictive first | An early guard captures cases meant for a later one | Order from most restrictive to least |
| No `otherwise` | `Non-exhaustive guards` at run time | Add `\| otherwise = …` |
| `otherwise` placed above other guards | It is always `True`, so nothing below runs | Put `otherwise` last |
| `where` aligned with the function name | Layout error | Indent `where` past the start of the equation |
| A guard returning a different type | All results must share one type | Make every result the same type |

## 8. Practice

Write each function with guards, then test the boundary values.

1. `isEven` returning `"The number is even"` or `"The number is odd"`.
2. `bothEven m n` returning `2`, `1`, or `0`.
3. `maxThree x y z` returning the largest of three integers.
4. `areSorted x y z` returning `True` when the three are in strictly ascending or strictly descending order.
5. `isDiv m n`, which reports whether `m` is divisible by `n`, but only when `m > n`. It must report the equal case and the `m < n` case separately.

<Accordion title="Check question 5">

```haskell
-- Report the divisibility of m by n, requiring m to exceed n.
isDiv :: Int -> Int -> String
isDiv m n
  | m == n         = "m and n are equal"
  | m < n          = "m should be greater than n"
  | m `mod` n == 0 = "Yes, m is divisible by n"
  | otherwise      = "No, m is not divisible by n"
```

The order is forced by the specification. Both `m == n` and `m < n` must be tested *before* the divisibility test, because `mod` would otherwise report a true but unwanted answer for equal values — and would divide by zero if `n` were `0`. Guards let you state those preconditions as ordinary readable lines.

As a program exercising all four branches:

```haskell
main :: IO ()
main = do
  putStrLn (isDiv 8 4)
  putStrLn (isDiv 8 3)
  putStrLn (isDiv 3 8)
  putStrLn (isDiv 4 4)
```

```text
Yes, m is divisible by n
No, m is not divisible by n
m should be greater than n
m and n are equal
```
