Most functions treat some inputs differently from others. The most direct way to express that in Haskell is the **conditional expression**:

```haskell
if condition then resultWhenTrue else resultWhenFalse
```

You met this briefly in Chapter 2. This lesson makes it precise.

| Placeholder | Stands for | Example |
|---|---|---|
| `condition` | A Boolean expression — must evaluate to `True` or `False`, nothing else | `mark >= 50`, `n < 0` |
| `then` / `else` | Keywords marking the two branches; both are compulsory | (written exactly as `then` and `else`) |
| `resultWhenTrue` | The value the whole expression takes if `condition` is `True` | `"Pass"`, `1` |
| `resultWhenFalse` | The value the whole expression takes if `condition` is `False` | `"Fail"`, `-1` |

Both branches must produce a value of the **same type** — `resultWhenTrue` and `resultWhenFalse` cannot be a `String` and an `Int` respectively, because the whole `if...then...else` needs exactly one type, decided before either branch is known to run. Try it, and GHC refuses before anything executes:

```haskell
bad :: Double -> String
bad mark = if mark >= 50 then "Pass" else 0
```

```text
BranchType.hs:2:43: error:
    * No instance for (Num String) arising from the literal `0'
    * In the expression: 0
      In the expression: if mark >= 50 then "Pass" else 0
```

GHC's complaint is about the `0`, not the `if`: it needs a `String` in that position (to match `"Pass"`'s branch), and a bare numeric literal has no `String` reading. This is rejected at compile time, before `mark` is ever supplied — the same discipline Chapter 3 introduced for type errors generally.

## 1. It is an expression, not a statement

In Java, C, and Python, `if` is a **statement**: it tells the machine to take a branch. It may exist without an `else`, because it does not have to produce anything.

In Haskell, `if` is an **expression**. It has a value, and therefore it has a type. This single fact explains every rule that follows.

```haskell
-- The whole expression evaluates to a String.
resultLabel :: Double -> String
resultLabel mark = if mark >= 50 then "Pass" else "Fail"
```

```text
ghci> resultLabel 64
"Pass"
ghci> resultLabel 49.5
"Fail"
```

As a complete program, calling it on a clear pass, a clear fail, and the boundary itself:

```haskell
main :: IO ()
main = do
  putStrLn (resultLabel 64)
  putStrLn (resultLabel 49.5)
  putStrLn (resultLabel 50)
```

```text
Pass
Fail
Pass
```

`resultLabel 50` takes the `then` branch: `50 >= 50` is `True`, so the boundary mark itself passes.

## 2. Why the `else` is compulsory

Ask what `if 3 > 5 then "yes"` would evaluate to. The condition is `False`, so there is no result — but the expression was supposed to *have* a value. Haskell rejects it before evaluation:

```text
ghci> if 3 > 5 then "yes"
<interactive>:1:1: error: ... parse error ...
```

Two rules follow, and both are enforced by the type checker:

1. **Every `if` must have an `else`.**
2. **Both branches must have the same type.** The whole expression has one type, so the two branches cannot disagree.

```haskell
-- Rejected: the branches have different types.
-- if n > 0 then "positive" else 0
```

<Callout type="warn" title="The condition must be Bool">
`if 1 then "a" else "b"` is rejected too. Haskell does not treat non-zero numbers as truth. The condition must have type `Bool`.
</Callout>

## 3. A worked example: the sign of an integer

Specify first. `getSign` maps an integer to `1`, `0`, or `-1`:

```text
getSign n = |  1   if n > 0
            |  0   if n = 0
            | -1   otherwise
```

Three outcomes, one Boolean test each — so we nest conditionals, using the `else` of one as the home of the next:

```haskell
getSign :: Integral a => a -> a
getSign n =
  if n < 0
    then -1
    else if n > 0
      then 1
      else 0
```

```text
ghci> getSign (-7)
-1
ghci> getSign 0
0
ghci> getSign 42
1
```

As a program that runs all three cases and prints what each one produces:

```haskell
main :: IO ()
main = do
  print (getSign (-7))
  print (getSign 0)
  print (getSign 42)
```

```text
-1
0
1
```

## 4. Nesting works, but it does not scale

Conditional expressions are exactly right for **two** outcomes. Beyond that they grow awkward:

```haskell
-- Correct, but already hard to scan.
grade :: Int -> String
grade score =
  if score >= 90
    then "A"
    else if score >= 80
      then "B"
      else if score >= 70
        then "C"
        else "F"
```

```text
ghci> grade 95
"A"
ghci> grade 85
"B"
ghci> grade 42
"F"
```

Wrapped in a program that exercises all four letter grades, so every branch is actually reached at least once:

```haskell
main :: IO ()
main = do
  putStrLn (grade 95)
  putStrLn (grade 85)
  putStrLn (grade 72)
  putStrLn (grade 42)
```

```text
A
B
C
F
```

The problems compound as cases are added:

- The conditions drift rightwards, so the shape of the decision is hidden by indentation.
- Every case after the first is buried inside the previous `else`.
- Adding a case in the middle means re-indenting everything below it.
- A missing `else` deep in the chain produces a parse error far from its cause.

### A second domain, the same problem

Nesting's cost has nothing to do with exam marks specifically — any decision with more than two outcomes runs into it. A shipping calculator that prices a package by its weight band shows the identical shape:

```haskell
-- Price a package by weight, in nested if...then...else.
shippingCost :: Double -> Double
shippingCost weight =
  if weight <= 1
    then 5.00
    else if weight <= 5
      then 12.50
      else if weight <= 20
        then 25.00
        else 45.00
```

```haskell
main :: IO ()
main = do
  print (shippingCost 0.5)
  print (shippingCost 3)
  print (shippingCost 20)
  print (shippingCost 25)
```

```text
5.0
12.5
25.0
45.0
```

Four independent weight bands, buried three `else`s deep — the same rightward drift as `grade`, in a domain with nothing to do with exam marks. The problem is structural, not topical.

The remaining lessons in this chapter introduce three forms that express the same decisions without the drift. Guards, in particular, rewrite `grade` as four aligned lines.

<Callout type="info" title="Not a rule against if">
`if … then … else` remains the clearest form for a genuine two-way decision. Prefer it there. The advice is only against deep nesting.
</Callout>

## 5. Indentation

Haskell uses layout to decide what belongs to what. When a conditional spans several lines, indent `then` and `else` consistently beneath the condition:

```haskell
-- Clear.
absoluteValue :: Integer -> Integer
absoluteValue n =
  if n < 0
    then -n
    else n
```

Exercising both branches:

```haskell
main :: IO ()
main = do
  print (absoluteValue (-5))
  print (absoluteValue 0)
  print (absoluteValue 5)
```

```text
5
0
5
```

Mixing tabs and spaces very often causes compiler errors. Use spaces only.

## 6. Common errors

| Attempt | What Haskell reports | Repair |
|---|---|---|
| `if n > 0 then "yes"` | Parse error | Add an `else` branch |
| `if n > 0 then "yes" else 0` | Couldn't match type `[Char]` with a numeric type | Make both branches the same type |
| `if n then 1 else 0` where `n :: Int` | Couldn't match expected type `Bool` | Write an actual comparison, e.g. `n /= 0` |
| `if n > 0 then 1 else if n < 0 then -1` | Parse error | The inner `if` also needs its own `else` |
| Misaligned `then` / `else` | Parse error on input `else` | Indent both consistently under the condition |

```haskell
-- Return how many of the two arguments are even.
bothEven :: Integer -> Integer -> Integer
bothEven m n =
  if even m && even n
    then 2
    else if even m || even n
      then 1
      else 0
```

Order matters here. Testing `even m || even n` first would report `1` for two even numbers, because that condition is also true of them. The most specific case must be tested first — a rule that returns in every form in this chapter.
