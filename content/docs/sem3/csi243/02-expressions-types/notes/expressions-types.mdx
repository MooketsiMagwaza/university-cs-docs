Haskell checks whether an expression is meaningful before evaluating it. This catches many mistakes before the program runs.

## The two questions to ask

Whenever you see an expression, ask:

1. **Is it well typed?** Do the function and operator inputs agree with the supplied values?
2. **If it is well typed, what value does it produce?**

Do not jump directly to arithmetic. A type error prevents evaluation.

## Reading a type signature

```haskell
square :: Integer -> Integer
square number = number * number
```

Read the signature as: “`square` has type integer to integer.” It accepts one `Integer` and returns one `Integer`.

```text
ghci> :type square
square :: Integer -> Integer
ghci> square 6
36
```

The signature is a contract. GHC checks whether the implementation obeys it.

## Reading `->` in a function's type, from scratch

Every signature so far has had exactly one `->`. Before signatures get any bigger, it is worth being completely explicit about what that arrow means, because it is the single most-used piece of notation in this course.

**The plain-English gloss:** read `A -> B` as *"takes a(n) `A`, and gives back a(n) `B`."*

```haskell
square :: Integer -> Integer
```

Read strictly left to right, one arrow at a time: "`square` takes an `Integer`, and gives back an `Integer`." That is the entire signature — nothing is hidden, nothing is implied beyond what is written.

<SiteDiagram chart={`flowchart LR
  A[Integer] -->|square| B[Integer]`} caption="One arrow, one input, one output: square consumes an Integer and produces an Integer. The arrow names the function that connects them." />

A signature with only one `->` is as simple as this notation gets. Real functions often need more than one input, which means more than one arrow — and the reading rule does not change, it just gets applied more than once.

<StepByStep>
  <StepByStepTitle>Reading a two-arrow signature, one arrow at a time</StepByStepTitle>

  <Step number={1}>
  Start with the full signature: `rectangleArea :: Integer -> Integer -> Integer`.
  </Step>

  <Step number={2}>
  Apply the gloss to the **first** arrow only, treating everything after it as one block: "`rectangleArea` takes an `Integer`, and gives back `[an Integer -> Integer]`."
  </Step>

  <Step number={3}>
  Look at that bracketed block on its own: `Integer -> Integer` is itself a function type — one input, one output. Apply the same gloss to it: "which takes an `Integer`, and gives back an `Integer`."
  </Step>

  <Step number={4}>
  Put the two readings together: `rectangleArea` takes an `Integer`, and gives back something that itself takes an `Integer` and gives back an `Integer`. For everyday use, that chains into: "give `rectangleArea` an `Integer` and an `Integer`, and it gives back an `Integer`."
  </Step>
</StepByStep>

```haskell
rectangleArea :: Integer -> Integer -> Integer
rectangleArea width height = width * height
```

```text
ghci> :type rectangleArea
rectangleArea :: Integer -> Integer -> Integer
ghci> rectangleArea 5 3
15
```

A third signature, with one more arrow again, reads exactly the same way — left to right, one arrow consumed at a time:

```haskell
volume :: Integer -> Integer -> Integer -> Integer
volume length width height = length * width * height
```

Read `Integer -> Integer -> Integer -> Integer` as: "`volume` takes an `Integer`, and gives back [something that takes an `Integer`, and gives back [something that takes an `Integer`, and gives back an `Integer`]]." Chained into an everyday reading: "give `volume` three `Integer`s, and it gives back an `Integer`."

```text
ghci> :type volume
volume :: Integer -> Integer -> Integer -> Integer
ghci> volume 2 3 4
24
```

| Signature | Arrow count | Everyday reading |
|---|---|---|
| `square :: Integer -> Integer` | 1 | Takes an `Integer`, gives back an `Integer` |
| `rectangleArea :: Integer -> Integer -> Integer` | 2 | Takes two `Integer`s, gives back an `Integer` |
| `volume :: Integer -> Integer -> Integer -> Integer` | 3 | Takes three `Integer`s, gives back an `Integer` |

What is *really* happening when there is more than one arrow — that `Integer -> Integer -> Integer` is secretly `Integer -> (Integer -> Integer)`, a function that takes one `Integer` and returns *another function* rather than taking two `Integer`s at once — is the subject of Chapter 7's lesson on currying. Nothing on this page is wrong; it simply is not yet the complete picture. Bracket-by-bracket reading like Step 3 above is already a preview of exactly that idea.
</Callout>

### The reading template, formalised — plus two variations not shown above

Everything above is one template, applied at three different lengths. Written out explicitly, with placeholder names instead of `square`/`rectangleArea`/`volume`:

**Template:**
```haskell
name :: Type1 -> Type2 -> ResultType
name arg1 arg2 = expression
```
`name` is whatever the function is called. Every `TypeN` before the *last* arrow is one argument's type, consumed strictly left to right. The type after the final arrow — `ResultType` — is what comes back. `square`, `rectangleArea`, and `volume` earlier on this page are this exact template with one, two, and three `TypeN` slots; the template's *shape* never changes as arrows are added, only its *length* does.

**Example:**
```haskell
initials :: String -> String -> String
initials firstName lastName = [head firstName, head lastName]
```
```text
ghci> initials "Naledi" "Mokoena"
"NM"
```
Two `String` arguments consumed in order, matching `Type1` and `Type2`; the result is a `String` too. Nothing in the template requires the result type to differ from the argument types — `ResultType` is just whichever type the body actually produces.

**A variation: arity zero — a signature with no arrow at all**
```haskell
courseCode :: String
courseCode = "CSI243"
```
```text
ghci> courseCode
"CSI243"
```
When a name has no arrow, the template `Type1 -> Type2 -> ResultType` collapses to just `ResultType` on its own — there is no first arrow, so there is nothing before it to be an argument. This is exactly what a bound constant's signature looks like; it is the same template with zero `TypeN` slots, not a different kind of thing needing new notation.

**A variation: the result is `String` — which is `[Char]` underneath**
```haskell
firstChar :: String -> Char
firstChar word = head word
```
```text
ghci> firstChar "Haskell"
'H'
```
`String` is a type synonym for `[Char]` — a list of characters ([Chapter 6](/docs/sem3/csi243/06-lists-tuples/notes/lists) covers lists properly). The arrow-reading rule does not notice or care that one side happens to be a list of characters instead of `Integer` or `Bool`: `firstChar :: String -> Char` reads exactly the way `square :: Integer -> Integer` did — "takes a `String`, gives back a `Char`." The two are the same type, just written two different ways, and GHCi agrees:
```text
ghci> :type "Haskell"
"Haskell" :: String
ghci> :type ['H','a','s','k','e','l','l']
['H','a','s','k','e','l','l'] :: [Char]
```

## Basic types

| Type | Meaning | Examples | Important distinction |
|---|---|---|---|
| `Int` | Fixed-width whole number | `0`, `42`, `-8` | Bounded; usually faster for machine-sized work |
| `Integer` | Arbitrary-precision whole number | `0`, `42`, a very large factorial | Grows as needed until memory is exhausted |
| `Float` | Single-precision floating point | `2.5` | Approximate, less precise than `Double` |
| `Double` | Double-precision floating point | `2.5` | Common default for approximate real-number calculations |
| `Bool` | Logical truth value | `True`, `False` | Constructors begin with capitals |
| `Char` | One character | `'A'`, `'7'`, `' '` | Single quotes |
| `String` | A list of characters | `"A"`, `"CSI243"` | Double quotes; equivalent to `[Char]` |

## `Int` versus `Integer`

Use `Int` when interoperability, indexes, or bounded machine integers are appropriate. Use `Integer` for beginner arithmetic where overflow should not silently limit the mathematical result.

```haskell
factorialResult :: Integer
factorialResult = product [1..50]
```

The same annotation as `Int` can overflow because `Int` has a maximum and minimum value.

## Whole-number division versus fractional division

```text
ghci> 7 `div` 2
3
ghci> 7 / 2
3.5
```

`div` works with integral values. `/` requires a fractional type.

```text
ghci> :type div
div :: Integral a => a -> a -> a
ghci> :type (/)
(/) :: Fractional a => a -> a -> a
```

The text before `=>` is a typeclass constraint. For now, read `Integral a =>` as “for any whole-number type `a`” and `Fractional a =>` as “for any fractional type `a`.”

### A first taste of operator sections

Sometimes what you want is not "divide 9 by 2" but "the function that divides *some* number by 2" — for instance, to use later or pass elsewhere. Wrapping an operator in parentheses with only one side filled in makes exactly that function. This is called a **section**, and Chapter 7 gives it a full treatment; for now, just recognise the shape.

```text
ghci> (+1) 5
6
ghci> (`div` 2) 9
4
ghci> (*3) 4
12
```

Read each one as "the operator, with one side already supplied": `(+1)` is "add 1"; `` (`div` 2) `` is "divide by 2" (the backticks turn `div` into an operator first, exactly as seen above); `(*3)` is "multiply by 3." Each is a complete, one-argument function — nothing here is evaluated yet until it is applied to an argument, exactly like any other function.

<Callout type="info" title="Not the whole story yet">
Sections can be built from either side of an operator, and one operator — `(-)` — does not section the way you would expect. Chapter 7's lesson on currying and sections covers both in full, including that trap. For now, recognise `(op value)` and `(value op)` as functions, not as errors.
</Callout>

## Boolean expressions

```haskell
isTeenager :: Integer -> Bool
isTeenager age = age >= 13 && age <= 19
```

Trace `isTeenager 16`:

```text
16 >= 13 && 16 <= 19
= True && True
= True
```

Useful operators:

| Operator | Meaning |
|---|---|
| `==` | equal |
| `/=` | not equal |
| `<`, `<=`, `>`, `>=` | ordering comparisons |
| `&&` | logical and |
| <code>&#124;&#124;</code> | logical or |
| `not` | logical negation |

## Characters and strings

```text
ghci> :type 'A'
'A' :: Char
ghci> :type "A"
"A" :: String
ghci> 'A' == "A"
```

The final expression fails because `Char` and `[Char]` are different types. A character is one value; a string is a list, even when the list contains one character.

Concatenate strings with `++`:

```haskell
courseLabel :: String -> String
courseLabel code = "Course: " ++ code
```

```text
ghci> courseLabel "CSI243"
"Course: CSI243"
```

## Lists

A list contains zero or more values of the same element type.

```haskell
scores :: [Integer]
scores = [72, 68, 91]
```

Valid:

```haskell
[1, 2, 3]       -- [Integer]
['a', 'b']      -- [Char]
[True, False]   -- [Bool]
```

Invalid:

```haskell
[1, 'a', True]
```

Haskell cannot choose one element type that makes an integer, a character, and a Boolean the same kind of value.

## Tuples

A tuple has a fixed number of positions, and the positions may have different types.

```haskell
student :: (String, Integer, Bool)
student = ("Kago", 2026001, True)
```

The tuple type records the type of each position. `(String, Integer)` and `(Integer, String)` are different types.

### List versus tuple

| Question | List | Tuple |
|---|---|---|
| Length | May vary | Fixed by its type |
| Element types | One shared type | Each position can differ |
| Typical use | A collection of similar items | One record-like group or multiple return values |
| Delimiters | Square brackets | Parentheses |

## Function application and precedence

Function application uses spaces and binds more tightly than ordinary operators.

```haskell
square 3 + 4
```

This means:

```haskell
(square 3) + 4
```

It does not mean:

```haskell
square (3 + 4)
```

Parentheses communicate the second intention explicitly.

## A mechanical type-checking method

Consider:

```haskell
not (3 < 5)
```

1. `3` and `5` are compatible numeric values.
2. `(<)` compares compatible ordered values and returns `Bool`.
3. Therefore `3 < 5 :: Bool`.
4. `not :: Bool -> Bool`, so it accepts that result.
5. `3 < 5` evaluates to `True`.
6. `not True` evaluates to `False`.

Now consider:

```haskell
not 3
```

`not` requires `Bool`, but `3` is numeric. The expression is rejected before evaluation.

## Type inference

You do not need to annotate every expression. GHC infers types by collecting constraints from how values are used.

```haskell
add x y = x + y
```

Because `(+)` requires a numeric type, GHC infers a constrained numeric signature similar to:

```haskell
add :: Num a => a -> a -> a
```

For course work, write explicit signatures. They document intent and expose mistakes near their cause.

### Why `2 + 3` shows `5` with no signature in sight

Type this at the prompt with nothing defined beforehand:

```text
ghci> :type 2 + 3
2 + 3 :: Num a => a
ghci> 2 + 3
5
ghci> :type it
it :: Integer
```

`:type` alone reports the *general* inferred type, `Num a => a` — "some numeric type, not yet pinned down." Nothing so far forces a specific choice. But the moment you actually **evaluate** `2 + 3` at the prompt, GHCi has to show you a concrete value, and showing a value requires a concrete type. Haskell resolves this with its **defaulting rule**: when an ambiguous numeric type is otherwise unconstrained, GHC tries `Integer` first. `Integer` satisfies `Num`, so that is what `2 + 3` becomes — which is why `:type it` reports `it :: Integer` right after.

Decimals tell a different story, because a literal containing a `.` needs `Fractional`, not just `Num`:

```text
ghci> :type 2.5
2.5 :: Fractional a => a
ghci> 2.5
2.5
ghci> :type it
it :: Double
```

`Integer` is a whole-number type — it does **not** satisfy `Fractional` — so the defaulting rule moves on to the next candidate, `Double`, which does. That is the entire reason `2 + 3` defaults to `Integer` while `2.5` defaults to `Double`: the constraint left over after inference determines which candidate type the rule is allowed to pick.

<Callout type="info" title="Why this matters in practice">
Defaulting is a convenience for the GHCi prompt, not a design tool. In a saved program, an explicit type signature (as this course requires) removes the ambiguity before defaulting is ever needed, and the concrete type comes from your signature instead of from a fallback rule.
</Callout>

## Static typing and lazy evaluation are different ideas

The phrase “Haskell is lazily typed” mixes up two independent questions:

1. **When are types checked?** Haskell is **statically typed**: GHC checks types before the program executes.
2. **When are values calculated?** Haskell is **lazily evaluated** (more precisely, non-strict): an expression is normally calculated only when its result is demanded.

| Axis | Haskell's choice | Meaning |
|---|---|---|
| Type checking | Static | An ill-typed program is rejected before `main` runs |
| Type annotations | Often inferred | You may omit many signatures because GHC can infer them; this is still static typing |
| Value evaluation | Lazy / non-strict | A well-typed expression may remain unevaluated until another expression needs its value |

### Type inference is not lazy typing

When GHC infers the type of `double x = x * 2`, it is not postponing type checking until `double` is called. It solves the type constraints while compiling or loading the definition and concludes that `double` needs a numeric input and produces the same numeric type. Inference changes who *writes* the type—the compiler instead of the programmer—not *when* the type is checked.

This program is rejected even though the bad branch would never be selected:

```haskell
bad = if True then 1 else "not a number"
```

The condition's value is clearly `True`, but both branches belong to one `if` expression and must have one shared type. Static type checking examines the whole expression before evaluation; laziness does not provide an escape hatch around the type system.

### What lazy evaluation postpones

Consider:

```haskell
first :: a -> b -> a
first x _ = x

answer = first 3 (10 `div` 0)
```

`answer` evaluates to `3`. The second argument is well typed, but calculating it would cause division by zero. `first` never uses that argument—the wildcard says its value is irrelevant—so lazy evaluation never demands the division and it is never performed.

This does **not** mean the second argument has no type. GHC still checks that `(10 `div` 0)` is a valid numeric expression. Laziness postpones or avoids its **value calculation**, not its **type checking**.

### Thunks: a useful beginner mental model

An expression that has been defined but not yet evaluated can be pictured as a **thunk**: a suspended recipe together with the environment needed to run it. If the value is demanded, Haskell evaluates the thunk and normally remembers the result so later demands can reuse it. This behaviour is called **sharing**; it prevents the same named computation from being repeated every time it is read.

Do not imagine that Haskell eagerly constructs an infinite object in memory. For `[1..]`, it can construct the first list cell—`1` and a suspended recipe for the rest—without constructing the rest. Then:

```haskell
take 5 [1..]
```

demands only enough of the range to produce five cells. After `[1,2,3,4,5]` has been produced, `take 0 _ = []` stops demanding the tail, so the unbounded remainder is never generated.

### Demand determines how far evaluation goes

Different consumers demand different amounts:

| Expression | What it demands |
|---|---|
| `head [1..]` | Only the first list cell |
| `take 5 [1..]` | The first five cells |
| `length [1..]` | Every cell, so it never finishes |
| `print [1..]` | More cells forever because printing the complete list never reaches an end |

Laziness is therefore powerful but not magic. A finite consumer can use a finite prefix of an infinite producer. A consumer that needs the complete infinite structure still diverges.

### The four combinations are conceptually possible

Typing strategy and evaluation strategy are separate axes. A language may be statically typed and strict, dynamically typed and strict, statically typed and lazy, or dynamically typed and lazy. Haskell's combination is **static typing plus lazy evaluation**. The precise sentence to use in an exam is:

> Haskell checks types before execution, but evaluates well-typed expressions only when their values are demanded.

## Common errors

| Error pattern | Likely cause | Repair question |
|---|---|---|
| “Couldn't match expected type `Bool` with actual type `Int`” | A number was supplied where a condition was required | Which subexpression must produce `Bool`? |
| “No instance for `Num Char`” | Arithmetic was attempted on a character | Should the input be parsed or compared instead? |
| “Ambiguous type variable” | GHC lacks enough context to choose a concrete type | Would a signature or annotation express the intended type? |
| Parse error near `-` | A negative literal follows an operator without grouping | Should the negative value be parenthesized? |

### A real error, in full

The table above summarises error *patterns*. Here is what GHC actually prints for the first row, verbatim, so the shape stops being a mystery the first time you meet it for real. Given this file:

```haskell
-- Score.hs
addBonus :: Integer -> Integer
addBonus n = n + "5"
```

Loading it produces:

```text
ghci> :load Score.hs
[1 of 1] Compiling Main             ( Score.hs, interpreted )

Score.hs:3:19: error: [GHC-83865]
    • Couldn't match expected type: Integer
                  with actual type: [Char]
    • In the second argument of ‘(+)’, namely ‘"5"’
      In the expression: n + "5"
      In an equation for ‘addBonus’: addBonus n = n + "5"
  |
3 | addBonus n = n + "5"
  |                   ^^^
Failed, no modules loaded.
```

Read it from the top down, the way GHC intends:

1. **`Score.hs:3:19`** — the file, line, and column where the problem starts. Column 19 is exactly where `"5"` begins.
2. **`Couldn't match expected type: Integer with actual type: [Char]`** — the two-line heart of the error. `n + "5"` needs its second argument to be `Integer` (because `n :: Integer` and `(+)` needs both sides to agree), but `"5"` is text — `[Char]`, Haskell's internal name for `String`.
3. **`In the second argument of ‘(+)’, namely ‘"5"’`** — names the exact subexpression that is wrong: not the whole line, specifically `"5"`, and specifically its position as the second argument to `+`.
4. **`In the expression: n + "5"`** — zooms out one level, to the smallest surrounding expression.
5. **`In an equation for ‘addBonus’`** — zooms out again, to the whole definition the error occurred inside.
6. **The `|` gutter** — echoes the actual source line, with `^^^` pointing at the exact span GHC is blaming.

Nothing here says what to do about it — GHC diagnoses, it does not repair. The fix, using the "repair question" column above, is to ask what `"5"` should have been: almost certainly the number `5`, not the text `"5"`.
