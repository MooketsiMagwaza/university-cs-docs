## 1. Design before code

First write the purpose and result type. Then partition the input into stopping and continuing cases. Removing a head decreases the length of a finite list; a count supplies another stopping condition. The finite-input assumption matters: consuming tails does not guarantee reaching an end on an infinite list.

```text
Purpose and policy: what happens at every boundary?
Signature:          scalar, list, pair or safe optional result?
Base cases:         empty; possibly singleton, zero count or first failure
Step:               inspect head(s), contribute something, solve smaller input
Dry run:            substitute one defining equation at a time and name it
Tests:              a representative of every boundary and guard outcome
```

Read the concrete templates below as instances of that plan. To adapt one, change the purpose and type first, then the base and contribution. A different predicate can change the promised result even though the code has the same shape.

| Result needed | Contribution of a matching head | Stopping answer |
|---|---|---|
| Count | add one | 0 |
| Conditional sum | add its value | 0 |
| Selection | cons the unchanged head | [] |
| Transformation | cons a changed head | [] |
| Membership | return True immediately | False at exhaustion |
| Sortedness | require this pair and remaining pairs | True with fewer than two elements |
| Split | prepend only to the front component | empty front paired with current suffix |

For ordinary product the identity is 1, not 0; the existing sum/product/length examples explain those foundational choices. The new conditional-sum and counting questions show why a shared structural shape can need different contributions.

## 2. Positional lookup: preserve the original index

A position is a distance from the beginning, starting at zero. A helper counts down while the public function keeps the original index for the result pair. Reporting the helper's final counter would incorrectly report zero for every successful lookup.

The partial lab signature is `atPosition :: [a] -> Int -> (Int,a)`. Here a safe version returns `Either String (Int,a)` so invalid inputs can be tested without crashing. Result consumption is taught in [Either in Depth](/docs/sem3/csi243/09-polymorphism/notes/either-in-depth). A length-four list has indices zero through three: equality with the length is invalid.

### Template and reading guide

```haskell
atPosition :: [a] -> Int -> Either String (Int,a)
atPosition xs original
  | original < 0 = Left "negative index"
  | otherwise = go xs original
  where
    go [] _ = Left "index outside list"
    go (x:_) 0 = Right (original,x)
    go (_:rest) remaining = go rest (remaining - 1)
```

`original` stays fixed; `remaining` counts heads still to skip. The zero equation precedes the general cons equation. The empty pattern rejects oversize indices without computing length. Each recursive call consumes one head.

### Common errors and repair

`Right (remaining,x)` reports `(0,x)` at success. Repair it to use original. A bounds test using only `y > length xs` misses equality. Testing only index zero hides the lost-index error.

A wrong result with the right type need not produce any GHC error. A discriminating test must expose that semantic mistake.

## 3. Threshold selection: largerY

Selection retains every passing value in encounter order, including duplicates. The threshold is strict: a value equal to y is excluded. The result is a list because zero, one or many candidates can pass.

### Template and reading guide

```haskell
largerY :: Ord a => [a] -> a -> [a]
largerY [] _ = []
largerY (x:xs) y
  | x > y = x : largerY xs y
  | otherwise = largerY xs y
```

`x` is the candidate, xs contains all later candidates and y stays fixed. Empty input supplies []. Both branches recurse: rejection does not mean later values fail. Ord supplies comparison; the original integer lab can use `[Integer] -> Integer -> [Integer]`.

## 4. Positive selection and its signed siblings

Positive means strictly greater than zero. Non-negative includes zero; negative means less than zero. These predicates share a keep-or-skip algorithm but answer different questions. Selection keeps existing values rather than changing their signs.

### Template and reading guide

```haskell
positiveNumbers :: [Integer] -> [Integer]
positiveNumbers [] = []
positiveNumbers (x:xs)
  | x > 0 = x : positiveNumbers xs
  | otherwise = positiveNumbers xs

nonNegative :: [Integer] -> [Integer]
nonNegative [] = []
nonNegative (x:xs)
  | x >= 0 = x : nonNegative xs
  | otherwise = nonNegative xs

negativeNumbers :: [Integer] -> [Integer]
negativeNumbers [] = []
negativeNumbers (x:xs)
  | x < 0 = x : negativeNumbers xs
  | otherwise = negativeNumbers xs
```

Each base returns []; each branch consumes xs. Only the predicate changes. The original order and duplicates survive in every selected result.

## 5. Adjacent pairs: descending, ascending and strict order

Sortedness validates every neighbouring pair without rearranging anything. Descending with ties means non-increasing, using `>=`; strictly descending uses `>`. Ascending has the corresponding `<=` and `<` variants. Empty and singleton lists have no bad pair, so all four conventions accept them.

### Template and reading guide

```haskell
ordered :: (a -> a -> Bool) -> [a] -> Bool
ordered _ [] = True
ordered _ [_] = True
ordered relation (x:y:rest) = relation x y && ordered relation (y:rest)

isSorted :: Ord a => [a] -> Bool
isSorted = ordered (>=)

strictDesc :: Ord a => [a] -> Bool
strictDesc = ordered (>)

ascending :: Ord a => [a] -> Bool
ascending = ordered (<=)

strictAsc :: Ord a => [a] -> Bool
strictAsc = ordered (<)
```

`relation` is the required relation for one adjacent pair. Retain y in the recursive `(y:rest)` so it meets its next neighbour. Exactly one input element is removed at each continuing step. Specialise to `[Integer] -> Bool` for the original lab.

## 11. Bounded prefixes: take

Taking n elements means up to n, rather than requiring exactly n. Non-positive counts return an empty prefix, and oversize counts stop at exhaustion. The count and the list shape are independent stopping conditions.

### Template and reading guide

```haskell
takeR :: Int -> [a] -> [a]
takeR n _ | n <= 0 = []
takeR _ [] = []
takeR n (x:xs) = x : takeR (n - 1) xs
```

The guard covers both negative and zero counts. The empty equation covers exhaustion with a positive count. Otherwise copy one head and reduce n while consuming xs.

## 12. Bounded suffixes: drop

Dropping n skips up to n heads and returns the remaining suffix. Non-positive counts preserve the whole input. Oversize counts exhaust it and return [], so dropping at exactly the length is valid even though indexing there fails.

### Template and reading guide

```haskell
dropR :: Int -> [a] -> [a]
dropR n xs | n <= 0 = xs
dropR _ [] = []
dropR n (_:xs) = dropR (n - 1) xs
```

Return the current xs at the count base and [] at exhaustion. The recursive step emits nothing: it skips one head and decreases n.

## 13. Return both halves: splitAt

A split returns the prefix and suffix together. Splitting at the length is valid, with an empty suffix. One recursive traversal can derive both components instead of walking independently for take and drop.

### Template and reading guide

```haskell
splitR :: Int -> [a] -> ([a],[a])
splitR n xs | n <= 0 = ([],xs)
splitR _ [] = ([],[])
splitR n (x:xs) = (x:front,back)
  where
    (front,back) = splitR (n - 1) xs
```

The recursive pair names two results of one call. On returning, add x only to front; back remains the suffix found at the boundary. Empty and non-positive policies follow take and drop.
