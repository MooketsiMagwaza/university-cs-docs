A **list comprehension** is a distinctive feature of Haskell. It allows a list to be created based on another list — describing the new list in terms of an existing one.

The syntax has two parts separated by a pipe:

```text
[ first part | second part ]
```

Read the pipe as **“such that.”**

```text
ghci> [x * 2 | x <- [1,2,3,4,5]]
[2,4,6,8,10]
```

Read aloud: “the list of `x * 2`, such that `x` is drawn from `[1,2,3,4,5]`.”

### The template, formalised, with every variation named

Everything in this lesson is one template, used with or without its optional pieces.

**Template:**
```haskell
[ expr | x <- xs, condition ]
```
`expr` is the output function — what gets built. `x <- xs` is a generator — where the values come from. `condition`, after the comma, is optional and may be repeated, comma-separated, any number of times. Every variation below is this same template with one piece added, removed, or repeated.

**Example:**
```haskell
squares :: [Integer] -> [Integer]
squares xs = [x * x | x <- xs]
```
```text
ghci> squares [1,2,3,4]
[1,4,9,16]
```
This is the template with `condition` left out entirely — a comprehension needs at least one generator, but zero conditions is completely ordinary, not a special case requiring different syntax. Every value the generator produces is kept.

**A variation: one condition** — covered fully in Section 2 below, e.g. `[x | x <- [1..10], mod x 2 == 0]`.

**A variation: several conditions, comma-separated** — also Section 2, e.g. `[x | x <- [1..50], mod x 3 == 0, mod x 5 == 0]`; every listed condition must hold, since a comma inside a comprehension means "and."

**A variation: several generators (nested iteration)** — Section 4 below, e.g. `[x + y | x <- [1,2,3], y <- [-3,0,3]]`, where the rightmost generator varies fastest.

**A variation: a tuple pattern in the generator** — Section 6 below, e.g. `[name | (name, mark) <- marks, mark >= 70]`, which destructures each pair as it is drawn instead of naming the whole tuple and taking it apart separately.

## Before memorising syntax: the four-stage machine

A comprehension is easier to understand when you stop seeing it as one dense line. For each possible input, Haskell repeats four conceptual stages:

1. **Generate** a candidate value from the source list.
2. **Test** the candidate with every Boolean condition, from left to right.
3. **Produce** the output expression only when all tests pass.
4. **Collect** each produced value into a new list, preserving generation order.

Take this example:

```haskell
[x * x | x <- [1,2,3,4,5], even x]
```

Do not begin with the squaring. The generator and tests determine which values survive first:

| Generated `x` | `even x` | Produce `x * x`? | Contribution to result |
|---:|:---:|:---:|---:|
| `1` | `False` | No | nothing |
| `2` | `True` | Yes | `4` |
| `3` | `False` | No | nothing |
| `4` | `True` | Yes | `16` |
| `5` | `False` | No | nothing |

Only the produced values are collected, so the final result is `[4,16]`. A rejected candidate does not contribute a placeholder, `False`, `0`, or an empty sublist. It contributes nothing at all.

This gives a dependable reading order:

```text
[ output | generator, test ]
              1        2
     3                         then collect as 4
```

The output is written first in the source code, but it is easiest to *reason* in this order: generator → tests → output → collection.

### The symbols do four different jobs

In `[x * x | x <- xs, even x]`:

- the outer `[` and `]` say that the whole expression produces a list;
- the pipe `|` separates the value to produce from the rules for producing it;
- the generator arrow `<-` means “draw one value from this list,” not assignment;
- the comma moves to the next qualifier and behaves like “and then.” Between Boolean tests, that means every test must be `True`.

Do not confuse the two arrows used elsewhere in Haskell. `->` appears in function types and lambdas, while `<-` points the other way and appears here in generators (and later in `do` blocks for extracting an action's result).

### Names come into scope from left to right

The generator introduces its name. Before `x <- xs`, there is no new `x`; after it, later tests, later generators, and the output expression may use `x`.

```haskell
[(x, y) | x <- [1..3], y <- [x..3]]
```

This is valid because `x` is already in scope when Haskell reaches `y <- [x..3]`. Reversing the qualifiers is not equivalent:

```haskell
[(x, y) | y <- [x..3], x <- [1..3]]
-- error: x is not in scope inside the first generator
```

The same rule explains why a test cannot use a name that is introduced only by a later generator. Read qualifiers from left to right and ask, “Which names have been introduced so far?”

### The result type comes from the output expression

The generator's element type and the output type do not have to be the same:

```haskell
[show x | x <- [1,2,3]]       -- [String]
[(x, even x) | x <- [1,2,3]]  -- [(Integer, Bool)]
[x > 2 | x <- [1,2,3]]        -- [Bool]
```

The source supplies integers in all three examples, but the expression before `|` decides what each surviving integer becomes. A comprehension always returns a list, even when exactly one or zero values survive.

## 1. The first part: the output function

Everything **before** the pipe is the **output function**. It specifies what to apply to each input element. For every value that satisfies the second part, the output function is evaluated and its result is included in the constructed list.

```text
ghci> [x | x <- [1,2,3]]        -- output is the element itself
[1,2,3]
ghci> [x * x | x <- [1,2,3]]    -- output is the square
[1,4,9]
ghci> [(x, x * 2) | x <- [1,2,3]]  -- output is a tuple
[(1,2),(2,4),(3,6)]
```

The output function does not have to mention the generated variable at all, though it usually does.

## 2. The second part: generators and tests

Everything **after** the pipe specifies how to get the input elements. It can be a generator, one or more tests, or both.

### Generators

A **generator** has the form `symbol <- listExpression`. It says that the symbol takes each value from the list expression in turn.

```text
x <- [1..10]
```

Read: “`x` is drawn from the list `[1..10]`” — that is, `x` takes each integer between 1 and 10.

### Tests

**Tests** are comma-separated Boolean expressions, also called predicates or filters. Only values for which every test is `True` are used.

```text
ghci> [x | x <- [1..10], mod x 2 == 0]
[2,4,6,8,10]
```

Read: “the list of `x`, such that `x` is drawn from 1 to 10, and `x` is even.”

Several tests may be combined:

```text
ghci> [x | x <- [1..50], mod x 3 == 0, mod x 5 == 0]
[15,30,45]
```

Both conditions must hold, so this keeps multiples of 15.

<CommonMistake title="Separating tests with the wrong punctuation">
Multiple tests are normally separated by **commas**, never semicolons: `[x | x <- xs, x > 0, even x]`. Writing `[x | x <- xs; x > 0]` is a parse error. A comma inside a comprehension reads as "and," so every test listed must hold, exactly like chaining conditions with `&&` would outside one. Joining the conditions with `&&` inside a single test, as in `[x | x <- xs, x > 0 && even x]`, is also valid and gives the same result; commas are simply the idiomatic form.
</CommonMistake>

### One problem, three equivalent views

A comprehension can perform transformation, filtering, or both. Compare the same job—square only the even inputs—written three ways:

```haskell
-- Comprehension: output, source, condition
squaredEvens xs = [x * x | x <- xs, even x]

-- Higher-order pipeline: filter first, then map
squaredEvensMap xs = map (\x -> x * x) (filter even xs)

-- Explicit recursion: spell out the traversal and choices
squaredEvensRec [] = []
squaredEvensRec (x:xs)
  | even x    = x * x : squaredEvensRec xs
  | otherwise = squaredEvensRec xs
```

These definitions have the same data flow:

| Comprehension part | `map`/`filter` part | Recursive part |
|---|---|---|
| `x <- xs` | consume `xs` | match `(x:xs)` |
| `even x` | `filter even` | guard `even x` |
| `x * x` | `map (\x -> x * x)` | cons `x * x` |
| no surviving value | filtered value disappears | recurse without consing |
| input exhausted | pipeline reaches `[]` | base case returns `[]` |

Use this correspondence to debug. If you are unsure what a comprehension means, translate it into `map` and `filter`, or write the two recursive equations. If the translation does not describe the intended job, the comprehension probably does not either.

<Callout type="info" title="Order of transform and test">
In `[x * x | x <- xs, even x]`, the test uses the original `x`, then the output squares it. `map (\x -> x * x) (filter even xs)` matches that order. Writing `filter even (map (\x -> x * x) xs)` asks whether each *square* is even. It happens to keep the same elements for this particular property, but that is not generally true. For `[x + 1 | x <- xs, even x]`, testing before and after adding one gives opposite parity.
</Callout>

### A writing recipe when the blank page feels confusing

Suppose the question says: “From a list of marks, return the names of students who scored at least 70.” Build the comprehension in small decisions:

1. **What list am I reading?** `marks`
2. **What does one element look like?** A pair `(name, mark)`
3. **What pattern gives useful names to its parts?** `(name, mark) <- marks`
4. **Which elements survive?** `mark >= 70`
5. **What should one output element be?** `name`
6. **Place those pieces in the template.**

```haskell
[name | (name, mark) <- marks, mark >= 70]
```

The type follows from those same choices. If `marks :: [(String, Integer)]`, then the generator binds `name :: String` and `mark :: Integer`; the test produces `Bool`; the output produces `String`; therefore the entire comprehension produces `[String]`.

### Empty results need no special case

There are two different ways to get `[]`:

```haskell
[x * 2 | x <- []]                  -- source has no candidates
[x * 2 | x <- [1,3,5], even x]     -- candidates exist, but all fail
```

Both return `[]`. The second result does not indicate an error; it is the correct list of all outputs whose inputs passed the tests—there simply were none. Unlike manual recursion, a comprehension needs no separate written base case because the list machinery supplies it.

## 4. Multiple generators

Multiple generators allow elements from two or more lists to be combined. Every combination is produced:

```text
ghci> [x + y | x <- [1,2,3], y <- [-3,0,3]]
[-2,1,4,-1,2,5,0,3,6]
```

Nine results, because three values of `x` each pair with three values of `y`.

**The rightmost generator varies fastest.** `x` is fixed at 1 while `y` runs through all three values, then `x` becomes 2, and so on — exactly like a nested loop with the second generator innermost.

```text
ghci> [(x, y) | x <- [1,2], y <- "ab"]
[(1,'a'),(1,'b'),(2,'a'),(2,'b')]
```

A later generator may depend on an earlier one, which avoids generating combinations you would only discard:

```text
ghci> [(x, y) | x <- [1..4], y <- [x..4]]
[(1,1),(1,2),(1,3),(1,4),(2,2),(2,3),(2,4),(3,3),(3,4),(4,4)]
```

Generators and tests may be interleaved, and a test placed early filters before the later generators run:

```text
ghci> [(x, y) | x <- [1..5], even x, y <- [1..2]]
[(2,1),(2,2),(4,1),(4,2)]
```

### A variation: a generator that draws from a list of lists

The two generators above each drew from an independent, already-flat list. Nothing requires that — a later generator may draw from a list produced by iterating the *elements* of an earlier one, which is exactly how a comprehension flattens a list of lists into one list while filtering it in the same breath.

```haskell
-- Keep only the positive numbers, out of a list of lists of numbers.
flattenPositives :: [[Int]] -> [Int]
flattenPositives xss = [x | xs <- xss, x <- xs, x > 0]
```
```text
ghci> flattenPositives [[1,-2,3],[-4,5],[],[6]]
[1,3,5,6]
```
Read the two generators in order, exactly as Section 4 already teaches: `xs <- xss` draws each *inner list* in turn — `[1,-2,3]`, then `[-4,5]`, then `[]`, then `[6]` — and for each one, `x <- xs` draws every element of *that* inner list before `xs` advances to the next one. The empty inner list `[]` contributes nothing and needs no special case: there is simply nothing for `x` to be drawn from that time. The final `x > 0` test applies to every element produced this way, regardless of which inner list it came from.

## 5. Comprehensions and recursion are interchangeable

Every comprehension can be written as a recursion, and vice versa. Compare the filter from the previous lesson:

```haskell
-- Recursive
positiveNumbers :: [Integer] -> [Integer]
positiveNumbers [] = []
positiveNumbers (x:xs)
  | x > 0     = x : positiveNumbers xs
  | otherwise = positiveNumbers xs

-- Comprehension
positiveNumbers' :: [Integer] -> [Integer]
positiveNumbers' xs = [x | x <- xs, x > 0]
```

```text
ghci> positiveNumbers' [-1,5,-3,8]
[5,8]
```

Both produce the same list. The comprehension states *what* the result is; the recursion states *how* to build it.

```haskell
-- Recursive
doubleAll :: [Integer] -> [Integer]
doubleAll []     = []
doubleAll (x:xs) = (x * 2) : doubleAll xs

-- Comprehension
doubleAll' :: [Integer] -> [Integer]
doubleAll' xs = [x * 2 | x <- xs]
```

A complete program runs both comprehension versions on a few varied lists, including two edge cases worth checking by habit — an empty list, and a list with nothing surviving the filter:

```haskell
main :: IO ()
main = do
  print (positiveNumbers' [-1,5,-3,8])
  print (positiveNumbers' [-4,-4,-4])
  print (positiveNumbers' [])
  print (doubleAll' [1,2,3])
  print (doubleAll' [])
  print (doubleAll' [-5,0,5])
```

Exact output:

```text
[5,8]
[]
[]
[2,4,6]
[]
[-10,0,10]
```

`positiveNumbers' [-4,-4,-4]` is `[]` not because the input was empty but because every element failed the test `x > 0` — an empty *result* from a non-empty *input*, which the comprehension handles with no special case at all.

<Callout type="info" title="When to prefer which">
A comprehension reads best when the result is “each element of that list, transformed and/or filtered.” Recursion is required when the result depends on more than one element at a time (as in `isSorted`), when elements must be combined into a single value (as in `sum`), or when the recursion is not over a list at all.
</Callout>

## 6. Comprehensions over tuples and strings

The generator pattern may itself be a pattern, which destructures as it generates:

```haskell
marks :: [(String, Integer)]
marks = [("Kago", 72), ("Naledi", 68), ("Thato", 91)]
```

```text
ghci> [name | (name, mark) <- marks, mark >= 70]
["Kago","Thato"]
ghci> [(name, mark + 5) | (name, mark) <- marks]
[("Kago",77),("Naledi",73),("Thato",96)]
```

A complete program tries the filter both ways round the same threshold, to see the two results are complementary:

```haskell
main :: IO ()
main = do
  print [name | (name, mark) <- marks, mark >= 70]
  print [(name, mark + 5) | (name, mark) <- marks]
  print [name | (name, mark) <- marks, mark < 70]
```

Exact output:

```text
["Kago","Thato"]
[("Kago",77),("Naledi",73),("Thato",96)]
["Naledi"]
```

The first and third lines partition `marks` into two disjoint groups — everyone at or above 70, and everyone below it — using the same generator with opposite tests. Between them they account for all three students, with nobody counted twice.

Because a `String` is a list of `Char`, comprehensions work on text directly:

```text
ghci> [c | c <- "CSI243", c `elem` ['0'..'9']]
"243"
```

## 7. Common errors

| Attempt | Problem | Repair |
|---|---|---|
| `[x <- [1..5] \| x * 2]` | The two parts are the wrong way round | Output first, then pipe, then generator |
| `[x \| x <- [1..5]; even x]` | Tests are separated by commas | `[x \| x <- [1..5], even x]` |
| `[x \| x = [1..5]]` | A generator uses `<-`, not `=` | `x <- [1..5]` |
| `[x + y \| x <- [1,2]]` with `y` undefined | Every name must be generated or in scope | Add a generator for `y` |
| Result is empty unexpectedly | No element satisfies the tests | Check the predicate; try it alone at the prompt |
| Combinations in an unexpected order | The rightmost generator varies fastest | Reorder the generators |
