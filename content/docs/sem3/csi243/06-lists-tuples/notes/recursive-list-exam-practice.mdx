## 1. How to attempt the questions

Allow six to ten minutes per design question. Award one mark for the signature, two for complete base/step equations, one for a decreasing input, one for the dry run and one for a discriminating boundary test. A library call may calculate the result but does not meet an explicit patterns-and-recursion restriction.

Use this attempt template:

```text
Read:   what result shape and boundary policy are required?
Plan:   what information must one call retain for the next?
Base:   what shape, count or predicate ends the problem?
Step:   what is emitted, and what becomes smaller?
Check:  empty, singleton, every branch and a counterexample to a tempting wrong answer
```

Each variation is a complete executable program. The exam answer then narrates its design and a reduction. Safe wrappers let missing input be tested without a crash; [Maybe in Depth](/docs/sem3/csi243/09-polymorphism/notes/maybe-in-depth) and [Either in Depth](/docs/sem3/csi243/09-polymorphism/notes/either-in-depth) teach how to consume those results.

## 2. Prefix selection: takeWhile

A prefix predicate consumes consecutive passing heads from the beginning. It stops at the first failure even if later elements would pass. Lab 5 asks for patterns and recursion, so calling takeWhile is not an implementation of that requirement.

### Template and reading guide

```haskell
takeWhileR :: (a -> Bool) -> [a] -> [a]
takeWhileR _ [] = []
takeWhileR p (x:xs)
  | p x = x : takeWhileR p xs
  | otherwise = []
```

p tests the original head. A passing head is copied; a failing one ends the whole prefix. Compare selection: its rejection branch recurses, whereas this one returns [] immediately.

```haskell
  | otherwise = []

main :: IO ()

```

```text

```

</HaskellTryIt>

## 3. Drop a prefix: dropWhile

Dropping while a predicate holds removes only the initial passing run. The first failing head and every later value remain. Later passing values are not dropped because prefix removal has finished.

### Template and reading guide

```haskell
dropWhileR :: (a -> Bool) -> [a] -> [a]
dropWhileR _ [] = []
dropWhileR p whole@(x:xs)
  | p x = dropWhileR p xs
  | otherwise = whole
```

The as-pattern `whole@(x:xs)` names both the current suffix and its pieces. Passing heads are skipped. Returning whole on failure preserves the boundary head.

## 4. One-pass predicate splits: span and break

span returns the maximal passing prefix together with the suffix starting at the first failure. break stops at the first success of its supplied predicate, so it is span with the condition negated. Neither partitions all matches across the list.

### Template and reading guide

```haskell
spanR :: (a -> Bool) -> [a] -> ([a],[a])
spanR _ [] = ([],[])
spanR p whole@(x:xs)
  | p x = (x:front,back)
  | otherwise = ([],whole)
  where
    (front,back) = spanR p xs

breakR :: (a -> Bool) -> [a] -> ([a],[a])
breakR p = spanR (\x -> not (p x))
```

The recursive pair is used only when the current head passes. On failure return ([],whole). break negates p because its stopping condition is True rather than False.

## 5. Append: consume the first list

Append places the entire first list before the second, preserving order and duplicates. When the first ends, the answer is the second list. Their lengths may differ, but their element type must agree.

### Template and reading guide

```haskell
appendR :: [a] -> [a] -> [a]
appendR [] ys = ys
appendR (x:xs) ys = x : appendR xs ys
```

Keep ys fixed while consuming xs. Each returning cons retains one first-list head. Return ys directly at the base without walking it.

## 6. Interleave: choose a leftovers policy

Interleaving alternates one value from each list. Here it retains every leftover value after either input ends. This differs from the shortest-input policy of zip; neither unequal-list case may be left implicit.

### Template and reading guide

```haskell
interleaveR :: [a] -> [a] -> [a]
interleaveR [] ys = ys
interleaveR xs [] = xs
interleaveR (x:xs) (y:ys) = x : y : interleaveR xs ys
```

Provide a base for either exhaustion direction. Otherwise emit x then y and consume both tails. Total remaining length decreases by two in the continuing equation.

## 7. Reverse with an accumulator invariant

## 8. Safe maximum: use a real seed

## 13. Safe init: retain all but the final cell

Init removes one required final element. Empty input fails, while a singleton succeeds with an empty prefix. Longer lists retain the current head and recursively remove the final element from the tail.

### Template and reading guide

```haskell
initR :: [a] -> Maybe [a]
initR [] = Nothing
initR [_] = Just []
initR (x:xs) = case initR xs of
  Nothing -> Nothing
  Just rest -> Just (x:rest)
```

The singleton base removes exactly one final cell. The longer equation adds x to the returned prefix. Nothing propagation is exhaustive, although xs is non-empty in this branch on finite defined input.

## 14. Two-list pairing and arithmetic: stop at the shorter

Pairwise processing consumes one head from each input and stops when either ends. Pairing may combine different element types; adding or subtracting needs compatible numeric values. This is a different unequal-list policy from interleave retaining leftovers.

### Template and reading guide

```haskell
zipR :: [a] -> [b] -> [(a,b)]
zipR [] _ = []
zipR _ [] = []
zipR (x:xs) (y:ys) = (x,y) : zipR xs ys

combineR :: (a -> b -> c) -> [a] -> [b] -> [c]
combineR _ [] _ = []
combineR _ _ [] = []
combineR f (x:xs) (y:ys) = f x y : combineR f xs ys
```

Both exhaustion directions have bases. Each output consumes one cell from each input, so result length is the shorter input length. f may build a pair or calculate one result from two heads.

## 15. Missing data and partial operations

The safe algorithms locate boundaries without deliberately crashing a runnable example. Prelude head, tail, last, init and (!!) return unwrapped results and have smaller valid domains. For finite defined input:

| Operation | Data required | Boundary |
|---|---|---|
| head xs | a first cell, and its value when the result is demanded | head [] has no head |
| tail xs | one cell to remove | tail [] fails; tail [x] returns [] |
| last xs | a final cell found by traversing the spine | last [] fails; an infinite spine has no end |
| init xs | a final cell to remove, reached as the result is consumed | init [] fails; init [x] returns [] |
| xs !! n | non-negative n and a cell after n skips | negative, exactly length and larger indices fail |

The spine is the chain of cons cells; inspecting it does not automatically evaluate every element. Length needs the spine; printing a selected head also needs that value. See [Lazy Evaluation](/docs/sem3/csi243/10-reasoning-revision/notes/lazy-evaluation) for partial demands and undefined values. A produced prefix of an init-like algorithm may be available before reaching the end, but its entire finite result still needs the final boundary.

This plain fence deliberately omits the empty case:

```haskell
-- Deliberately partial: demand firstOnly [] to expose missing data.
firstOnly :: [a] -> a
firstOnly (x:_) = x
```

The key runtime phrase is `Non-exhaustive patterns`. With `-Wincomplete-patterns`, GHC can warn `Pattern match(es) are non-exhaustive`. Adding an explicit error at [] explains failure but does not make a partial function total.

A type error is a separate category:

```haskell
-- Deliberately wrong: cons makes a list, but the result promises Int.
badCount :: [Int] -> Int
badCount [] = 0
badCount (_:xs) = 1 : badCount xs
```

GHC's key diagnostic phrase is `Couldn't match`. Repair the step to `1 + badCount xs`. The compiler catches incompatible result types; it does not infer that the prose required a different comparison.
