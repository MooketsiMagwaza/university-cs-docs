## 2. Worked example: `sumNumbers`

**Purpose.** `sumNumbers n` computes the sum of all positive whole numbers up to and including `n`.

**Examples.**

```text
sumNumbers 1 = 1
sumNumbers 3 = 1 + 2 + 3 = 6
sumNumbers 5 = 15
```

**Base case.** The smallest positive whole number is `1`, and the sum up to `1` is `1`.

**Recursive step.** The sum up to `n` is `n` plus the sum up to `n - 1`.

**Specification.**

```text
sumNumbers n = | 1                       if n = 1
               | n + sumNumbers (n - 1)  if n > 1
```

**Signature and implementation.**

```haskell
-- Sum all positive whole numbers up to and including n.
sumNumbers :: Integer -> Integer
sumNumbers 1 = 1
sumNumbers n = n + sumNumbers (n - 1)
```

**Verification.**

```text
ghci> sumNumbers 1
1
ghci> sumNumbers 5
15
ghci> sumNumbers 100
5050
```

## 3. The same recursion in every form

Chapter 4 gave four ways to express a choice. A recursive definition is a choice between the base case and the recursive step, so all four apply.

```haskell
-- 1. Pattern matching: base case is a literal, so this reads best.
sumPat :: Integer -> Integer
sumPat 1 = 1
sumPat n = n + sumPat (n - 1)

-- 2. Guards
sumGuard :: Integer -> Integer
sumGuard n
  | n == 1    = 1
  | otherwise = n + sumGuard (n - 1)

-- 3. Conditional expression
sumIf :: Integer -> Integer
sumIf n = if n == 1 then 1 else n + sumIf (n - 1)

-- 4. Case expression
sumCase :: Integer -> Integer
sumCase n =
  case n of
    1 -> 1
    _ -> n + sumCase (n - 1)
```

All four compute the same values. The rule from Chapter 4 still decides: the base case here is a **literal**, so pattern matching expresses it most directly.

When the base case is a **range**, guards win:

```haskell
-- The base case covers 0 and 1, which no single literal pattern can express.
facSafe :: Integer -> Integer
facSafe n
  | n >= 0 && n <= 1 = 1
  | otherwise        = n * facSafe (n - 1)
```

## 4. Recursion on two arguments

Not every recursion counts down a single number. `rangeSum` takes two integers and returns the sum of all integers from the first to the second, inclusive.

```text
ghci> rangeSum 3 5
12
```

Because `3 + 4 + 5 = 12`.

**Which argument shrinks?** The gap between them must close. Moving the *first* argument up towards the second does that:

```text
rangeSum m n = | m               if m = n
               | m + rangeSum (m + 1) n   if m < n
```

**What about `rangeSum 9 6`, where the first exceeds the second?** The specification must say. Two defensible choices: return `0` for an empty range, or report an error. Here we treat a reversed range as empty:

```haskell
-- Sum every integer from m to n inclusive; a reversed range sums to zero.
rangeSum :: Integer -> Integer -> Integer
rangeSum m n
  | m > n     = 0
  | m == n    = m
  | otherwise = m + rangeSum (m + 1) n
```

```text
ghci> rangeSum 3 5
12
ghci> rangeSum 4 4
4
ghci> rangeSum 9 6
0
```

Dry running confirms it:

```text
rangeSum 3 5
= 3 + rangeSum 4 5
= 3 + (4 + rangeSum 5 5)
= 3 + (4 + 5)            <- base case reached
= 3 + 9
= 12
```

<Callout type="info" title="Order the guards carefully">
`m > n` must be tested before `m == n`, and both before the recursive step. Reversing the first two still works, because the conditions are mutually exclusive — but putting the recursive step anywhere but last would make it capture cases meant for the base.
</Callout>

## 5. Recursion that builds on another recursive function

`sumFac n` computes `fac 0 + fac 1 + … + fac n`. It is recursive, and its recursive step calls a *different* recursive function:

```haskell
-- Sum the factorials of every whole number from 0 to n.
sumFac :: Integer -> Integer
sumFac 0 = 1
sumFac n = fac n + sumFac (n - 1)
```

```text
ghci> sumFac 3
10
```

Because `fac 0 + fac 1 + fac 2 + fac 3 = 1 + 1 + 2 + 6 = 10`.

The base case is `sumFac 0 = 1` because `fac 0` is `1`. Writing `sumFac 0 = 0` would be a natural-looking mistake — and the dry run catches it, because the total would come out one short. Here is that dry run, so the claim has evidence behind it rather than just asserting it.

**Dry run: `sumFac 3`, with the correct base case.** Using `fac 0 = 1`, `fac 1 = 1`, `fac 2 = 2`, `fac 3 = 6` from earlier in this chapter:

```text
sumFac 3
= fac 3 + sumFac 2
= fac 3 + (fac 2 + sumFac 1)
= fac 3 + (fac 2 + (fac 1 + sumFac 0))
= fac 3 + (fac 2 + (fac 1 + 1))     <- base case reached: sumFac 0 = 1
= 6 + (2 + (1 + 1))
= 6 + (2 + 2)
= 6 + 4
= 10
```

Matches `sumFac 3` at the prompt: `10`.

**Now retrace with the mistaken base case, `sumFac 0 = 0`.** Every other line is identical — only the base-case substitution changes:

```text
sumFac 3
= fac 3 + sumFac 2
= fac 3 + (fac 2 + sumFac 1)
= fac 3 + (fac 2 + (fac 1 + sumFac 0))
= fac 3 + (fac 2 + (fac 1 + 0))     <- base case reached: sumFac 0 = 0 (the mistake)
= 6 + (2 + (1 + 0))
= 6 + (2 + 1)
= 6 + 3
= 9
```

A complete program confirms the buggy total:

```haskell
fac :: Integer -> Integer
fac 0 = 1
fac n = n * fac (n - 1)

-- BUGGY: the base case should return 1 (fac 0), not 0.
sumFacBug :: Integer -> Integer
sumFacBug 0 = 0            -- the mistake
sumFacBug n = fac n + sumFacBug (n - 1)

main :: IO ()
main = print (sumFacBug 3)
```

```text
9
```

Both traces are identical except for one substituted value, and that is exactly what makes the dry run useful here: the fault is pinned to a single line — the base-case substitution — rather than showing up only as a mysteriously wrong final number.

## 6. Worked example: a recursive list generator (`evensUpTo`)

The functions so far have each produced a single number. `evensUpTo` produces a **list**, built up as the recursion unwinds — the same "cons in the recursive step" shape Chapter 6 uses throughout, reached here starting from a number rather than from an existing list.

**Purpose.** `evensUpTo n` returns the list of even numbers from `2` up to and including `n`, in ascending order (or up to the largest even number below `n`, if `n` is odd).

**Examples.**

```text
evensUpTo 1 = []
evensUpTo 2 = [2]
evensUpTo 7 = [2,4,6]
evensUpTo 8 = [2,4,6,8]
```

**Base case.** The recursion tracks a running value, counting up from `2`. Once that running value has stepped past `n`, there are no more even numbers to add, and the answer for that point onward is the empty list.

**Recursive step.** If the running value has not yet passed `n`, put it at the front of the list and recurse with the next even number, two higher.

This counts **up** rather than down, which needs the same trick as `rangeSum` in Section 4: a helper that closes the gap between a starting point and a target, carried in an extra argument the public function hides.

**Signature and implementation.**

```haskell
-- Helper: build the ascending list of even numbers from k up to n.
evensFrom :: Integer -> Integer -> [Integer]
evensFrom k n
  | k > n     = []
  | otherwise = k : evensFrom (k + 2) n

-- Build the list of even numbers from 2 up to (and including, if even) n.
evensUpTo :: Integer -> [Integer]
evensUpTo n = evensFrom 2 n
```

Read `evensFrom` equation by equation:

- `k > n`: the base-case guard. Once the running value `k` has stepped past the bound `n`, nothing more belongs in the list, so the answer is `[]`.
- `k : evensFrom (k + 2) n`: the recursive step. `:` conses `k` onto the **front** of whatever the recursive call produces; the call itself asks for the rest of the list starting two higher, skipping the odd number in between since only even numbers are wanted.

**Dry run: `evensUpTo 7`.**

```text
evensUpTo 7
= evensFrom 2 7
= 2 : evensFrom 4 7
= 2 : (4 : evensFrom 6 7)
= 2 : (4 : (6 : evensFrom 8 7))
= 2 : (4 : (6 : []))             <- base case reached: 8 > 7
= [2,4,6]
```

**Verification.**

```haskell
evensFrom :: Integer -> Integer -> [Integer]
evensFrom k n
  | k > n     = []
  | otherwise = k : evensFrom (k + 2) n

evensUpTo :: Integer -> [Integer]
evensUpTo n = evensFrom 2 n

main :: IO ()
main = do
  print (evensUpTo 1)
  print (evensUpTo 2)
  print (evensUpTo 7)
  print (evensUpTo 8)
```

```text
[]
[2]
[2,4,6]
[2,4,6,8]
```

## 7. Worked example: recursive linear search (`containsValue`)

**Purpose.** `containsValue v xs` decides whether the value `v` occurs anywhere in the list `xs`.

**Examples.**

```text
containsValue 3 [1,2,3]  = True
containsValue 5 [1,2,3]  = False
containsValue 'a' "cat"  = True
containsValue 7 []       = False
```

**Base case.** The smallest list is the empty list, and nothing occurs in it: `containsValue v [] = False`, whatever `v` is.

**Recursive step.** For a non-empty list `(x:xs)`, `v` occurs in it exactly when `v` is the head, or `v` occurs somewhere in the tail.

**Signature.** Comparing `v` against elements requires `==`, which is only available for types that support equality — so the type needs an `Eq a` constraint:

```haskell
containsValue :: Eq a => a -> [a] -> Bool
```

**Implementation.**

```haskell
-- Does v occur anywhere in xs?
containsValue :: Eq a => a -> [a] -> Bool
containsValue _ []     = False
containsValue v (x:xs)
  | v == x    = True
  | otherwise = containsValue v xs
```

Read the pattern `(x:xs)` the way Chapter 6 will introduce it formally: `x` is the head of the list, the one element being looked at right now; `xs` is everything after it, the list still to search if `x` is not a match. The two equations are exhaustive the same way every list recursion's are: `[]` is the base case, `(x:xs)` covers every non-empty list, and together they cover every possible list.

**Dry run: `containsValue 3 [5,1,3,9]`, a value that is found.**

```text
containsValue 3 [5,1,3,9]
= containsValue 3 [1,3,9]     <- guard: 3 == 5 is False, so recurse on the tail
= containsValue 3 [3,9]       <- guard: 3 == 1 is False, so recurse on the tail
= True                         <- guard: 3 == 3 is True, returned directly, no further call
```

**Dry run: `containsValue 5 [1,2,3]`, a value that is absent.**

```text
containsValue 5 [1,2,3]
= containsValue 5 [2,3]       <- guard: 5 == 1 is False
= containsValue 5 [3]         <- guard: 5 == 2 is False
= containsValue 5 []          <- guard: 5 == 3 is False
= False                        <- base case reached: containsValue _ [] = False
```

Both traces terminate — one by finding a match partway through and returning immediately, the other by exhausting the list down to `[]` and letting the base case answer. That is the shape of every linear search: shrink towards `[]`, and either a guard fires early or the base case has the final word.

**Verification.**

```haskell
containsValue :: Eq a => a -> [a] -> Bool
containsValue _ []     = False
containsValue v (x:xs)
  | v == x    = True
  | otherwise = containsValue v xs

main :: IO ()
main = do
  print (containsValue 3 [1,2,3])
  print (containsValue 5 [1,2,3])
  print (containsValue 'a' "cat")
  print (containsValue (7 :: Integer) [])
```

```text
True
False
True
False
```

<CommonMistake title="Forgetting to recurse on the tail">
A tempting first attempt is `containsValue v (x:xs) = v == x`, with no `otherwise` branch calling `containsValue` again. This compiles, and even passes a quick test where the value happens to be the *first* element — but it only ever looks at the head. `containsValue 3 [5,1,3,9]` would incorrectly return `False`, because only `3 == 5` is checked. Every recursive search needs an explicit "keep looking in the rest of the list" branch, or it stops after one comparison.
</CommonMistake>

<Callout type="info" title="An index-returning variant">
A natural extension asks *where* the value is, not just whether it is present, by threading a position counter through the recursion — the same technique `atPosition` uses in Chapter 6. That variant is left as an exercise; `containsValue` itself is the version later chapters build on.
</Callout>

## 8. Common errors

| Symptom | Cause | Repair |
|---|---|---|
| Function hangs | The argument does not shrink | Check the recursive call actually changes the argument |
| Off-by-one in the total | The base case returns the wrong value | Re-read the specification for the smallest input |
| Base case never matched | The argument skips past it | Make the step move by one, or widen the base to a range with guards |
| Works for `n > 0`, hangs on `0` | The base case is `1` but `0` was allowed by the type | Either widen the base case or reject `0` explicitly |
| Correct for small `n`, unbearably slow for large | The definition recomputes sub-results, as `fib` does | Acceptable at this stage; note it and move on |
| List-generator returns `[]` unexpectedly | The base-case guard (e.g. `k > n`) fires before the first value is consed | Check the guard's boundary against the examples, especially the smallest one |
| `No instance for (Eq a)` | A function compares elements with `==` but the signature omits the constraint | Add `Eq a =>` before the arrow, as `containsValue` does |


Note the wildcard in `power _ 0 = 1`: the base value is irrelevant when the exponent is `0`, and `_` documents that. Only the second argument shrinks; the first is carried along unchanged.

</Accordion>
<Accordion title="Check question 5">

```haskell
gcdRec :: Integer -> Integer -> Integer
gcdRec a 0 = a
gcdRec a b = gcdRec b (a `mod` b)
```

It terminates because `a mod b` is always strictly less than `b`, so the second argument decreases on every call and cannot go below `0`. The argument shrinks even though no subtraction is visible — the requirement is that *something* measurably decreases towards the base case, not that it decreases by one.

</Accordion>
