---
title: "2. Dry Running a Recursive Function"
description: "Trace a recursive call by hand through unwinding and rewinding, lay out a dry run for marks, and use tracing to find termination faults and wrong answers."
---



A **dry run** is a hand trace of a function: you substitute the argument into the definition and reduce, step by step, writing down every intermediate expression until a value appears. In plain English: pretend you are the computer — replace each call with its own definition, one line at a time, exactly as written, until a plain value is left with nothing more to substitute. Decoding a dense definition into a sentence like that before acting on it is the same habit [Decoding Exam and Lab Language](/docs/sem3/csi243/decoding-questions) teaches for lab and exam wording generally.

Dry running is a required part of every laboratory submission in this course, and it is examinable. It is also the fastest way to find out why a recursive function loops forever or returns the wrong answer.

## 1. Why trace by hand

A compiler proves that types are consistent. It does not prove that your formula matches the problem. A dry run is the evidence that it does.

Tracing answers three questions at once:

1. **Does it terminate?** Watch whether the argument shrinks towards the base case.
2. **Is the answer right?** Compare the final value against the specification.
3. **Where is the fault?** The first line that looks wrong locates the bug.

## 2. Unwinding and rewinding

A recursive evaluation has two phases. Recognising them is the whole skill.

<StepByStep>
  <StepByStepTitle>The two phases of a recursive call</StepByStepTitle>

  <Step number={1}>
  <StepTitle>Unwinding</StepTitle>
  Each call replaces itself with the recursive step, producing a longer and longer expression. Nothing is calculated yet — the calls are stacking up, waiting.
  </Step>

  <Step number={2}>
  <StepTitle>Hitting the base case</StepTitle>
  Eventually an argument matches the base case, which returns a value directly instead of calling again. The stacking stops.
  </Step>

  <Step number={3}>
  <StepTitle>Rewinding</StepTitle>
  That value is substituted back into the waiting expression, and the arithmetic is finally performed, innermost first, until one value remains.
  </Step>
</StepByStep>

## 3. A full dry run: `fac 5`

Using the definition:

```haskell
fac :: Integer -> Integer
fac 0 = 1
fac n = n * fac (n - 1)
```

**Unwinding.** Each line substitutes the argument into the recursive step:

```text
fac 5
= 5 * fac 4
= 5 * (4 * fac 3)
= 5 * (4 * (3 * fac 2))
= 5 * (4 * (3 * (2 * fac 1)))
= 5 * (4 * (3 * (2 * (1 * fac 0))))
```

**Base case.** `fac 0` matches the first equation and returns `1` without calling again:

```text
= 5 * (4 * (3 * (2 * (1 * 1))))
```

**Rewinding.** Now the multiplications are performed, innermost first:

```text
= 5 * (4 * (3 * (2 * 1)))
= 5 * (4 * (3 * 2))
= 5 * (4 * 6)
= 5 * 24
= 120
```

So `fac 5` evaluates to `120`. Confirm at the prompt:

```text
ghci> fac 5
120
```

<Callout type="info" title="How to lay this out for marks">
Show one reduction per line, keep the parentheses so the pending calls are visible, mark the line where the base case is reached, and state the final value on its own line. A trace that jumps from `fac 5` to `120` earns nothing, because it demonstrates no reasoning.
</Callout>

## 4. Tracing a two-branch recursion: `fib 5`

`fib` calls itself **twice** per step — once for `n - 1`, once for `n - 2`. The previous lesson drew those calls out as a branching call-tree diagram. A dry run, though, is still written the same way as every other trace in this lesson: one line per step, top to bottom — it does not draw itself as a tree on the page. The branching is still there; it is just carried by the **nested parentheses** instead of by shape. Each pair of parentheses below is one call waiting on both of its children, the same waiting the diagram showed as two branches meeting at a node.

```haskell
fib :: Integer -> Integer
fib 0 = 0
fib 1 = 1
fib n = fib (n - 1) + fib (n - 2)
```

```text
fib 5
= fib 4 + fib 3
= (fib 3 + fib 2) + (fib 2 + fib 1)
= ((fib 2 + fib 1) + (fib 1 + fib 0)) + ((fib 1 + fib 0) + 1)
= (((fib 1 + fib 0) + 1) + (1 + 0)) + ((1 + 0) + 1)
= (((1 + 0) + 1) + (1 + 0)) + ((1 + 0) + 1)
= ((1 + 1) + 1) + (1 + 1)
= (2 + 1) + 2
= 3 + 2
= 5
```

<Callout type="info" title="Where the tree is hiding in this trace">
[How Recursion Works](/docs/sem3/csi243/05-recursion/notes/how-recursion-works) draws this exact computation as a call-tree diagram, with one node per call and the leaves at the base cases `fib 1` and `fib 0`. Put that diagram next to the trace above: every opening parenthesis here is a node splitting into two children in the diagram, and every `fib 1` or `fib 0` in the trace is a leaf being reached. The diagram and this trace describe the identical set of calls — the diagram shows the branching shape at a glance; the trace shows the arithmetic actually being carried out, line by line.
</Callout>

Checking against the sequence table in the previous lesson: position 5 holds `5`. Correct.

Notice how often `fib 1` and `fib 0` appear. `fib 5` evaluates `fib 2` three separate times. This is why the naive Fibonacci definition becomes unusably slow well before `fib 40` — the work doubles with each step. Chapter 10 returns to the cost of recursive definitions.

## 5. Using a trace to find a fault

Suppose a student writes:

```haskell
-- Intended: sum all whole numbers up to n.
sumNumbers :: Integer -> Integer
sumNumbers 1 = 1
sumNumbers n = n + sumNumbers n   -- fault is here
```

The type checker is satisfied. The trace exposes the problem immediately:

```text
sumNumbers 4
= 4 + sumNumbers 4
= 4 + (4 + sumNumbers 4)
= 4 + (4 + (4 + sumNumbers 4))
...
```

The argument never changes, so the base case is never reached. In GHCi this appears as a session that hangs, or eventually a stack overflow. The repair is to shrink the argument:

```haskell
sumNumbers n = n + sumNumbers (n - 1)
```

<Callout type="warn" title="Two lines is usually enough">
You rarely need a full trace to spot a termination fault. Write two or three unwinding steps and look at the argument. If it is not moving towards the base case, stop — the fault is found.
</Callout>

## 6. Tracing a wrong answer

A function can terminate and still be wrong. Here the base case returns the wrong value:

```haskell
fac :: Integer -> Integer
fac 0 = 0          -- should be 1
fac n = n * fac (n - 1)
```

```text
fac 3
= 3 * fac 2
= 3 * (2 * fac 1)
= 3 * (2 * (1 * fac 0))
= 3 * (2 * (1 * 0))
= 3 * (2 * 0)
= 3 * 0
= 0
```

Every factorial returns `0`. The trace shows exactly where: the base case injected a `0` that then absorbed the whole product. Comparing the trace against the specification's `fac 0 = 1` locates the error in one line.

## 7. Tail recursion vs. naive recursion

Look again at the fully unwound trace of `fac 5` from Section 3, just before rewinding starts:

```text
= 5 * (4 * (3 * (2 * (1 * fac 0))))
```

That is a single number, `5`, and four **pending multiplications**, each one waiting on the result of a call that has not returned yet. Nothing can be computed until `fac 0` finally resolves — only then, right at the end, does the rewinding phase perform all four multiplications, innermost first. The deeper the recursion, the longer that chain of pending multiplications grows before any arithmetic happens at all.

There is another way to write factorial that avoids building up that pending chain: carry the running answer along as an extra argument, updating it at every step instead of leaving it for later.

```haskell
-- Multiply acc by every whole number from n down to 1, then return it.
-- acc is the answer accumulated so far; it starts at 1, the identity for *.
facAcc :: Integer -> Integer -> Integer
facAcc acc 0 = acc
facAcc acc n = facAcc (acc * n) (n - 1)

-- Compute n! by starting the accumulator at 1 and counting down from n.
fac' :: Integer -> Integer
fac' n = facAcc 1 n
```

Read the equations one at a time:

- `facAcc acc 0 = acc` — the base case: once the countdown argument reaches `0`, there is nothing left to multiply in, so the accumulated answer *is* the final answer. Return it directly.
- `facAcc acc n = facAcc (acc * n) (n - 1)` — the recursive step: multiply `n` into the accumulator **now**, then recurse with one less left to do and the already-updated accumulator.
- `fac' n = facAcc 1 n` — the function a caller actually uses. It seeds the accumulator at `1`, the multiplicative identity, and hands the counting off to `facAcc`.

This shape — where the recursive call is the very last thing that happens, and every piece of the answer is folded into an argument before that call, rather than left pending — is called **tail recursion**, and the extra argument that carries the running answer is an **accumulator**.

**Tracing `fac' 4`.** Compare this, line by line, with the naive trace of `fac 4` from the previous lesson:

```text
fac' 4
= facAcc 1 4
= facAcc (1 * 4) 3
= facAcc 4 3
= facAcc (4 * 3) 2
= facAcc 12 2
= facAcc (12 * 2) 1
= facAcc 24 1
= facAcc (24 * 1) 0
= facAcc 24 0
= 24                    <- base case reached, and the answer was already sitting in acc
```

Every line of the `facAcc` trace is a plain, fully-evaluated number — `4`, `12`, `24` — with nothing left multiplying against a not-yet-returned call. There is no separate rewinding phase at all: by the time the base case fires, the answer is already sitting in `acc`, and `facAcc acc 0 = acc` just hands it back.

Both compute the same function. A complete program confirms it:

```haskell
fac :: Integer -> Integer
fac 0 = 1
fac n = n * fac (n - 1)

facAcc :: Integer -> Integer -> Integer
facAcc acc 0 = acc
facAcc acc n = facAcc (acc * n) (n - 1)

fac' :: Integer -> Integer
fac' n = facAcc 1 n

main :: IO ()
main = do
  print (fac 4)
  print (fac' 4)
  print (fac 10)
  print (fac' 10)
```

```text
24
24
3628800
3628800
```

<CommonMistake title="Seeding the accumulator with the wrong value">
`fac' n = facAcc 1 n` seeds the accumulator at `1`, not `0`. `1` is the identity for multiplication — the same reasoning behind `sum' [] = 0` and `product' [] = 1` in Chapter 6: the base case must be the value that leaves the result unchanged. Seeding with `facAcc 0 n` would multiply every partial product by `0` at the very first step, and `fac' n` would return `0` for every `n`, no matter how large.
</CommonMistake>

<Callout type="info" title="Why bother, if the answer is the same?">
For `fac 4`, the difference is invisible — both versions return `24` instantly. It starts to matter for large `n`, where the naive version's pending chain of multiplications takes real memory to hold before any of it can be evaluated, while the accumulator version never holds more than one number at a time. GHC can sometimes optimise tail-recursive functions like `facAcc` to run in constant space; Chapter 10 returns to this trade-off in more depth.
</Callout>


The argument moves *away* from the base case with every call, so `fac 0` is never matched and the recursion never terminates. This is not a coding slip — it is the function being applied outside its domain. The specification said factorial is defined for non-negative integers, but the type `Integer -> Integer` promises a result for every integer. The next lessons close that gap.
