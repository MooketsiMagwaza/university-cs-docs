Encapsulation and abstraction are related but different:

- **encapsulation** bundles state with behaviour and controls access to representation;
- **abstraction** exposes the essential contract while hiding implementation detail.

## 1. Preserve an invariant

An invariant is a condition that should remain true for every valid object state.

~~~java
public final class Account {
    private double balance; // Representation is hidden.

    public Account(double openingBalance) {
        if (openingBalance < 0) {
            throw new IllegalArgumentException("negative opening balance");
        }
        balance = openingBalance;
    }

    public boolean withdraw(double amount) {
        if (amount <= 0 || amount > balance) {
            return false; // State remains valid and unchanged.
        }
        balance -= amount;
        return true;
    }

    public double getBalance() {
        return balance;
    }
}
~~~

## 2. Access modifiers

| Modifier | Same class | Same package | Subclass outside package | Unrelated outside class |
|---|---:|---:|---:|---:|
| public | yes | yes | yes | yes |
| protected | yes | yes | yes, with protected receiver rules | no |
| package-private | yes | yes | no | no |
| private | yes | no | no | no |

“No modifier” means package-private; it is not the same as public.

## 3. Program to a contract

When callers depend only on public operations, the implementation may change without rewriting caller logic.

## 4. Benefits and limits

Encapsulation supports data protection, local reasoning, testing, and implementation freedom. It does not guarantee good design: a class with setters for every field may still expose invalid state transitions.

Abstraction reduces what a caller must understand. It does not mean “hide everything”; the contract, constraints, results, and failure behaviour must be clear.
