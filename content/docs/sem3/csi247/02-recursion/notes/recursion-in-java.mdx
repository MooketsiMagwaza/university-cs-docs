<Callout type="analogy">

You're in a long queue and want to know your position. You ask the person in front, "what's your position?" They don't know either, so they ask the person in front of them, and so on. The person at the very front knows without asking: "I'm number 1". Then each answer travels back: "I'm 2", "I'm 3"… until it reaches you. Each person did one small step and trusted someone else with the smaller problem.

</Callout>

## The two parts of every recursive method

1. **A base case**: a version of the problem small enough to answer directly, with no further calls. (The person at the front of the queue.)
2. **A recursive case**: a rule that solves the problem by calling the same method on a *smaller* input, then uses that answer. Each call must move closer to the base case.

The classic example is the **factorial** of a whole number, written *n*!, which is the product of all whole numbers from 1 to *n*: 4! = 4 × 3 × 2 × 1 = 24. Notice that 4! = 4 × 3!, and in general *n*! = *n* × (*n*−1)!. That's a smaller version of the same problem, so it maps directly onto recursion.

```java title="Factorial.java"
public static long factorial(int n) {
    if (n <= 1) {                    // BASE CASE: 1! (and 0!) is 1 — answer directly
        return 1;
    }
    return n * factorial(n - 1);     // RECURSIVE CASE: n! = n × (n−1)!   (n−1 is smaller → progress)
}
// factorial(4) → 24
```

## How it actually runs

Recursion isn't magic; it uses the same call stack as any other method call. Each call to `factorial` gets its own stack frame with its own separate `n`. A call can't finish until the call it made returns, so frames pile up on the way down and are removed on the way back up.

## When recursion goes wrong

If there's no base case, or the recursive call doesn't make the problem smaller, the method calls itself forever. Each call adds a frame, the stack's memory runs out, and Java stops with a **`StackOverflowError`**. The same error can happen with a correct method if the recursion is simply too deep (typically many thousands of nested calls), which is why algorithms that recurse *n* levels deep on large inputs are a problem, as you'll see with quick sort's worst case.

```java title="Broken.java"
static int broken(int n) {
    return n * broken(n - 1);   // ✗ no base case → calls never stop → StackOverflowError
}
```

## Divide and conquer

Many fast algorithms use a recursive strategy called **divide and conquer**:

1. **Divide** the problem into smaller pieces of the same kind.
2. **Conquer** each piece by solving it recursively (tiny pieces are base cases).
3. **Combine** the pieces' answers into an answer for the whole.

Binary search divides the array in half and only needs to conquer one half. Merge sort divides in half, sorts both halves, and combines them by merging. Quick sort divides around a pivot and sorts both sides; its combine step is free. Whenever a problem is halved at every level, there are about log₂ *n* levels, which is where the "log *n*" in their running times comes from.

<Callout type="tip">

When writing a recursive method, don't try to follow every call in your head. Make sure the base case is right, then *trust* that the recursive call correctly solves the smaller problem, and only ask: "given that answer, how do I solve my problem?" This mental leap is sometimes called the "recursive leap of faith".

</Callout>

<Callout type="key">

Every recursive method needs a base case and a recursive case that makes the problem smaller. Each call gets its own stack frame. No base case means `StackOverflowError`. Halving at each level gives log *n* levels.

</Callout>
