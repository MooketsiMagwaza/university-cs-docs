Insertion sort grows one sorted section from left to right. On every pass it picks up the next value, shifts larger values one place to the right, and inserts the saved value into the gap.

Think of arranging playing cards in your hand. The cards already in your left hand stay sorted; you pick up one new card and slide it into the correct position among them.

## 1. What moves during a pass?

We will use the same array for the whole explanation:

```text
start  [4, 2, 5, 1, 3]
goal   [1, 2, 3, 4, 5]
```

Four ideas must stay separate:

| Term | What it means |
|---|---|
| **Sorted section** | The left prefix that is already in order |
| **Key** | The card picked up for this pass and stored in a variable |
| **Shift** | Copy a larger card one position to the right |
| **Insertion** | Drop the saved key into the final gap |

A shift is **not** a swap. The key stays safely in a variable while the gap travels left through the sorted section.

The important invariant is now visible: at the start of pass `i`, `arr[0..i-1]` is sorted. When the key fills the gap, `arr[0..i]` is sorted. The green section therefore grows by exactly one card after each pass.

<Callout title="Why the key must be saved first">
When the first larger value shifts right, it overwrites the key's original array cell. `int key = arr[i]` protects that value before any shifting begins.
</Callout>

## 3. Properties you should know

| Property | Insertion sort | Why |
|---|---|---|
| Best-case time | `O(n)` | A sorted array needs one failed key comparison per pass and no shifts |
| Average-case time | `O(n²)` | Keys usually move through part of the sorted section |
| Worst-case time | `O(n²)` | A reverse-sorted array makes each key cross the whole sorted section |
| Extra space | `O(1)` | Only the key and indexes are stored |
| Stable | Yes | Equal values do not cross when the condition uses `>` |
| Adaptive | Yes | Nearly sorted input causes only a few local shifts |

The cost is controlled by **how far each key travels**. This is why insertion sort can feel almost linear on nearly sorted data but becomes quadratic on reverse-sorted data.

## 4. Read the Java after the movement makes sense

```java
public static void insertionSort(int[] arr) {
    for (int i = 1; i < arr.length; i++) {
        int current = arr[i];
        int j = i - 1;

        while (j >= 0 && arr[j] > current) {
            arr[j + 1] = arr[j];
            j--;
        }

        arr[j + 1] = current;
    }
}
```

Java evaluates `&&` from left to right and short-circuits. The boundary test `j >= 0` must come first; when it is false, `arr[j]` is not evaluated.

### Complete runnable example

```java
import java.util.Arrays;

public class InsertionSortDemo {
    public static void insertionSort(int[] arr) {
        for (int i = 1; i < arr.length; i++) {
            int current = arr[i];
            int j = i - 1;
            while (j >= 0 && arr[j] > current) {
                arr[j + 1] = arr[j];
                j--;
            }
            arr[j + 1] = current;
        }
    }

    public static void main(String[] args) {
        int[] values = {8, 3, 5, 1};
        insertionSort(values);
        System.out.println(Arrays.toString(values));
    }
}
```

## 5. Ascending and descending order

The algorithm stays the same. Only the question asked by the `while` condition changes:

| Required order | Shift when | Meaning |
|---|---|---|
| Ascending | `arr[j] > current` | Move larger values right |
| Descending | `arr[j] < current` | Move smaller values right |

For descending order, shift values that are **smaller** than `current`:

```java
while (j >= 0 && arr[j] < current) {
    arr[j + 1] = arr[j];
    j--;
}
```

### Exam-style dry run

Sort `[50, 83, 76, 6, 32, 90, 12, 2, 59]` in descending order. A complete answer shows the array at the end of **every** pass, including passes where nothing moves.

| Pass | Key | Operation | Array at the end of the pass |
|---:|---:|---|---|
| Start | - | The first value is the initial sorted section | `[50, 83, 76, 6, 32, 90, 12, 2, 59]` |
| 1 | 83 | `50 < 83`; shift 50, insert 83 | `[83, 50, 76, 6, 32, 90, 12, 2, 59]` |
| 2 | 76 | `50 < 76`; shift 50, insert 76 after 83 | `[83, 76, 50, 6, 32, 90, 12, 2, 59]` |
| 3 | 6 | `50 < 6` is false; no shift | `[83, 76, 50, 6, 32, 90, 12, 2, 59]` |
| 4 | 32 | `6 < 32`; shift 6, insert 32 after 50 | `[83, 76, 50, 32, 6, 90, 12, 2, 59]` |
| 5 | 90 | Shift `6, 32, 50, 76, 83`; insert 90 at the front | `[90, 83, 76, 50, 32, 6, 12, 2, 59]` |
| 6 | 12 | `6 < 12`; shift 6, insert 12 after 32 | `[90, 83, 76, 50, 32, 12, 6, 2, 59]` |
| 7 | 2 | `6 < 2` is false; no shift | `[90, 83, 76, 50, 32, 12, 6, 2, 59]` |
| 8 | 59 | Shift `2, 6, 12, 32, 50`; insert 59 after 76 | `[90, 83, 76, 59, 50, 32, 12, 6, 2]` |

The pass number is the key's original index. Nine values therefore produce eight passes.

## 6. Shifting is not repeated swapping

Some explanations describe an insertion as repeated adjacent swaps. That can produce the same final array, but the implementation above does something more precise:

1. save `current` once;
2. copy each larger value one cell right;
3. write `current` once into the final gap.

This distinction matters when counting writes. State the convention used by a question before comparing algorithms.

<CommonMistake title="Overwriting the value being inserted">
If the code shifts `arr[i - 1]` into `arr[i]` before saving `arr[i]`, the original current value is lost. Always assign `current = arr[i]` before the first shift.
</CommonMistake>

## 7. Common errors

| Attempt | What happens | Repair |
|---|---|---|
| Start `i` at 0 | There is no previous sorted prefix; `j` begins at -1 | Start at `i = 1` |
| Test `arr[j]` before `j >= 0` | A value smaller than all earlier values causes an invalid access | Put the boundary check first |
| Write to `arr[j]` after shifting | `j` has moved one position left of the gap | Insert at `arr[j + 1]` |
| Use `>=` for ascending order | Equal records can reverse order | Use `>` to preserve stability |
| Compare with `arr[i]` during shifts | `arr[i]` may have been overwritten | Compare with saved `current` |
