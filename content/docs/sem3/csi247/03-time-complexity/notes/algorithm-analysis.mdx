## What is an algorithm?

An **algorithm** is a precise, step-by-step procedure for solving a problem that is guaranteed to finish. A recipe is an everyday algorithm. "Look through the list from the start until you find the name" is an algorithm for searching. An algorithm is the *idea*; a Java method is one way of *writing it down* so a computer can follow it. The same algorithm can be written in any programming language.

For any problem there are usually several algorithms that all give the right answer. They differ in how much **time** they take and how much **memory** they need. This page gives you the vocabulary for comparing them.

## Why not just time it?

You could run two methods and time them with a stopwatch, but the result would depend on how fast your computer is, what else it is doing, which Java version you run and, above all, on the particular input you tried. Instead, computer scientists count how many **basic steps** (comparisons, assignments, array reads) an algorithm performs, and ask: *as the input gets bigger, how fast does that number grow?* The size of the input is always called ***n***. For searching and sorting, *n* is the number of elements in the array.

## Big-O notation

<KeyTerm title="Big-O notation">

A way of describing how an algorithm's number of steps grows as the input size *n* grows, keeping only the fastest-growing part and ignoring constant multipliers. "O" stands for "order of". O(n) is read "order n" or "big-O of n".

</KeyTerm>

Suppose an algorithm takes exactly 3*n* + 5 steps. For *n* = 1,000,000 that's 3,000,005 steps. The "+ 5" is irrelevant at that size, and the "3×" depends on details like how fast one step is on a given machine. What really matters is that the cost is *proportional to n*: double the input and you double the work. So we write it as **O(n)**. Likewise, *n*²/2 + *n*/2 steps is written **O(n²)**, because for large *n* the *n*² part dominates everything else.

The rules for simplifying are:

1. **Keep only the fastest-growing term.** *n*² + 100*n* + 7 becomes *n*².
2. **Drop constant multipliers.** 5*n* becomes *n*; *n*²/2 becomes *n*².

## A logarithm, explained from zero

Two of the most important growth rates contain "log", so let's make sure that word holds no fear. The **logarithm base 2** of a number, written log₂ *n*, answers one question: *"how many times can I halve n before I get down to 1?"*

| *n* | Halving it repeatedly | Number of halvings = log₂ *n* |
| --- | --- | --- |
| 8 | 8 → 4 → 2 → 1 | 3 |
| 16 | 16 → 8 → 4 → 2 → 1 | 4 |
| 1,024 | 1024 → 512 → … → 1 | 10 |
| 1,000,000 | … | about 20 |
| 1,000,000,000 | … | about 30 |

Equivalently, log₂ *n* is the power you'd raise 2 to in order to get *n*: 2³ = 8, so log₂ 8 = 3. The crucial thing to notice is how *slowly* it grows. Multiplying *n* by a thousand only adds about 10 to log₂ *n*. Any algorithm that throws away half of the remaining work at each step (like binary search) takes O(log *n*) steps, which is why it can search a billion items in about 30 steps. In Big-O we usually just write "log *n*" because the base only changes a constant multiplier.

## The common growth rates

| Big-O | Name | What it feels like | Example in this course |
| --- | --- | --- | --- |
| **O(1)** | constant | Same time no matter how big the input | Reading `a[i]`; swapping two elements |
| **O(log n)** | logarithmic | Grows very slowly; double *n* → one more step | Binary search |
| **O(n)** | linear | Double *n* → double the time | Linear search; finding the maximum |
| **O(n log n)** | "n log n", linearithmic | A little more than linear | Merge sort; quick sort on average |
| **O(n²)** | quadratic | Double *n* → four times the time | Bubble, selection and insertion sort |

## How to work out Big-O from code

You can usually read the growth rate straight off the loop structure:

- **No loop over the input** (just a fixed number of statements) → O(1).
- **One loop** that visits each element once → O(*n*).
- **A loop inside a loop**, each running up to *n* times → O(*n*²). This is the nested-loop multiplication from the Decisions & loops page.
- **A loop that halves the remaining range each time** → O(log *n*).
- **Halving into pieces, but doing O(*n*) work at each level of halving** → O(*n* log *n*).

```java title="Shapes of cost"
// O(1): one step regardless of n
int first = a[0];

// O(n): the body runs n times
for (int i = 0; i < n; i++) { total += a[i]; }

// O(n²): the inner body runs about n × n times
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) { count++; }
}

// O(log n): `size` is halved each time, so about log₂ n iterations
for (int size = n; size > 1; size = size / 2) { steps++; }
```

<Callout type="note" title="The sum 1 + 2 + … + (n−1)">

In bubble, selection and insertion sort the inner loop gets one shorter each time: it runs (*n*−1) times, then (*n*−2), and so on down to 1. That sum equals *n*(*n*−1)/2. Here's why: write the sum forwards and backwards and add the pairs, (1 + (*n*−1)), (2 + (*n*−2)), …; each pair is *n*, and there are (*n*−1) pairs, which counts every term twice, so divide by 2. *n*(*n*−1)/2 = *n*²/2 − *n*/2, which simplifies to O(*n*²).

</Callout>

## Best, average and worst case

The number of steps often depends on the input itself, not just its size. Searching for a name that happens to be first in the list is instant; searching for one that isn't there at all means checking everything. So we describe three cases:

- **Best case**: the luckiest possible input of size *n*.
- **Average case**: the expected cost over typical (random) inputs.
- **Worst case**: the unluckiest possible input. This is usually the most important one, because it is a *guarantee*: the algorithm will never be slower than this.

## Time and space

Big-O is used for memory as well. **Space complexity** measures how much *extra* memory an algorithm needs beyond the input itself. Insertion sort needs only a few variables whatever the size of the array: O(1) extra space. Merge sort needs a second array as big as the input: O(*n*) extra space. Sometimes you can trade one for the other.

<Callout type="caution">

Big-O describes behaviour as *n* grows large. For small inputs, an O(*n*²) algorithm with very simple steps can beat an O(*n* log *n*) one with complicated steps. That is exactly why Java's built-in sort switches to insertion sort for small pieces of an array.

</Callout>

<Callout type="key">

Count steps, not seconds. Keep the fastest-growing term and drop constants. log₂ *n* = how many times you can halve *n*. From fastest to slowest: O(1) \< O(log *n*) \< O(*n*) \< O(*n* log *n*) \< O(*n*²).

</Callout>
