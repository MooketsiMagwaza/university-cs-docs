Java's standard library contains thousands of types. Packages divide that library into named groups such as `java.lang`, `java.util`, and `java.io`.

| Package | Typical purpose | Examples |
|---|---|---|
| `java.lang` | Fundamental language classes | `String`, `Math`, `System` |
| `java.util` | Collections and general utilities | `Scanner`, `ArrayList`, `Arrays`, `Random` |
| `java.io` | Stream and file input/output | `File`, `FileReader`, `BufferedReader`, `PrintWriter` |

## 1. Simple and fully qualified names

The class's **fully qualified name** combines its package and simple name:

```text
java.util.Scanner
| package | class |
```

Java can use the full name directly:

```java
java.util.Scanner input = new java.util.Scanner(System.in);
```

An import lets the same source file use the short name `Scanner`:

```java
import java.util.Scanner;

public class ReadName {
    public static void main(String[] args) {
        Scanner input = new Scanner(System.in);
        System.out.print("Name: ");
        String name = input.nextLine();
        System.out.println("Hello, " + name);
        input.close();
    }
}
```

The import changes name lookup in this source file. It does **not** copy the class into the file or make an external library available.

A wildcard imports types from one package only. `import java.util.*;` does not import `java.util.concurrent.*`, because subpackages are separate packages.

`java.lang` is automatically available, which is why programs use `String`, `System`, and `Math` without explicit imports.

## 3. Name conflicts

Both `java.util` and `java.sql` contain a class named `Date`. Importing both simple names is ambiguous:

```java
import java.util.Date;
import java.sql.Date;
```

`javac` reports that a type with the same simple name is already defined by another import. A clear repair is to import one and fully qualify the other:

```java
import java.util.Date;

public class DatesDemo {
    Date createdAt;
    java.sql.Date storedDate;
}
```

<CommonMistake title="Expecting a wildcard to include subpackages">
Package names are not a recursive folder search. `java.util.*` makes types directly inside `java.util` available by simple name, but not types in `java.util.concurrent` or any other subpackage.
</CommonMistake>

## 4. Static imports are different

A normal import brings a **type name** into scope. A static import brings a static member into scope:

```java
import static java.lang.Math.sqrt;

public class DistanceDemo {
    public static void main(String[] args) {
        System.out.println(sqrt(81));
    }
}
```

```text
9.0
```

This is valid, but `Math.sqrt(81)` often communicates the owner more clearly. Use static imports sparingly.

## 5. Common errors

| Attempt | What happens | Repair |
|---|---|---|
| Use `Scanner` with no import | `cannot find symbol` | Import `java.util.Scanner` or use its full name |
| Write `import java.util.Scanner()` | Imports name a type, not a constructor call | Remove parentheses |
| Place an import inside a class | Syntax error | Put imports after any package declaration and before type declarations |
| Expect `java.util.*` to include subpackages | A subpackage type is not found | Import its actual package |
| Import two classes with the same simple name | The simple name becomes ambiguous | Fully qualify at least one |
