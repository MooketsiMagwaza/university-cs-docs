Most real objects are built from other objects.

<ConceptFrame>

<FrameBox label="The idea">

A car isn't a kind of engine; it *has* an engine. Build big things by snapping smaller things together, like building blocks.

</FrameBox>

<FrameBox label="The definition">

**Composition**: a class holds references to other objects as fields (a **has-a** relationship) and **delegates** work to them.

</FrameBox>

<FrameBox label="Why it works">

Inheritance fixes the relationship when you write the code and exposes all of the parent's methods. Composition is looser: parts can be swapped (petrol engine → electric motor) and only the methods you choose are exposed.

</FrameBox>

<FrameBox label="What it is for">

Flexible, testable designs. Experienced developers' standard advice is: *favour composition over inheritance*.

</FrameBox>

</ConceptFrame>

**Figure 11.1** In UML, a hollow triangle means inheritance; a filled diamond on the "whole" end means composition (the part belongs to the whole).

</SvgFigure>

## Example: a car built from an engine

```java title="Engine.java · Car.java"
public class Engine {
    private final int horsepower;
    public Engine(int horsepower) { this.horsepower = horsepower; }

    public void start() {
        System.out.println(horsepower + "hp engine starts");
    }
}

public class Car {
    private final Engine engine;    // HAS-A: a Car is built FROM an Engine

    public Car(Engine engine) {     // the part is handed in from outside
        this.engine = engine;       // → easy to swap engines, or use a fake one when testing
    }

    public void drive() {
        engine.start();             // DELEGATION: Car asks its part to do that part of the job
        System.out.println("Car is moving");
    }
}

// new Car(new Engine(150)).drive();
```

```text
150hp engine starts
Car is moving
```

Passing the part into the constructor, instead of having `Car` create its own engine with `new Engine(…)` inside, is called **dependency injection**. It means the caller decides which engine the car gets, which makes the class more flexible and easier to test.

Combine composition with an interface and you get real flexibility. If `Engine` were an interface with implementations `PetrolEngine` and `ElectricMotor`, the same `Car` class would work with either, chosen at run time, without changing a single line of `Car`.

<Callout type="tip" title="The sentence test">

Say the relationship out loud. If "an X *is a* Y" sounds right, inheritance may fit. If "an X *has a* Y" sounds right, use composition. If "an X *can do* Y" sounds right, use an interface. When in doubt, compose.

</Callout>

<Callout type="key" title="The OOP section in five lines">

- **Encapsulation** protects each object's data.
- **Inheritance** shares code down an is-a hierarchy.
- **Polymorphism** lets one call behave differently for each object.
- **Abstraction** hides implementations behind contracts.
- **Composition** assembles objects from parts.

</Callout>
