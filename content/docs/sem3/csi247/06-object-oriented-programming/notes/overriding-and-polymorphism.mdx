<ConceptFrame>

<FrameBox label="The idea">

Say "speak!" to a room full of animals. You give one instruction, and each animal responds in its own way.

</FrameBox>

<FrameBox label="The definition">

A variable of a **supertype** can refer to an object of any of its **subtypes**. When you call an overridden method, Java runs the version belonging to the object's *actual* class, decided while the program runs. This is called **dynamic dispatch**.

</FrameBox>

<FrameBox label="Why it works">

The calling code depends only on the general type (`Animal`). New subtypes can be added later without touching that code; it simply works with them.

</FrameBox>

<FrameBox label="What it is for">

It replaces long `if (type == DOG) … else if (type == CAT) …` chains, so code can be extended with new types without being modified.

</FrameBox>

</ConceptFrame>

## A subclass object can sit in a superclass variable

Because a `Dog` *is an* `Animal`, Java lets you store a reference to a `Dog` in a variable of type `Animal`:

```java title="Upcast"
Animal a = new Dog("Rex");   // legal: every Dog is an Animal
```

This line involves two different types, and keeping them apart is the key to the whole topic:

- The **reference type** (also called the *declared* or *static* type) is `Animal`: the type written on the variable. The *compiler* looks only at this. It decides which methods you are *allowed* to call.
- The **object type** (also called the *actual* or *run-time* type) is `Dog`: the class of the object that really exists in memory. The *JVM* looks at this while the program runs. It decides *which version* of an overridden method runs.

## One loop, many behaviours

```java title="Zoo.java"
Animal[] zoo = { new Dog("Rex"), new Cat("Tom"), new Animal("Generic") };

for (Animal a : zoo) {
    // ONE line of code, THREE different behaviours.
    // On each iteration the JVM checks the real object and runs ITS speak().
    System.out.println(a.speak());
}
// Adding `class Cow extends Animal` later needs ZERO changes to this loop.
```

```text
Woof!
... Meow
...
```

The loop was written knowing only about `Animal`. It has no idea dogs or cats exist. Yet each object answers in its own way. If someone adds a `Cow` class next year, this loop will print "Moo" without being edited or even recompiled. Code that is *open for extension but closed for modification* is one of the main goals of good design, and polymorphism is how Java achieves it.

## Upcasting, downcasting and `instanceof`

Treating a `Dog` as an `Animal` is called **upcasting** (moving up the hierarchy). It's automatic and always safe, because every dog really is an animal. Going the other way, **downcasting**, needs an explicit cast and can fail, because not every animal is a dog. The `instanceof` operator tests an object's actual type at run time, so you can check before you cast.

```java title="Casting.java"
Animal a = new Dog("Rex");      // upcast: automatic and always safe

// a.fetch();                   // ✗ compile error: the reference type Animal has no fetch()

if (a instanceof Dog d) {       // Java 16+: test the type AND create a Dog variable d in one step
    d.fetch();                  // ✓ inside this block, d is a Dog → Rex fetches the ball.
}

// The older style, still common:
if (a instanceof Dog) {
    Dog d2 = (Dog) a;           // explicit downcast — safe because we just checked
    d2.fetch();
}

Animal b = new Cat("Tom");
// Dog x = (Dog) b;             // ✗ compiles, but throws ClassCastException at run time: Tom is a Cat
```

<Callout type="tip">

If you find yourself writing lots of `instanceof` checks followed by casts, it's often a sign the behaviour should be a method overridden in each subclass instead. Let polymorphism make the decision for you.

</Callout>

## Overriding versus overloading

These two words sound alike but mean very different things, and the difference comes down to *when* the decision is made.

- **Overriding**: a subclass provides its own version of an inherited method with the *same* name and the *same* parameters. Which version runs is decided at **run time** from the object's actual type. This is the polymorphism described above.
- **Overloading**: one class has several methods with the same name but *different* parameter lists. Which one runs is decided at **compile time** from the types of the arguments you write. It's really just a naming convenience.

|   | Overriding | Overloading |
| --- | --- | --- |
| Where | A subclass redefines a parent's method | Usually within the same class |
| Parameters | Identical | Different (number or types) |
| Decided | At run time, by the object's type | At compile time, by the argument types |
| Marked with | `@Override` | nothing |
| Example | `Dog.speak()` replaces `Animal.speak()` | `add(int, int)` and `add(double, double)` |

```java title="Calculator.java"
public class Calculator {
    // Same name, different parameter lists → OVERLOADING.
    // The compiler picks one by looking at the types of the arguments.
    public int    add(int a, int b)        { return a + b; }
    public double add(double a, double b)  { return a + b; }
    public int    add(int a, int b, int c) { return a + b + c; }
}
// calc.add(2, 3)      → the int version     → 5
// calc.add(2.5, 1.0)  → the double version  → 3.5
// calc.add(1, 2, 3)   → the 3-arg version   → 6
```

<Callout type="note">

The return type alone can't distinguish overloads. `int f(int x)` and `double f(int x)` in the same class won't compile, because a call `f(5)` wouldn't tell the compiler which one you mean.

</Callout>

<Callout type="key">

Supertype variable, subtype object. The compiler checks *whether* you may call a method (reference type); the JVM chooses *which version* runs (object type). Overriding is decided at run time, overloading at compile time.

</Callout>

<CheckQuestion question={<>Given <code>Animal a = new Dog("Rex");</code>, which <code>speak()</code> runs, and why does <code>a.fetch()</code> not compile?</>}>

`Dog`'s `speak()` runs, because dispatch uses the object's actual type. `a.fetch()` fails because the compiler only allows methods declared on the reference type, `Animal`, which has no `fetch()`.

</CheckQuestion>

<CheckQuestion question={<>Is <code>println</code> printing an <code>int</code> in one call and a <code>String</code> in another an example of overriding or overloading?</>}>

Overloading. `PrintStream` has several `println` methods with different parameter types, and the compiler picks one from the argument's type.
