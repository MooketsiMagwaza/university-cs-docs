<ConceptFrame>

<FrameBox label="The idea">

A memory diagram is a picture of what is stored in the computer's memory at one moment. Variables are labelled boxes; objects are bigger boxes elsewhere; arrows show which variable leads to which object.

</FrameBox>

<FrameBox label="The definition">

A drawing of the **stack** (variables) and the **heap** (objects and arrays), where every reference is shown as an **address** written in the variable's box and an **arrow** to the object at that address.

</FrameBox>

<FrameBox label="Why it works">

In Java a variable of a class type never holds an object. It holds the object's address. Once you draw addresses and arrows, surprising behaviour (two variables changing "together", `==` being false for equal-looking objects) becomes obvious.

</FrameBox>

<FrameBox label="What it is for">

Predicting what code does, finding bugs, and answering exam questions. You will also use exactly these pictures to understand ArrayLists and linked lists later.

</FrameBox>

</ConceptFrame>

## Two areas of memory: the stack and the heap

While your program runs, Java keeps its data in two separate areas of memory:

- **The stack** holds your *variables*: the names you declared inside methods, such as `int x` or `Student s`. Draw it on the **left**.
- **The heap** holds everything created with `new`: objects and arrays. Draw it on the **right**.

Every object on the heap sits at some **address**: a number that says where in memory it is, just like a house number says where a house is on a street. Real addresses are long, ugly numbers, so in diagrams we simply invent neat ones: 100, 200, 300 and so on. All that matters is that each object has a different one.

<Callout type="analogy">

The heap is a street of houses. Each house (object) has a house number (address). A reference variable is a slip of paper with a house number written on it. Copying the slip of paper does not build a new house; it just gives a second person directions to the same house.

</Callout>

## The ten drawing rules

<Steps>

<Step title="Draw two areas">

Write *Stack* on the left and *Heap* on the right.

</Step>

<Step title="Every variable is a box on the stack">

with its name written above it.

</Step>

<Step title="Primitive variables hold the value itself">

For `int age = 18;` write `18` inside the box. The primitive types are `int`, `double`, `boolean`, `char`, `long`, `float`, `short` and `byte`.

</Step>

<Step title="Every new draws something on the heap">

and gives it a fresh address, written just above it (100, 200, 300…).

</Step>

<Step title="A reference variable holds an address">

Write the address in its box *and* draw an arrow from the box to the object with that address.

</Step>

<Step title="An array is a row of small boxes">

with the index (`[0]`, `[1]`, …) written underneath each one. A new array is never empty: every slot starts with a default value (see the table below).

</Step>

<Step title="An object is one big box">

containing a smaller labelled box for each field (each instance variable).

</Step>

<Step title="Strings are objects too">

A String gets its own box on the heap with its own address, and a String field holds that address. (Unless your lecturer says otherwise, draw them this way: that's how the revision notes do it.)

</Step>

<Step title={"null means \"no object\""}>

Write `null` in the box and draw no arrow.

</Step>

<Step title="Never rub out">

When a value changes, cross out the old value and write the new one beside it. When a reference changes, also cross out the old arrow with an No and draw the new arrow. The examiner wants to see the history.

</Step>

</Steps>

| Array type | Every slot starts as | Example |
| --- | --- | --- |
| `int[]`, `long[]`, `short[]`, `byte[]` | `0` | `new int[3]` → 0, 0, 0 |
| `double[]`, `float[]` | `0.0` | `new double[2]` → 0.0, 0.0 |
| `boolean[]` | `false` | `new boolean[2]` → false, false |
| `char[]` | the "empty" character <code>'\u0000'</code> | usually drawn as a blank |
| any class type: `String[]`, `Student[]`, `Integer[]`… | `null` | `new Student[3]` → null, null, null |

*Table 6a.1 — Fields of a new object get the same defaults before the constructor runs.*

Two lessons from this example. First, `y = x` copied a number, so changing `x` later did nothing to `y`. Second, `other = arr` copied an *address*, so `arr` and `other` lead to the same array and a change through one is seen through the other.

## Example 2: an array of objects

This is the most common exam question, and it's the example from the diagram in your notes. Here is the `Student` class it uses, so you can see where the three fields come from:

```java title="Student.java"
public class Student {
    private String name;    // a reference to a String object
    private int age;        // a primitive: the number sits inside the object
    private double gpa;     // a primitive too

    public Student(String name, int age, double gpa) {
        this.name = name;
        this.age = age;
        this.gpa = gpa;
    }

    public void setName(String name) { this.name = name; }
    public void setAge(int age) { this.age = age; }
}
```

<MemoryDiagram scenario="student" />

<Callout type="mistake">

`new Student[3]` does **not** create three students. It creates one array with three empty (`null`) slots. Only `new Student(…)` creates a student. This is the single most common mistake in memory-diagram questions.

</Callout>

### The same thing from the revision notes: `Course`

Assume `Course` has a String field `code`, an int field `enrol`, a constructor `Course(String code, int enrol)` and setters. Step through it, then try drawing it yourself on paper before pressing **Jump to final diagram**.

<MemoryDiagram scenario="course" />

Notice the expression `ours[1].setCode("CSI247")`. Read it from left to right: *go to the array* (address 100), *take slot \[1\]* (address 200), *follow that arrow to the Course object*, *call setCode on it*. Since `c1` points at the same object, `c1.getCode()` would now also return `"CSI247"`.

## How to answer the question, step by step

1. Read the code once to count how many times `new` appears. That's how many things you'll draw on the heap. (String literals like `"John"` count too.)
2. Go line by line. For each line ask: *does this create something?* (draw it with a new address), *does it declare a variable?* (draw a box on the stack), *does it change something?* (cross out and rewrite).
3. For any expression with dots or brackets, like `ours[1].setCode(…)`, follow the arrows one step at a time to find which box actually changes.
4. At the end, check every reference box: does it contain an address *and* an arrow to the object with that address?

<Callout type="note" title="Garbage">

When nothing points at an object any more (like `"John"` after `setName("Smith")`), the program can never reach it again. Java's **garbage collector** will delete it automatically. You still leave it in your exam diagram: the crossed-out arrow shows what happened. In the stepper we fade such objects out so you can spot them.

</Callout>

<Callout type="key">

Stack on the left, heap on the right. Primitive → value in the box. Reference → address in the box *plus* an arrow. Every `new` (and every String) gets its own address. Arrays of objects start full of `null`. Never erase: cross out and rewrite.

</Callout>

<CheckQuestion question={<>Why does <code>int[] a = &#123;1, 2&#125;; int[] b = a; b[0] = 9;</code> change <code>a[0]</code>?</>}>

`b = a` copies the address of the array, not the array itself. There is only one array, with two variables pointing at it, so changing it through `b` is the same as changing it through `a`.

</CheckQuestion>

<CheckQuestion question={<>How many objects does <code>String[] names = new String[50];</code> create?</>}>

One: the array. All 50 slots are `null` until you put Strings in them.

</CheckQuestion>

<CheckQuestion question={<>Two different <code>Student</code> objects have the same name, age and gpa. Is <code>s1 == s2</code> true?</>}>

No. `==` compares the addresses in the two boxes, and two different objects always have different addresses. To compare contents you need `equals`, which the class must override (see [The Object class](/docs/sem3/csi247/06-object-oriented-programming/notes/object-class-casting-and-wrappers)).

</CheckQuestion>
