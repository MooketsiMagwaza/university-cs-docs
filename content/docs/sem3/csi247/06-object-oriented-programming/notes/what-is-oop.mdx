## The problem: programs get big

The programs on the previous pages were tiny. Real programs, such as a banking system, a school's student records or a game, can contain hundreds of thousands of lines written by many people over many years. If all the data lives in loose variables, and any line of code anywhere can change any of it, then:

- When a value turns out wrong, the culprit could be *any* line in the whole program.
- Changing how one piece of data is stored means hunting down every place that uses it.
- Similar code gets copied and pasted, so a bug fixed in one copy survives in the others.

Programming styles (also called *paradigms*) are ways of organising code to keep it manageable. The style you have seen so far, where a program is a sequence of steps and methods that act on separate data, is called **procedural programming**. It works well for small programs. OOP is a different way of organising larger ones.

## The object-oriented idea

<Callout type="analogy">

Think of a restaurant. Nobody writes one giant instruction list for "run the restaurant". Instead there are *people with roles*: a waiter knows the table numbers and takes orders; a chef knows the recipes and cooks; a cashier knows the bill and takes payment. Each one keeps their own information and does their own jobs. They cooperate by *asking each other* to do things: the waiter doesn't reach into the oven, he hands the order to the chef.

</Callout>

In OOP the program is made of **objects**. Each object bundles together:

- **state**: the facts it knows, stored in variables called *fields* (a bank account's balance and owner), and
- **behaviour**: the jobs it can do, written as *methods* (deposit, withdraw, check balance).

Objects cooperate by calling each other's methods, which is often described as "sending messages". The data and the code that works on it live together, in one place, so when something goes wrong you know where to look.

**Procedural thinking**

"What steps does the program perform?"

Data (a balance variable) and functions (`withdraw(balance, amount)`) are separate. Any function can change any data.

**Object-oriented thinking**

"What things exist, what does each know, and what can each do?"

An `account` object holds its own balance and has its own `withdraw(amount)` method. Only the account changes its balance.

Everything in OOP rests on two words, **class** and **object**, which the next page explains in full. On top of them sit four principles, traditionally called the **four pillars of OOP**. Here is a one-sentence preview of each; each gets its own page.

<Callout type="note">

Java is designed around OOP: every piece of code lives inside a class, and almost everything you use from Java's library (`String`, `ArrayList`, `Scanner`) is a class. You have already been using objects since the first page: `System.out` is an object, and `println` is one of its methods.
