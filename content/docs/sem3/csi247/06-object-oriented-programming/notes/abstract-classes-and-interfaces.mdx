<FrameBox label="The idea">

You drive a car with a steering wheel and two pedals. You don't need to understand fuel injection; that's hidden beneath the surface.

<FrameBox label="The definition">

Abstraction means exposing only the essential operations of a type and hiding the details. Java's two tools are **abstract classes** (partial blueprints with some unfinished methods) and **interfaces** (pure contracts listing what a type can do).

</FrameBox>

<FrameBox label="Why it works">

If calling code depends only on a small contract, the implementations behind it can be swapped, improved or multiplied without callers ever noticing. Less to know means less to break.

</FrameBox>

<FrameBox label="What it is for">

Managing complexity in large systems, and "plug-in" designs. For example, any class that implements `Comparable` can be sorted by Java's sort methods.

</FrameBox>

</ConceptFrame>

## Abstract classes

Some classes describe ideas that should never exist on their own. There's no such thing as "just a shape"; every real shape is a circle, a rectangle, or something specific. Mark such a class `abstract`, and Java will refuse to let anyone write `new Shape(…)`.

An abstract class can contain **abstract methods**: method headers with no body, ending in a semicolon. Each one is a promise: "every concrete (non-abstract) subclass *must* provide this method". Alongside them, an abstract class can contain ordinary fields, constructors and fully written methods that all subclasses share.

```java title="Shape.java"
// abstract → a partial blueprint.  `new Shape(...)` will NOT compile.
public abstract class Shape {
    private final String label;

    protected Shape(String label) {     // abstract classes still have constructors; subclasses call them
        this.label = label;
    }

    // ABSTRACT METHOD: a promise with no body. Every concrete subclass MUST implement it.
    public abstract double area();

    // CONCRETE METHOD: shared code every shape gets for free
    public String summary() {
        return label + " with area " + String.format("%.2f", area());
        //                                            ↑ calls the SUBCLASS's area() — polymorphism!
    }
}
```

```java title="Circle.java · Rectangle.java"
public class Circle extends Shape {
    private final double r;
    public Circle(double r) { super("Circle"); this.r = r; }

    @Override
    public double area() { return Math.PI * r * r; }   // fulfils the promise
}

public class Rectangle extends Shape {
    private final double w, h;
    public Rectangle(double w, double h) { super("Rectangle"); this.w = w; this.h = h; }

    @Override
    public double area() { return w * h; }
}
```

`String.format("%.2f", x)` turns a number into text with exactly two digits after the decimal point. Notice how `summary()` is written once, in `Shape`, yet calls `area()`, which only the subclasses define. When `summary()` runs on a `Circle`, dynamic dispatch calls `Circle`'s `area()`. The general class supplies the overall procedure; the subclasses fill in the specific step. (This arrangement is a well-known design pattern called the *template method*.)

## Interfaces

An **interface** is a pure statement of capability: "any class that implements me *can* do these things". It lists method headers, and a class signs the contract by writing `implements` and providing a body for each one. Interfaces can't have instance fields or constructors, and you can't create an object of an interface type directly.

The big difference from classes: a class can `extend` only one class, but it can `implement` **any number** of interfaces. This gives many of the benefits of multiple inheritance (one type belonging to several families) without the confusion of inheriting conflicting fields from several parents.

Since Java 8, an interface may also contain `default` methods (methods with a body, built on top of the abstract ones) and `static` helper methods. Since Java 9 it may contain `private` helper methods too.

```java title="Drawable.java · Square.java"
// A contract. Its methods are automatically public and abstract.
public interface Drawable {
    void draw();

    default void drawTwice() {          // Java 8+: a ready-made method built on the contract
        draw();
        draw();
    }
}

// extends ONE class, implements ANY number of interfaces
public class Square extends Shape implements Drawable {
    private final double side;
    public Square(double side) { super("Square"); this.side = side; }

    @Override public double area() { return side * side; }    // owed to Shape
    @Override public void draw()   {                          // owed to Drawable
        System.out.println("[] a square with side " + side);
    }
}
```

```java title="ShapesDemo.java"
import java.util.Arrays;
import java.util.List;

// Program to the abstraction, not the implementation:
List<Shape> shapes = Arrays.asList(new Circle(1), new Rectangle(2, 3), new Square(4));

for (Shape s : shapes) {
    System.out.println(s.summary());    // this loop has no idea which shapes exist
}

Drawable d = new Square(2);             // an interface type can hold any implementing object
d.drawTwice();
```

```text
Circle with area 3.14
Rectangle with area 6.00
Square with area 16.00
[] a square with side 2.0
[] a square with side 2.0
```

<Callout type="note" title={"New syntax: List and <Shape>"}>

`List<Shape>` is a list that holds `Shape` references. `List` itself is an interface from Java's library, and the part in angle brackets is a *type parameter* saying what kind of elements it holds; this feature is called **generics**. `Arrays.asList(…)` creates a list of fixed size containing the given items (Java 8 has no `List.of`). You'll see generics again on the Comparable & Comparator page.

</Callout>

## Abstract class or interface?

|   | Abstract class | Interface |
| --- | --- | --- |
| Keywords | `abstract class`, used with `extends` | `interface`, used with `implements` |
| How many a class can have | One | Many |
| Fields | Any, including instance fields (state) | Only constants (`public static final`) |
| Constructors | Yes | No |
| Methods | Abstract and concrete, any access level | Abstract, `default`, `static`, and `private` helpers |
| Use it when… | Closely related classes share state and code | Possibly unrelated classes share a *capability* (`Comparable`, `Runnable`) |

*Table 10.1 — A quick rule: "is a kind of" → abstract class; "can do" → interface.*

<Callout type="mistake">

A concrete class that "forgets" one of the abstract methods it inherits won't compile: *"Square is not abstract and does not override abstract method area() in Shape"*. Either implement the method or mark the class `abstract` as well.

</Callout>

<Callout type="key">

Abstraction = expose *what*, hide *how*. Abstract class: shared state and partial code, single inheritance. Interface: a pure capability, and a class may implement many.

</Callout>

<CheckQuestions>

<CheckQuestion question={<>Can you write <code>Shape s = new Shape("x");</code> if <code>Shape</code> is abstract? Can you write <code>Shape s = new Circle(2);</code>?</>}>

No to the first: abstract classes can't be instantiated. Yes to the second: a variable of the abstract type can refer to an object of any concrete subclass.

</CheckQuestion>

<CheckQuestion question={"When would you choose an interface over an abstract class?"}>

When unrelated classes need to share a capability, or a class needs several capabilities at once (a class can implement many interfaces but extend only one class), and no shared instance state is needed.

</CheckQuestion>
